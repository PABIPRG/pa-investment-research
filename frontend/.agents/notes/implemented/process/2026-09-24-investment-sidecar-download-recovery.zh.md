# Agent Note: 投研侧车下载容忍暂时性网络故障

Status: implemented

中文 | [English](2026-09-24-investment-sidecar-download-recovery.md)

## Problem

原生桌面应用打包时必须取得锁定版本的 Python 压缩包，CI runner 却可能没有缓存。连接超时较短、三次尝试间隔很近时，暂时性的 GitHub 连接故障就会使构建失败。Python 压缩包缓存与前端依赖锁文件绑定，还会让无关的依赖更新触发重新下载。

## Decision

侧车构建器使用明确的连接超时 30 秒、响应头超时 60 秒、响应体空闲超时 120 秒和总时限 8 分钟下载不可变的压缩包。对暂时性网络故障和可重试 HTTP 状态最多尝试 5 次，依次等待 2、4、8、16 秒。永久性 HTTP 错误和压缩包 SHA-256 不匹配仍直接失败。每次失败均删除不完整文件，只有通过校验的压缩包才会发布到共享缓存。

侧车打包和手动发布 workflow 使用原生目标与 Python 运行时锁文件生成独立的 Python 下载缓存键。pip 与 Electron 下载缓存的键仍包含前端依赖锁文件。从 CI 缓存恢复的 Python 压缩包在使用前再次与运行时锁文件核对哈希；缓存只用于加速，不作为可信来源。

## Alternatives considered

**重试整个打包任务。** 重新构建前端和安装依赖会浪费 runner 时间，而且仍可能在同样短的连接窗口内遇到冷缓存下载失败。重试应由压缩包下载器负责。

**所有打包下载共用一个缓存键。** 前端依赖变化仍会丢弃有效的 Python 压缩包。拆分缓存键可以保留压缩包，同时让其他下载随其依赖输入变化。

**不校验就使用缓存文件。** 缓存可能缺失、过期或损坏。运行时锁文件始终决定压缩包的正确内容。

## Consequences

冷缓存 runner 在暂时性故障下会等待更久才失败，但重试次数有上限，永久性错误仍会显现。GitHub 按 ref 限制缓存范围，也可能清理缓存；因此打包流程必须在没有缓存时仍能工作。
