# Agent Note: 统一投研通知中心

Status: implemented

## Problem

投研产品此前由行情、简报和持仓等模块各自直接推送，缺少统一的消息事实、阅读状态和投递审计。用户无法在产品内回看完整历史、筛选消息或判断外部渠道是否送达；浏览器、macOS、Server 酱、企业微信与邮件也没有共享去重、重试和隐私边界。

## Decision

交易核心以 SQLite 通知库作为权威收件箱。生产者提交带版本的领域事件，通知服务完成确定性去重和语义聚合，再按用户偏好生成彼此独立的投递任务。通知、领域事件、投递尝试、阅读/归档状态、渠道偏好和审计记录持久化；设备订阅属于本机能力，不进入可迁移备份。恢复备份时，未结束的旧投递会被冻结且目的地址被清除，避免在新设备上重放历史外发任务。

通知入口采用两层交互：顶部铃铛下拉框仅展示最近未读消息，用于快速直达；完整通知中心使用大模态框承载列表、阅读状态、过滤条件、渠道设置和内嵌详情。打开下拉框不改变阅读状态；选择某条消息才会打开大模态框并标记已读；“查看全部”打开完整列表，但不自动选中或读取任何消息。桌面端使用列表与详情双栏，窄屏仍在同一模态框内切换列表和详情。

登录态运行时使用 Host 进程生成的短期内部令牌访问通知接口，令牌不暴露给渲染器参数、日志或远程运行时。浏览器在具备 VAPID 配置时，于用户进入产品后注册 Service Worker 和 Web Push 订阅；Electron 在 macOS 上通过带租约的领取、确认和失败回写协议展示原生系统通知。Server 酱、企业微信和邮件共用带退避、死信和人工重试能力的投递队列。所有通知接口都需要内部令牌，避免任意本地网页借助宽松 CORS 读取通知历史。

行情预警、行情事件、定时简报、自进化闭环和持仓事实已经接入统一事件入口。持仓计划以及被动同步的 stale/recovered 事件保留已版本化的生产者契约，等待对应领域模块进入公共基线后直接接入，不在通知中心内另造第二套领域状态。

## Alternatives considered

**各业务模块继续直接调用外部渠道。** 不采用，因为每个模块会重复实现去重、重试和偏好，并且产品内没有可审计的统一历史。

**只保留产品内消息，不支持系统渠道。** 不采用，因为风险预警与同步异常需要在用户没有停留于页面时仍能触达；同时所有外部渠道必须以权威收件箱为事实来源，而不是独立消息系统。

**将完整通知中心放在侧边栏。** 不采用，因为侧边栏会与当前工作区导航争夺空间，也难以在窄屏保持列表、详情和设置的完整层级；大模态框更适合一次性查看和处理通知。

**打开铃铛或查看全部时自动标记已读。** 不采用，因为浏览入口不代表用户已经查看具体消息，自动读取会破坏未读状态的可信度。

**把设备订阅和未结束投递完整恢复到新设备。** 不采用，因为设备端点不可移植，恢复后继续投递可能造成重复外发或向旧设备泄露内容。

## Consequences

用户获得一致的未读数、筛选、详情、归档撤销和渠道状态；不同渠道共享同一消息事实和阅读状态，投递失败可审计且可重试。业务事务先完成自身持久化，随后发布通知；通知失败不会回滚简报、持仓或闭环结果。

代价是交易核心承担了新的通知数据库、Worker 和渠道配置，部署方需要配置内部令牌、VAPID 或外部渠道凭据。浏览器通知仍受浏览器权限与用户手势政策约束；macOS 原生通知依赖 Electron 常驻。持仓计划与完整被动同步生产者在其领域实现并入公共基线前，只能消费已定义契约，不能由通知中心自行推导业务事实。
