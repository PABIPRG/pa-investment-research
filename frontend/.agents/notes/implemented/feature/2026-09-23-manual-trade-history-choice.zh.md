# Agent Note: 手工成交补录与当前持仓影响选择

Status: implemented

[English](2026-09-23-manual-trade-history-choice.md) | 中文

## Problem

用户可能先录入或同步当前持仓，再补录较早发生的成交。把补录一律当作新的持仓变更会重复计算数量和成本；一律拒绝较早时间又会让真实历史成交无法记录。浏览器原生 `datetime-local` 输入框还会按浏览器或系统区域设置展示不同的日期顺序和十二小时制。

## Decision

成交表单要求用户明确选择“已计入，只补成交记录”或“未计入，更新当前持仓”，不替用户预设。前者仅在 `holdings.manual_trades` 追加记录，保留 `holdings.default` 与已有快照；后者沿用当前持仓的数量、成本计算和保存时快照。两种路径共用预览、文档版本校验、请求编号幂等、原子写入及操作留痕。较早成交选择更新时，预览明确说明只校正当前持仓，不倒推重算历史快照。没有显式选择的旧客户端仍受较早时间保护，错误提示改为说明可选动作。

成交时间在表单中用固定 `YYYY/MM/DD HH:mm:ss` 本地格式输入，并复用共享日期选择器辅助修改日期；严格验证日历日期与时分秒，再转换为带时区的接口时间。历史列表把带时区的记录转为查看者本地时间，把未标时区的券商时间按原本地钟点展示，并标明手工记录是否改变了当前持仓。

## Alternatives considered

**自动重放较早成交并改写已有快照。** 不采用，因为券商同步、直接编辑和导入形成的持仓快照不是完整成交流水，无法可靠重建每个历史时点的数量和成本。

**始终只补历史或始终更新当前持仓。** 不采用，因为是否已计入当前持仓取决于用户录入顺序，系统无法从成交时间单独判断。

**只设置浏览器输入框的语言。** 不采用，因为原生 `datetime-local` 的可见格式仍可能由浏览器与操作系统决定，无法保证各端一致。

## Consequences

用户可以补录旧成交并明确控制是否调整当前持仓；只补记录不会生成新的持仓快照，仍保留一条可追溯的成交资料变更。代价是每笔手工成交都要多选一次影响方式，且较早成交选择更新只以当前持仓计算，不能把结果解释为历史持仓重算。日期选择器只修改日期，时分秒继续按固定格式输入。
