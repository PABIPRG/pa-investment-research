# Agent Note: 投研智能体单镜像容器运行时

Status: implemented

[English](2026-09-11-single-image-container-runtime.md) | 中文

## Problem

投研 profile 组合一个 Node Host 和三个由 Host 管理的 Python 服务，而服务器部署需要一个可审计的制品身份、一个持久状态所有者、一个调度器所有者和一个受认证保护的网络入口。在启动时安装依赖、发布后端端口或让多个容器共用一个状态根，都会让运行系统偏离已评审制品，并破坏进程或调度器所有权。

## Decision

仓库根目录的 `Dockerfile` 通过独立的前端、Python sidecar 和操作系统运行库阶段构建一个 Linux x86_64 镜像。前端依赖阶段安装由 lockfile 管理的 pnpm 依赖图，并保留既有 workspace 安装生命周期脚本。前端构建编译 Host 与 Web 应用，物化可迁移的 CLI 生产依赖闭包。Python 阶段接收 Node 工具依赖及明确的 Python 输入，不继承前端应用源码或编译产物，组装由校验值锁定的 Python 3.10 运行时、精确版本的 requirements 和三个后端。运行阶段组合这些产物，以非特权 `dsh` 用户运行，不安装依赖或编译源码。

容器工作流只恢复 Linux x64 sidecar 缓存，键包含 Dockerfile、打包与裁剪脚本、Node 依赖清单和配置、Python 锁文件及后端源码。仅修改 UI 源码时键保持不变。可选的 `.investment-sidecar-cache` 目录作为只读构建挂载，不进入运行镜像。缓存元数据必须匹配输入指纹、每个文件的哈希与权限以及完整运行时描述；缺失、过期或损坏时回退到原有 sidecar 构建器。这些校验检测内容损坏，不认证发布者身份；来源由工作流控制。只有正式仓库 master 的 push 或手动运行能保存缓存，且必须先让同一个镜像通过全部冒烟和安全检查。工作流从已验证的镜像 ID 提取 `/opt/investment-python`，不重新构建，也不上传 BuildKit 中间层。每个使用缓存的镜像仍需通过全部既有检查，包括安全扫描。独立的 restore/save Action 避免任务结束时自动上传缓存。运行编号后缀允许替换不可变的损坏条目；恢复前缀始终包含完整输入指纹，有效条目不会重复保存。

`compose.yaml` 只把 Web 端口发布到主机回环地址，要求使用既有 Web 认证及受信 Host/代理边界，声明 `DSH_DEPLOYMENT_SURFACE=cloud-web`，在 `$DSH_HOME` 挂载一个命名卷，并保持根文件系统只读。容器入口只接受该精确的部署值，并把验证后的声明传给 CLI 子进程；直接启动镜像时若缺少该值、值中含前后空白或指定了其他模式，会在获取应用资源前终止启动。管理员密码哈希副本和临时文件只写入 tmpfs。`TZ` 与 `TIMEZONE` 必须指定同一时区，使 Node 与 Python 调度器使用相同墙上时间。

容器入口在已挂载的投研状态目录下认领原子锁目录，并每两秒刷新携带随机 token 的心跳。第二个容器拒绝仍存活的租约；废弃租约十秒后才可替换。CLI 会把外层 token 写入既有应用锁；后继容器只有在内层锁携带已过期外层 token 时才可隔离它，即使其命名空间内 PID 已被复用，未标记或携带当前 token 的所有者仍遵循普通冲突行为。只有 token 所有者可以释放租约，因此旧所有者不能删除后继租约。入口把终止信号转发给 CLI，并在 Compose 宽限期内限制关闭时间。

镜像健康命令通过容器回环地址检查 Web 认证就绪端点，以及 trading-core、market-watch 和 industry-chain 带身份的健康端点。Pull Request CI 构建并启动按 commit 标记的镜像但不推送，断言运行时与网络边界，再导出同一个已验证镜像及归档校验值、镜像 ID 和 BuildKit 元数据。运维步骤由[容器部署与回滚指南](../../../../../docs/maintainers/容器部署与回滚.md)维护。

## Alternatives considered

**在容器启动时安装 Node 或 Python 依赖。** 拒绝，因为 registry 可用性和可变依赖解析会改变启动行为，并让实际运行字节脱离已评审镜像。

**在镜像构建时导出最大模式的 BuildKit 缓存。** 拒绝，因为这会在最终镜像安全扫描之前上传中间层，而扫描运行镜像不能覆盖所有中间层。从已扫描镜像提取并缓存 sidecar，可以保持上传顺序，并把可复用内容限制为已检查的运行时文件。

**让每个 Python 后端运行在独立容器。** 拒绝，因为已交付 Runtime 已经拥有后端生命周期与状态分配；拆分服务会引入本次发布范围外的编排协议和跨容器所有权模型。

**使用 PID 文件或既有 localhost 控制端口作为跨容器锁。** 拒绝，因为容器 PID 与网络命名空间不能提供共享活性。已共享持久文件系统上的心跳能够保留单一调度器所有者，且不需要接管其他命名空间中的进程。

**在 Pull Request CI 推送镜像。** 拒绝，因为 PR 验证不等同于发布授权。工作流只导出内容可验证的镜像归档，后续必须由获得明确授权的交付流程提升。

**根据容器镜像、认证模式或监听地址推断云端 Web。** 拒绝，因为打包形态和网络拓扑不授予产品能力。容器在启动应用进程前验证 Host 所消费的同一份显式部署声明。

## Verification

容器契约测试固定独立的 Dockerfile 阶段、非 root 运行时、Compose 端口与卷边界、精确的云端 Web 声明及子进程继承、失败关闭的启动配置、排他租约行为，以及扫描先于缓存保存的顺序。缓存测试覆盖仅修改 UI 时复用、后端/锁文件/工具链变化时失效、文件缺失或增加、哈希或权限变化、元数据损坏及符号链接。Sidecar 测试固定 Linux 描述符和既有打包隐私规则。Pull Request CI 提供真实 Linux 镜像构建、符号链接闭包、非 root/只读断言、Compose 聚合健康、优雅停止和按 commit 导出的证据。PAB-20 负责容器交付能力；PAB-21 负责在真实容器环境中完成反向代理浏览器路径和完整业务 UAT。

## Consequences

一个镜像和一个卷为运维提供较小的部署与回滚单元，同时保留 Host 的既有后端权限。镜像会较大，因为它包含三个 Python 依赖集合和完整 Node 生产闭包。精确 Python 版本没有固定每个 wheel 的 hash，Debian 包也在构建时解析，因此不同构建不承诺逐字节可复现；导出镜像的 digest 与校验值标识 CI 实际验证的字节。租约假设存储支持原子目录创建、一致的修改时间和持久写入，因此不支持不满足这些语义的网络文件系统。十秒废弃租约间隔以稍慢的崩溃重启换取不重叠的调度器所有权。镜像仓库发布和多主机编排仍是需要单独授权的交付决策。

新输入的首次运行、缓存被淘汰或没有匹配 master 缓存的 PR，都会完整构建 sidecar。缓存下载、哈希校验和复制仍有耗时。前端依赖安装仍与前端源码树关联；本阶段不引入跨运行的前端构建缓存，也不减少平台覆盖。实际提速需要比较一次冷运行和随后使用同一份 master sidecar 缓存的纯 UI PR。Docker 构建和缓存命中耗时需要 Linux Docker runner 验证，不能从契约测试推断。
