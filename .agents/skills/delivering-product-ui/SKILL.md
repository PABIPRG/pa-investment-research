# 交付产品级 UI

## 核心原则

把每次可见改动都视为产品设计与工程实现的共同任务。范围可以很小，但不能把视觉层级、完整状态、无障碍或真实验收降级为“之后再补”。

开始前必须完整读取仓库根目录 [`DESIGN.md`](../../../DESIGN.md)、[`frontend/docs/web-styling.zh.md`](../../../frontend/docs/web-styling.zh.md)，以及从仓库根目录到目标文件目录路径上所有适用的 `AGENTS.md`。

## 工作流

实现任务执行以下全部步骤。只读审查任务使用第 1、2 步建立检查基线，再核对被审查产物是否满足第 3、4 步；只报告带证据的缺口、验证债务和结论，不自行实现或把缺少证据描述为通过。

### 1. 建立体验契约

从请求与现有产品中明确：目标用户、主任务、最重要信息、主要操作、成功结果和受支持视口。输出紧凑的体验契约与状态矩阵；对加载、刷新、空数据、筛选无结果、部分成功、过期、错误、无权限、禁用、成功、确认/撤销逐项标记“适用”或说明“不适用”的依据。若选择会显著改变产品行为且无法从上下文判断，先询问用户；否则记录最小假设并继续。

已批准界面图需要拆成布局、层级、组件、文案和交互意图，同时补齐图片没有展示的状态。图片不得覆盖真实数据语义、权限、无障碍或既有工程契约；关键冲突必须在实现前列出并取得用户选择。若批准图代表新的长期方向，把相应 `DESIGN.md`、共享 token 或公共组件更新纳入同一变更。

### 2. 审计后再设计

检查相似页面、`ui-primitives`、`ui-theme`、投研 UI 包、状态所有者和现有测试。用简表记录每项用户动作对应的现有入口、状态所有者、缺口、证据，以及复用、组合、扩展或新建的唯一决策；无法证明缺口时不得创建平行组件、token、数据状态或交互模式。

实现前形成紧凑的设计判断：页面层级、数据与操作优先级、状态矩阵、响应式变化和与现状的差异。局部小改可直接在对话中说明；复杂或有多个关键取舍时先让用户确认。

### 3. 实现完整行为

- 功能组件使用 CSS Modules、现有组件和 `--dsw-alias-*` 语义 token；主题所有方按 `web-styling.zh.md` 在所属全局样式表中定义共享 token。
- 保持中文产品文案、可见标签、键盘路径和清晰焦点。
- 按已记录的状态矩阵实现加载、刷新、空数据、筛选无结果、部分成功、过期、错误、无权限、禁用、成功和确认/撤销。
- 使用语义 HTML，验证对比度、可访问名称、live region、键盘顺序和减少动态效果。
- 对 AI 与投研内容区分事实、推断和行动；不补造数据，不把 `null` 显示为 `0`。
- 先实现最小完整体验，不以装饰、卡片数量或新组件数量衡量完成度。

### 4. 验证真实产品

先运行目标组件测试和主题检查；可见组装界面变化按仓库规则运行 GUI 与 Web 测试。然后在真实运行的产品中完成与风险相称的验收：

- 检查 1440px、1024px，以及适用时的 768px 与 390px；若产品不支持某档宽度，记录最小宽度和不丢失数据或操作的降级结果；
- 检查浅色/深色、长中文、大数值、缩放和溢出；
- 操作键盘路径，以及加载、空态、错误和危险操作；
- 有参考图时逐项记录差异，不以“看起来差不多”代替对照。

自动测试结果不等于真实产品证据。没有真实渲染证据时，不得声称 UI 已完成；验收记录至少包含运行环境、视口、主题、数据状态、操作结果、截图或录屏路径、限制和未验证项。

## 快速判定

| 情况 | 必须补充的判断 |
|---|---|
| “先能用”“今天演示” | 缩小范围，不降低已交付范围的状态与验收门槛 |
| 已批准截图 | 复用映射、未展示状态、响应式和规范冲突 |
| 局部控件 | 用户任务、默认值、清除/恢复路径和窄宽行为 |
| 自动测试通过 | 继续检查真实渲染、层级、对齐和交互反馈 |

## 常见失败

- 只读组件代码，不读 `DESIGN.md`。
- 因需求小而直接套一个传统控件，没有确认用户目标。
- 复制截图的静态外观，却漏掉 loading、empty、error、focus 和窄屏。
- 新写字面颜色、局部 token 或近似组件，造成设计漂移。
- 用 jsdom、快照或构建成功代替真实产品验收。
