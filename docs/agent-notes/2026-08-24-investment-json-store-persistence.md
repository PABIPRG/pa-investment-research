# Agent Note: 投研 JSON 状态的并发与原子提交

Status: implemented

## Problem

`dsh-trading-core` 与 `market-watch` 的 `JsonStore` 原先把锁保存在实例内，但接口、调度器和分析模块会为同一个数据目录创建多个实例。不同实例可以同时执行同一文件的读改写，并共同使用固定的 `<collection>.tmp`，因此线程并发时可能丢失已提交字段、互相替换临时文件或产生写入异常。读取又把 JSON 解析失败和文件系统错误当作空对象，持久化损坏会伪装成“用户没有持仓或自选”。此外，持仓整体替换接口用列表真值判断是否写入，显式提交 `[]` 只返回 `saved: 0`，并不会删除旧持仓。

## Decision

两套 `JsonStore` 都以解析后的绝对 JSON 文件路径为键，在模块级注册同进程共享锁。每个 `get`、`set`、`update`、`delete` 和 `all` 操作继续在一次锁持有期间完成完整读取或读改写，因此同一进程内指向同一文件的不同实例按提交顺序串行执行。

每次写入在目标目录通过 `tempfile.mkstemp` 创建唯一临时文件。内容写入后刷新 Python 缓冲区并执行 `fsync`，再用 `os.replace` 原子替换目标；无论写入或替换在哪一步失败，尚存的临时文件都会被删除，原目标文件不会被主动改写。

文件不存在仍表示空状态。文件存在但不是有效 UTF-8、不是有效 JSON 或顶层不是 JSON 对象时，读取抛出 `JsonStoreCorruptionError`，错误包含文件路径，原始字节保持不变。普通文件系统错误继续按原异常向上传播。持仓保存仅把 `None` 解释为“未提供”，显式空列表会写入并清空已保存持仓。

该锁只承诺同一 Python 进程内的线程安全。当前两个 FastAPI 服务各自以单进程运行，符合现有部署方式；如果未来启用多个 worker，必须先引入跨进程文件锁或事务型数据库。

## Alternatives considered

**继续使用固定临时文件，只扩大实例锁范围。** 固定临时文件在不同实例或未来新增写入路径之间仍会互相覆盖，也无法独立清理失败写入，因此没有采用。

**损坏时自动重命名文件并返回空对象。** 自动恢复会让调用方继续基于丢失的数据执行风险分析，并且未经用户确认改变取证现场，因此没有采用。明确失败既保留原文件，也迫使诊断发生在首次读取处。

**本次直接迁移到 SQLite。** SQLite 可以同时解决跨进程事务和查询扩展问题，但会引入数据迁移、schema 版本与打包依赖，超出修复现有同进程并发缺陷所需范围，因此暂不采用。

## Consequences

同进程并发写不再丢失其他实例刚提交的字段，替换失败不会留下共享临时文件，损坏状态也不会被误报为空数据。调用方现在会看到此前被吞掉的解析或编码错误，这是有意的失败语义变化；用户需要根据错误路径修复或恢复原文件。模块级锁表会在进程生命周期内保留访问过的规范化文件路径，现有固定 collection 集合使其保持有界。并发写、损坏保留、替换失败清理和空列表清空均由两个后端的 focused Python 测试覆盖。
