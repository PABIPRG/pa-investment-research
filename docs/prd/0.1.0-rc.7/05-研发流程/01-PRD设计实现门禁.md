# PRD → 设计 → 实现门禁

## 1. 强制顺序

```text
问题确认
  ↓
PRD：定义用户价值、范围、行为与验收
  ↓ 产品评审通过
设计文档：定义状态、数据、接口、组件、迁移与测试方案
  ↓ 设计评审通过
实现计划：拆解任务、依赖、顺序和验证
  ↓ 计划确认
编码与测试
  ↓
产品验收与发布
```

任何阶段发现前置决策缺失，都退回上一阶段补齐，不能在代码中临时拍板。

## 2. Gate 1：PRD 评审

PRD 必须具备：

- 明确用户、问题、范围和不做什么。
- 可观察的业务行为与异常行为。
- 稳定需求编号、优先级和验收条件。
- 与其他模块的输入、输出和状态流转。
- 隐私、安全、失败和降级边界。

评审输出：`批准 / 有条件批准 / 退回`。有条件批准必须列出关闭条件和负责人。

## 3. Gate 2：设计评审

设计文档必须：

- 引用具体需求编号并逐项说明如何满足。
- 给出状态模型、对象归属和数据一致性策略。
- 明确前端、Host、三套后端和模型工具边界。
- 覆盖空、慢、错、并发、重试、幂等和迁移。
- 给出主题、可访问性、可观测性和安全方案。
- 列出取舍、未决问题与回滚方式。

没有 PRD 编号的设计内容不能进入实现；应先提交需求变更。

## 4. Gate 3：实现计划

实现计划必须：

- 按可独立验证的垂直切片拆分，不按“先写完前端再说”拆分。
- 每个任务引用需求和设计章节。
- 标明依赖、影响文件、测试层级和完成证据。
- 明确旧数据、现有脏工作区和兼容性处理。
- 区分必须串行的合同变更与可并行的页面工作。

## 5. Gate 4：实现与评审

- 代码评审逐项核对追踪矩阵。
- 新行为必须有对应测试；修复必须先有失败复现。
- 页面不得自行扩展后端任意路径或复制业务规则。
- 共享组件、会话、工作区和上下文的变更必须跑全局专项回归。
- 未经用户明确要求，不自动提交、推送或创建 PR。

## 6. Gate 5：验收与发布

- 执行[产品验收标准](../04-验收发布/02-产品验收标准.md)。
- 执行[全量回归测试矩阵](../04-验收发布/03-回归测试矩阵.md)。
- 更新[需求追踪矩阵](../04-验收发布/04-需求追踪矩阵.md)。
- 记录已知限制、豁免、回滚和观察指标。

## 7. 文档位置

| 文档 | 建议位置 |
|---|---|
| 版本 PRD | `docs/prd/<version>/` |
| 设计文档 | `docs/design/<version>/` |
| 实现计划 | `docs/implementation/<version>/` |
| 产品验收报告 | `docs/qa/<version>/` |
| 重大决策记录 | 对应设计目录的 `decisions/` |

## 8. 完成定义

“代码能跑”不等于完成。只有需求、设计、实现、自动测试、真实浏览器回归和产品验收全部可追溯，任务才算完成。
