# 变更与决策管理

## 1. 何时必须变更 PRD

出现以下任一情况，先停下设计或实现并提交 PRD 变更：

- 新增、删除或改变用户可见行为。
- 改变 1+7 导航、报告入口或关键业务流。
- 改变策略、影子、自进化等状态或确认语义。
- 改变数据归属、隐私、安全或真实交易边界。
- P0/P1 需求延期、降级或豁免。
- 设计发现验收标准不可实现或相互冲突。

纯内部重构且不改变任何产品契约时，不需要改 PRD，但仍需设计或实现说明。

## 2. 变更记录格式

每个变更至少包含：

| 字段 | 内容 |
|---|---|
| 变更编号 | 例如 `PRD-CR-001` |
| 发起原因 | 用户问题、数据、缺陷或外部约束 |
| 影响需求 | 具体需求编号 |
| 旧行为 / 新行为 | 可观察差异 |
| 范围影响 | 模块、数据、报告、会话、测试和发布 |
| 替代方案 | 至少说明为何不选主要替代方案 |
| 验收变化 | 新增、删除或调整的测试 |
| 决策与日期 | 批准、拒绝或延期 |

## 3. 决策层级

- 产品行为与范围：PRD 变更。
- 技术边界与选型：设计决策记录。
- 任务顺序与提交拆分：实现计划更新。
- 临时发布豁免：发布记录，且必须引用 PRD/设计风险。

不能用设计决策记录替代产品需求，也不能用实现计划发明新产品行为。

## 4. 评审与冲突

- 产品、设计、前端、后端和测试对受影响部分共同评审。
- 冲突时先回到用户目标与产品原则，不以已写代码量决定。
- 未决问题不得用模糊措辞隐藏；标记负责人、截止时间和阻断级别。
- 被拒绝方案保留简短原因，防止后续重复争论。

## 5. 紧急缺陷

安全、数据损坏或发布阻断缺陷可以先做最小风险控制，但必须：

1. 记录临时行为和影响范围。
2. 不扩大为未经评审的新功能。
3. 修复后在下一工作日内补齐 PRD 或设计变更。
4. 完成专项回归和回滚验证。

## 6. 文档状态

文档使用：草案、评审中、已批准、已废弃。

已批准内容的修改必须带变更编号；禁止无痕改写历史决策。
