# 0.2.0-alpha.2 云端部署指南

本文面向准备把投研智能体 `0.2.0-alpha.2` 部署到公网的维护者，给出从主机准备到上线验收的最短路径。容器的完整运行、安全和回滚契约以[容器部署与回滚](maintainers/容器部署与回滚.md)为准，持久数据布局、迁移和一致性要求以[单实例数据目录与迁移](maintainers/单实例数据目录与迁移.md)为准；本文不替代这两份维护者文档。

## 是否需要虚拟机

推荐使用一台 Linux x86_64 云主机，在主机上安装 Docker Engine 和 Docker Compose v2。Node Host、Web 前端和三个 Python 后端已经打包在同一个 `investment` 容器内，不需要为每个服务各准备一台虚拟机，也不应把它们拆成可独立扩缩的多实例服务。

推荐拓扑如下：

```text
浏览器
  │ HTTPS 443
  ▼
域名与云防火墙
  │
  ▼
同一台 Linux 云主机上的 TLS 反向代理
  │ HTTP 127.0.0.1:3080
  ▼
Docker Compose：单个 investment 容器
  ├─ Node Host 与 Web 前端
  ├─ trading-core、market-watch、industry-chain（仅容器回环）
  └─ 唯一持久卷 dsh-data（挂载为 /var/lib/dsh）
```

加载 CI 已构建镜像时，可以从 `2 vCPU、4 GiB 内存、30 GiB SSD` 起步；若要在云主机本地构建镜像，建议至少 `4 vCPU、8 GiB 内存、40 GiB 可用磁盘`。这些是单用户部署的起步值，不是容量保证；上线后应根据镜像占用、卷增长、构建峰值和实际负载扩容。

## 上线前提

- 云主机架构为 Linux x86_64，已安装可用的 Docker Engine、`docker buildx` 和 Docker Compose v2，并为维护账号配置了受控的 Docker 权限。
- 一个专用域名的 A／AAAA 记录已经指向云主机公网地址，DNS 生效；反向代理能够为该域名申请或加载有效 TLS 证书。
- 云安全组和主机防火墙只向公网开放业务所需的 `80/tcp`、`443/tcp`，以及限定来源的维护入口；不要向公网开放 `3080/tcp`。仓库的 `compose.yaml` 只把应用端口发布到 `127.0.0.1`。
- 反向代理部署在同一主机，转发到 `http://127.0.0.1:3080`，保留原始 `Host`，并正确设置 `X-Forwarded-For` 和 `X-Forwarded-Proto`。若使用容器化反向代理，必须先重新设计网络和精确代理来源地址，不能为了连通而把应用端口暴露到公网。
- 已确定卷备份位置、保留周期、恢复责任人和恢复演练方式；备份介质不能与唯一业务卷共用同一故障域。

## 取得固定身份的镜像

当前仓库的 Pull Request CI 会构建并验证 Linux x86_64 镜像，但不会把镜像推送到 registry。不要假设存在官方公共镜像或可直接拉取的 `0.2.0-alpha.2` 标签；可从一次成功的 PR 工作流下载 commit 级产物，或在与目标源码一致的 checkout 中本地构建。

### 方案一：使用 PR CI 产物

在 GitHub Actions 的 `Investment container image` 工作流中下载 `investment-container-<完整 commit SHA>` 产物。产物保留 14 天，包含镜像归档、SHA-256、镜像 ID 和 BuildKit 元数据；把其中的文件复制到云主机后执行：

```bash
sha256sum --check investment-container.tar.gz.sha256
gzip --decompress --stdout investment-container.tar.gz | docker load
docker image inspect pa-investment-research:<commit-sha>
```

把 `<commit-sha>` 替换为产物对应的完整提交 SHA。校验失败、镜像标签与目标提交不一致或工作流未成功时不得继续部署。

### 方案二：在目标源码上本地构建

从仓库根目录执行以下命令；`Dockerfile` 只接受 `linux/amd64` 目标，构建会安装前端依赖并生成三个 Python sidecar，因此需要网络、时间和足够磁盘空间。

```bash
commit_sha="$(git rev-parse HEAD)"
docker buildx build \
  --platform linux/amd64 \
  --load \
  --tag "pa-investment-research:${commit_sha}" \
  --build-arg "VCS_REF=${commit_sha}" \
  .
docker image inspect "pa-investment-research:${commit_sha}"
```

无论采用哪条路径，`DSH_IMAGE` 都必须固定到已验证的不可变 registry digest，或至少固定到完整 commit SHA 标签。禁止使用 `latest`、浮动版本标签或未经验证的本地同名镜像。

## 首次部署

以下命令都在包含当前 `Dockerfile`、`compose.yaml` 和 `.env.container.example` 的仓库根目录执行。

### 1. 生成密码哈希 secret

管理员密码至少 12 个字符。不要把明文密码写进 Compose、环境变量、shell 历史或仓库；使用目标镜像从标准输入生成版本化 scrypt 哈希，并把文件所有者设为容器用户 `10001:10001`、权限设为 `0400`。

```bash
sudo install -d -o root -g root -m 0755 /srv/pa-investment-research
hash_file="$(mktemp)"
chmod 0600 "$hash_file"
read -r -s DSH_ADMIN_PASSWORD
printf '%s\n' "$DSH_ADMIN_PASSWORD" \
  | docker run --rm -i --entrypoint node pa-investment-research:<commit-sha> \
      /opt/dsh/lib/bin.js web-password-hash \
  > "$hash_file"
unset DSH_ADMIN_PASSWORD
sudo install -o 10001 -g 10001 -m 0400 \
  "$hash_file" /srv/pa-investment-research/web-admin-password.hash
rm -f "$hash_file"
```

若本地构建时使用了 shell 变量标签，就把命令中的 `pa-investment-research:<commit-sha>` 替换为实际完整 SHA 标签。文件型 Compose secret 保留宿主文件的 owner 和 mode，不能通过放宽为 group/world-readable 来绕过读取失败。

### 2. 配置环境

复制模板并限制权限：

```bash
cp .env.container.example .env.container
chmod 0600 .env.container
```

编辑 `.env.container`，至少逐项确认：

```dotenv
DSH_IMAGE=pa-investment-research:<commit-sha>
PORT=3080
TZ=Asia/Shanghai
TIMEZONE=Asia/Shanghai
DSH_WEB_ADMIN_USERNAME=admin
DSH_WEB_ADMIN_PASSWORD_HASH_FILE=/srv/pa-investment-research/web-admin-password.hash
DSH_WEB_TRUSTED_HOSTS=research.example.com
DSH_WEB_TRUSTED_PROXIES=<反向代理连接容器时的精确源 IP>
```

`DSH_WEB_TRUSTED_HOSTS` 填浏览器实际访问的 authority；使用非默认 HTTPS 端口时要包含端口。`DSH_WEB_TRUSTED_PROXIES` 填反向代理连接容器时的精确源 IP，而不是浏览器 IP、网段、`0.0.0.0` 或未经确认的 Docker 默认地址；网络重建后应重新核对。`TZ` 和 `TIMEZONE` 必须相同且为有效 IANA 时区。

先让 Compose 展开并检查配置；输出会包含环境配置，保存或分享时按敏感信息处理：

```bash
docker compose --env-file .env.container config
```

### 3. 启动唯一实例

```bash
docker compose --env-file .env.container up -d --no-build
docker compose --env-file .env.container ps
docker compose --env-file .env.container logs --tail 200 investment
```

不要使用 `--scale`。一个 Compose 项目只能运行一个 `investment` 容器，一个 `dsh-data` 卷也只能由一个调度实例挂载；禁止让新旧容器或两台主机同时共享同一个卷。

### 4. 配置公网 HTTPS

让反向代理为 `research.example.com` 终止 TLS，并转发到 `http://127.0.0.1:3080`。外部请求必须保留真实 authority，浏览器只能通过 HTTPS 登录；`compose.yaml` 已固定 `DSH_WEB_AUTH=required` 和 `DSH_WEB_INSECURE_COOKIES=0`，不要为排障关闭认证或安全 Cookie。

## 持久卷与备份

`compose.yaml` 只声明一个命名卷 `dsh-data`，并将其挂载为容器内的 `/var/lib/dsh`，也就是唯一 `$DSH_HOME`。设置、profile、会话、附件、storage、投研备份和三个 Python 后端状态都位于这棵目录中；不要把仓库 `backend/*/data` 或其中某个子目录单独当作完整备份。

```bash
docker volume inspect pa-investment-research_dsh-data
```

备份前停止 `investment` 和所有写入任务，对整个卷制作离线文件系统副本或云盘快照，记录镜像 digest／完整 commit SHA、Compose 配置和备份身份，然后再启动原实例。恢复也必须在所有进程停止后恢复整卷，并按[单实例数据目录与迁移](maintainers/单实例数据目录与迁移.md)核对数据布局和一致性；运行中的 SQLite 文件不能直接逐文件复制。

永远不要执行会删除卷的 `docker compose down -v`，也不要删除 `.container-instance.lock` 或 `application.lock` 来绕过单实例保护。外置 `.pabackup` 目录若不在 `$DSH_HOME` 内，必须另行挂载、备份和恢复验证。

## 健康检查与验收

Compose 健康检查会等待 Web 认证配置可用，以及 `trading-core`、`market-watch`、`industry-chain` 三个后端全部就绪。状态为 `starting` 或 `unhealthy` 都不能视为部署成功。

```bash
docker compose --env-file .env.container ps
docker compose --env-file .env.container logs --tail 200 investment
curl --fail --silent --show-error \
  -H 'Host: research.example.com' \
  http://127.0.0.1:3080/healthz
curl --fail --silent --show-error https://research.example.com/healthz
```

本机诊断请求的 `Host` 必须与 `DSH_WEB_TRUSTED_HOSTS` 一致；生产验收应直接请求真实 HTTPS URL，不要覆盖 `Host`。聚合健康检查通过后，还要在浏览器中通过 HTTPS 登录，并实际验证智能分析、实时盯盘和产业链三项后端能力。

## 升级与回滚

升级前记录当前镜像 ID／digest、完整 commit SHA 和 Compose 配置，停止容器并按前述要求备份整个卷。载入新的 CI 归档或取得新的不可变 registry digest 后，更新 `.env.container` 的 `DSH_IMAGE`，只重建一个实例：

```bash
docker compose --env-file .env.container up -d --no-build --force-recreate investment
docker compose --env-file .env.container ps
docker compose --env-file .env.container logs --tail 200 investment
```

等待聚合健康检查通过，再重复 HTTPS 登录和三后端业务验收。完整步骤和故障语义见[容器部署与回滚](maintainers/容器部署与回滚.md)。

如果新版本启动失败且确认没有写入或迁移持久格式，可把 `DSH_IMAGE` 恢复为已记录的旧 digest／完整 SHA 标签并重建。若新版本已经写入或迁移数据，不能只回退镜像；必须先停止全部进程，恢复与旧镜像匹配的整卷备份，再启动旧镜像。回滚期间严禁让新旧容器同时挂载同一卷。

## 上线验收清单

- [ ] 云主机为 Linux x86_64，Docker Engine、Buildx 和 Compose v2 可用，容量满足当前镜像、卷和备份需求。
- [ ] 部署镜像来自成功的 commit 级 CI 产物或目标源码本地构建，SHA-256、镜像标签和 revision 已核对；未使用 `latest`。
- [ ] 域名解析正确，TLS 证书有效，公网仅开放 `80/443` 和受限维护入口，`3080` 只监听 `127.0.0.1`。
- [ ] 管理员密码哈希通过目标镜像生成，宿主文件归 `10001:10001` 所有、权限为 `0400`，明文密码未写入配置或仓库。
- [ ] `DSH_WEB_TRUSTED_HOSTS` 是真实 authority，`DSH_WEB_TRUSTED_PROXIES` 是反向代理的精确源 IP，反向代理正确传递 Host 和转发头。
- [ ] Compose 只运行一个 `investment` 实例，只有一个完整 `dsh-data` 持久卷，没有第二实例或第二主机共享该卷。
- [ ] `docker compose ps` 显示容器为 `healthy`，本机带正确 Host 的 `/healthz` 与公网 HTTPS `/healthz` 都成功。
- [ ] 浏览器通过 HTTPS 登录成功，智能分析、实时盯盘和产业链三项后端能力均已实际验收。
- [ ] 已完成整个 `$DSH_HOME` 的离线备份，记录了镜像身份、Compose 配置、备份身份、恢复负责人和回滚触发条件。
- [ ] 已确认升级与回滚流程不使用 `latest`、不并行挂载共享卷，也不会通过删锁或 `down -v` 绕过保护。
