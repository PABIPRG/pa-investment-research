# 0.2.0-alpha.2 云端部署指南

本文面向准备把投研智能体 `0.2.0-alpha.2` 部署到公网的维护者，给出单机落地路径与上线检查。容器内部的运行契约、故障定位和精确回滚规则以[容器部署与回滚](maintainers/容器部署与回滚.md)为准；数据布局、迁移和一致性恢复以[单实例数据目录与迁移](maintainers/单实例数据目录与迁移.md)为准。本文不会替代这两份维护者文档。

## 是否需要虚拟机

推荐准备一台公网 Linux x86_64 云主机，在主机上安装 Docker Engine、Docker Compose v2 和一个终止 TLS 的反向代理。不需要为 Web、Node Host 或三个 Python 后端分别创建虚拟机：仓库的 `Dockerfile` 已把这些组件打进同一个 `linux/amd64` 镜像，`compose.yaml` 也只定义一个 `investment` 服务。

`0.2.0-alpha.2` 的容器交付契约是单主机、单实例。不要使用 `docker compose up --scale`，不要让多个容器、Compose 项目或主机同时挂载同一个数据卷。高可用、多副本和共享存储不在这个版本的支持范围内。

### 建议规格

| 场景 | vCPU | 内存 | 系统盘 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 小规模运行起步 | 2 | 4 GiB | 30 GiB SSD | 适合单用户试运行；需要监控内存、镜像和数据增长 |
| 推荐公网运行 | 4 | 8 GiB | 50 GiB SSD 或更大 | 为三个 Python 后端、研究任务和升级留出余量 |
| 同机从源码构建 | 4 或更多 | 8 GiB 或更多 | 额外预留构建缓存空间 | 镜像构建会安装前端依赖并生成 Linux x64 Python sidecar，生产机资源不足时应在 CI 或独立构建机完成 |

磁盘容量还应覆盖 `dsh-data`、至少一份离线备份和两个镜像版本。实际需求取决于会话、附件、报告和备份增长量；上线后应按磁盘、内存和任务峰值监控结果扩容。

## 推荐拓扑

```text
浏览器
  │ HTTPS 443
  ▼
域名 ──► 云防火墙／安全组 ──► 同一台 Linux x86_64 云主机
                                      │
                                      ├─ TLS 反向代理
                                      │      │ 127.0.0.1:3080
                                      │      ▼
                                      └─ Docker Compose
                                             └─ investment（唯一实例）
                                                    └─ dsh-data（唯一持久卷）
```

推荐在主机上直接运行 Caddy、Nginx 或同类反向代理，由它连接 Compose 发布的 `127.0.0.1:3080`。这样无需改变仓库现有 Compose 网络，应用端口也不会暴露到公网。反向代理必须保留浏览器的 `Host`，正确设置 `X-Forwarded-Proto: https`，并支持 WebSocket 升级。

## 上线前提

### 主机和软件

- 使用支持 Docker 的 Linux x86_64 主机；当前 `Dockerfile` 只接受 `linux/amd64` 构建目标。
- 安装 Docker Engine 和带 `docker compose` 子命令的 Compose v2，并确保维护者能够管理 Docker、读取待部署镜像以及备份 Docker volume。
- 校准系统时间并选择有效的 IANA 时区；`.env.container` 中 `TZ` 与 `TIMEZONE` 必须完全相同。
- 若在本机从源码构建，构建阶段需要访问基础镜像、pnpm 依赖和 Python sidecar 依赖来源；容器运行阶段不会执行源码编译或下载依赖。

### 域名、TLS 和防火墙

- 为服务准备独立域名，例如 `research.example.com`，让 DNS A 记录指向云主机公网 IPv4；只有在主机和防火墙完整支持 IPv6 时才添加 AAAA 记录。
- 在反向代理上配置受信 CA 签发的证书、自动续期和 HTTP 到 HTTPS 跳转。浏览器业务访问必须走 HTTPS，否则安全 Cookie 无法按生产契约工作。
- 公网只开放 TCP 443；确需证书签发或跳转时开放 TCP 80。SSH 仅允许管理网段或 VPN，禁止公网开放 Compose 的 `3080` 端口以及 Docker daemon 端口。
- 允许主机访问业务所需的 DNS、NTP、软件源和模型／行情等外部服务；不要为方便而开放不相关的入站端口。

## 准备镜像和部署文件

部署时必须同时取得同一完整 commit SHA 对应的仓库文件、镜像和构建证据。生产配置禁止使用 `latest`，也不要仅用可移动分支名标识镜像。

### 路径 A：使用 Pull Request CI 归档

当前仓库没有可直接拉取的官方 registry 发布。Pull Request 的 `Investment container image` 工作流会构建但不推送镜像，并上传名为 `investment-container-<commit SHA>` 的归档，保留 14 天。下载归档后，把四个文件放到同一目录，先核对 SHA-256，再载入镜像：

```bash
sha256sum --check investment-container.tar.gz.sha256
gzip --decompress --stdout investment-container.tar.gz | docker load
cat investment-container.image-id
```

归档还包含 `investment-container-build.json`。记录归档校验值、镜像 ID、完整 commit SHA 和对应 CI 运行链接，并在服务器上 checkout 同一 commit，以取得匹配的 `compose.yaml` 与 `.env.container.example`。CI 归档是短期交付物，不应当作长期镜像仓库或唯一备份。

### 路径 B：从当前仓库本地构建

在已经 checkout 到发布批准 commit 的仓库根目录运行：

```bash
RELEASE_SHA=$(git rev-parse HEAD)
docker buildx build \
  --platform linux/amd64 \
  --load \
  --tag "pa-investment-research:${RELEASE_SHA}" \
  --build-arg "VCS_REF=${RELEASE_SHA}" \
  .
docker image inspect \
  --format '{{.Id}} {{index .Config.Labels "org.opencontainers.image.revision"}}' \
  "pa-investment-research:${RELEASE_SHA}"
```

检查输出中的 revision 与 `RELEASE_SHA` 完全一致。若以后由维护者自行推送到私有 registry，应在 `DSH_IMAGE` 中使用不可变 digest；这不表示本仓库当前已经提供 registry 发布。

## 首次部署

以下命令都在对应 release commit 的仓库根目录执行。

### 1. 创建环境文件

```bash
cp .env.container.example .env.container
chmod 0600 .env.container
```

编辑 `.env.container`，至少核对以下值：

```dotenv
DSH_IMAGE=pa-investment-research:<commit-sha>
PORT=3080
TZ=Asia/Shanghai
TIMEZONE=Asia/Shanghai
DSH_WEB_ADMIN_USERNAME=admin
DSH_WEB_ADMIN_PASSWORD_HASH_FILE=/srv/pa-investment-research/web-admin-password.hash
DSH_WEB_TRUSTED_HOSTS=research.example.com
DSH_WEB_TRUSTED_PROXIES=127.0.0.1
```

`DSH_WEB_TRUSTED_HOSTS` 填浏览器实际使用的 authority，不带协议或路径；HTTPS 使用非默认端口时必须包含端口。多个值用英文逗号分隔。

`DSH_WEB_TRUSTED_PROXIES` 只填写反向代理连接应用时的精确源 IP。主机原生代理连接 `127.0.0.1:3080` 时通常是 `127.0.0.1`；若网络方案不同，应从实际 socket 对端核实后填写。不要填网段、`0.0.0.0` 或未经确认的 Docker 网关地址，也不要信任来自其他来源的转发头。

### 2. 生成密码哈希 secret

先确保 `DSH_IMAGE` 指向的镜像已经载入本机。不要把管理员明文密码写进 shell 参数、环境文件或 Compose 文件；以下流程从标准输入读取至少 12 个字符的密码，只保存版本化 scrypt 哈希：

```bash
sudo install -d -o root -g root -m 0755 /srv/pa-investment-research
hash_file=$(mktemp)
chmod 0600 "$hash_file"
read -r -s DSH_ADMIN_PASSWORD
printf '%s\n' "$DSH_ADMIN_PASSWORD" \
  | docker run --rm -i --entrypoint node "pa-investment-research:<commit-sha>" \
      /opt/dsh/lib/bin.js web-password-hash \
  > "$hash_file"
unset DSH_ADMIN_PASSWORD
sudo install -o 10001 -g 10001 -m 0400 \
  "$hash_file" /srv/pa-investment-research/web-admin-password.hash
rm -f "$hash_file"
```

把示例中的镜像标签替换为 `.env.container` 使用的精确镜像。Compose 文件型 secret 保留宿主文件的 owner 和 mode，因此哈希文件必须由容器 UID/GID `10001:10001` 所有并保持 `0400`，不能通过放宽 group/world 权限绕过读取错误。

### 3. 启动唯一实例

先校验 Compose 展开结果，再启动已经载入的精确镜像：

```bash
docker compose --env-file .env.container config --quiet
docker compose --env-file .env.container up -d --no-build
docker compose --env-file .env.container ps
docker compose --env-file .env.container logs --tail 200 investment
```

不要添加 `--scale`，也不要同时启动另一套指向相同 `dsh-data` 的 Compose 项目。若启动失败，按[容器部署与回滚](maintainers/容器部署与回滚.md#故障定位)检查配置和日志，不要删除实例锁或放宽鉴权边界。

### 4. 配置反向代理并检查健康

让反向代理把 `https://research.example.com` 转发到 `http://127.0.0.1:3080`，保留原始 Host，设置 HTTPS 转发协议并启用 WebSocket。确认公网无法直接连接 `3080` 后，分别执行本机和公网健康检查：

```bash
curl --fail --silent --show-error \
  -H 'Host: research.example.com' \
  http://127.0.0.1:3080/healthz
curl --fail --silent --show-error \
  https://research.example.com/healthz
```

本机检查的 `Host` 必须与 `DSH_WEB_TRUSTED_HOSTS` 中的实际 authority 一致。生产验收使用真实 HTTPS URL，不应通过覆盖 `Host` 绕过代理或 TLS。

容器只有在 Web 鉴权配置可用且 `trading-core`、`market-watch`、`industry-chain` 全部就绪后才会变为 `healthy`。`starting` 或 `unhealthy` 都不能视为部署成功。

## 持久数据和备份

`compose.yaml` 只定义一个持久卷 `dsh-data`，挂载为容器内的 `DSH_HOME=/var/lib/dsh`。它同时保存 Host 设置、profile、会话、附件、业务存储、备份和三个 Python 后端状态；不要把 `backend/*/data` 单独当作完整备份，也不要把同一个卷共享给多个实例。

首次上线后记录 `docker volume inspect pa-investment-research_dsh-data` 的结果。执行一致性备份前先停止唯一实例，并确认没有活动导入、重置、seed 下载或后台写任务：

```bash
docker compose --env-file .env.container stop investment
docker volume inspect pa-investment-research_dsh-data
# 在实例停止期间完成整卷快照或备份后重新启动。
docker compose --env-file .env.container up -d --no-build
```

在实例停止期间，使用云盘快照或运维备份工具复制整个 volume 对应的 `$DSH_HOME`，完成后再执行上面的启动命令。不要只备份部分子目录，不要在运行中直接复制 SQLite 文件，也不要用 `docker compose down -v` 删除卷。详细白名单、在线 SQLite 限制、迁移与恢复步骤见[单实例数据目录与迁移](maintainers/单实例数据目录与迁移.md)。备份只有在隔离环境完成恢复演练并核对设置、会话、附件、投研历史、行业链报告和 `.pabackup` 后才算可用。

## 升级与回滚

升级前记录当前镜像 ID 或 digest、完整 commit SHA、`.env.container`、展开后的 Compose 配置和整卷备份身份。停止旧容器并完成离线一致性备份后，载入新的 CI 归档或本地构建的新镜像，把 `DSH_IMAGE` 改为新的不可变身份，再重建唯一实例：

```bash
docker compose --env-file .env.container up -d --no-build
docker compose --env-file .env.container ps
docker compose --env-file .env.container logs --tail 200 investment
```

等待容器变为 `healthy`，再通过真实 HTTPS 入口完成登录和三后端业务验收。不要让新旧容器并行挂载同一个卷。

如果新版本尚未写入或迁移持久格式，可以把 `DSH_IMAGE` 恢复为已记录的旧镜像 ID/digest 对应引用，并再次执行 `up -d --no-build`。如果新版本已经修改持久数据，不能只回退镜像：先停止容器，按迁移文档恢复与旧镜像匹配的整卷备份，再启动旧镜像。完整判断和故障处理见[容器部署与回滚](maintainers/容器部署与回滚.md#教程升级与回滚)。

## 上线验收清单

- [ ] 主机是 Linux x86_64，Docker Engine 与 Compose v2 可用，容量满足当前数据和至少一次回滚。
- [ ] 镜像、仓库文件、完整 commit SHA、CI 或本地构建证据互相匹配，`DSH_IMAGE` 未使用 `latest`。
- [ ] DNS 指向正确主机，TLS 证书有效且能自动续期，HTTP 会跳转到 HTTPS。
- [ ] 公网只开放必要的 80/443，`3080` 和 Docker daemon 未暴露，SSH 已限制来源。
- [ ] `.env.container` 权限为 `0600`，`TZ` 与 `TIMEZONE` 相同，trusted hosts/proxies 都是核实后的精确值。
- [ ] 管理员密码哈希文件由 `10001:10001` 所有、权限为 `0400`，任何配置和日志都不含明文密码。
- [ ] 只有一个 `investment` 容器挂载唯一 `dsh-data` 卷，未使用 `--scale`，没有第二个共享卷实例。
- [ ] `docker compose ps` 显示容器为 `healthy`，本机 Host 健康检查和公网 HTTPS 健康检查都通过。
- [ ] 使用真实域名完成管理员登录，并验证 `trading-core`、`market-watch`、`industry-chain` 的关键业务路径。
- [ ] 已记录镜像身份、配置和卷位置，已完成离线整卷备份及隔离恢复演练。
- [ ] 已准备旧镜像与匹配的数据备份，维护者理解应用回滚与数据回滚的区别。
