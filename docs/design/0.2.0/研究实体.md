A股对话式投研：研究实体 Schema v1.0
文档类型：工程设计与实现规范

目标读者：Claude Code / 工程研发人员

适用场景： 伙伴式陪伴投研产品。用户通过自然语言发起投研委托，系统识别研究对象，明确研究范围，并提前匹配所需工具，为后续研究流程做准备。
一、项目背景与核心目标
1.1 业务背景
用户可能通过以下方式提出研究需求：
- “帮我分析一下宁德时代最近的投资价值。”
- “看看我的持仓里哪些公司和固态电池产业链有关。”
- “人形机器人产业链有哪些值得关注的公司？”
- “如果未来降息，对高股息板块有什么影响？”
- “帮我分析一下比亚迪和特斯拉在产业链、财务和估值方面的差异。”
这些问题通常同时包含研究对象、研究主题、研究范围、时间要求和潜在的数据需求。

如果只做通用意图识别，系统可能知道用户想“分析股票”，却不知道具体要分析哪些实体、需要建立哪些关联，以及应该提前准备哪些数据工具。

因此，需要设计一套独立的研究实体识别与 Scope 构建机制。
1.2 核心处理流程
用户自然语言输入

原始问题、研究诉求、约束条件

实体抽取与类型识别

识别股票、公司、行业、事件、宏观因子等

实体标准化与消歧

统一名称、代码、实体 ID，处理歧义与关联关系

研究 Scope 构建

确定研究对象、范围、时间、约束和待确认事项

Tool 预挂载

根据实体类型和研究需求，推荐需要准备的工具


1.3 本期交付目标
1. 建立可扩展、可维护的研究实体类型注册表。
2. 定义统一的实体数据结构及标准化规则。
3. 支持实体抽取、候选实体检索、消歧和关联关系识别。
4. 定义研究 Scope 的标准输出协议。
5. 建立实体类型与 Tool 的映射机制。
6. 提供可执行的测试用例与验收标准。
本期重点是实体 Schema 与处理机制的工程落地，不要求一次性建设完整的证券主数据、产业链知识图谱或全部投研数据接口。

二、核心概念与边界
系统必须区分以下四个概念，不能将它们混为一谈。
概念	含义	示例
Intent（研究意图）	用户希望完成什么任务	个股分析、行业研究、公司比较、情景分析
Entity（研究实体）	研究涉及的具体对象	宁德时代、固态电池、降息、CPI
Scope（研究范围）	本次任务实际覆盖哪些对象和维度	宁德时代、固态电池产业链、近一年
Tool（研究工具）	完成任务所需的数据查询或分析能力	行情查询、财务分析、产业链查询
例如，用户提出“分析宁德时代与固态电池产业链的关系”：
- Intent：产业链关联分析。
- Entity：宁德时代、固态电池。
- Scope：宁德时代在固态电池产业链中的业务布局、关联环节及相关证据。
- Tool：公司业务查询、公告检索、产业链映射查询等。
关键原则：实体识别不等于意图识别；识别到实体也不意味着必须立即调用所有相关工具。

三、研究实体类型体系
3.1 类型设计原则
实体类型需要满足以下要求：
- 稳定性： 类型编码一经发布，不应随意变更。
- 可扩展性： 新增实体类型时，不影响既有类型。
- 可识别性： 每种类型均有清晰定义、示例和边界。
- 可标准化： 能映射到标准实体 ID 或可验证的标准标识。
- 可挂载工具： 实体类型可以关联默认工具，但具体挂载仍需结合 Intent 和 Scope。
- 可审计： 保留原始提及、标准化结果、候选实体和消歧依据。

3.3 各实体类型的定义与识别规则
A. ENTITY_01：证券标的
类型	定义与示例	标准化重点
ENTITY_01_01 A股股票	宁德时代、贵州茅台、比亚迪	证券代码、交易所、证券名称
ENTITY_01_02 ETF／指数基金	沪深300ETF、科创50ETF	基金代码、基金全称、跟踪标的
ENTITY_01_03 宽基指数／行业指数	沪深300、中证500、半导体指数	指数代码、指数名称、编制机构
ENTITY_01_04 可转债	某上市公司发行的可转债	债券代码、债券名称、发行主体
注意：
- 同一公司可能对应股票、债券、基金等不同证券实体。
- 公司实体与股票实体必须分别建模。
- 仅有简称且存在多个候选标的时，不得直接认定为唯一证券。
B. ENTITY_02：公司主体
类型	定义与示例	标准化重点
ENTITY_02_01 上市公司	宁德时代、贵州茅台	统一公司 ID、法定名称、证券关联
ENTITY_02_02 子公司／关联公司	上市公司旗下子公司、参股企业	公司 ID、母子公司关系、持股关系
ENTITY_02_03 实际控制人／核心管理人员	实际控制人、董事长、总经理	人员 ID、任职公司、任职时间
公司名称与证券简称不能直接当作同一实体。公司更名、人员任职变化、股权关系变化应当保留时间维度。
C. ENTITY_03：行业与产业
类型	定义与示例	标准化重点
ENTITY_03_01 标准行业	银行、汽车、电子、医药生物	行业分类体系、行业代码
ENTITY_03_02 细分赛道／主题产业	HBM、固态电池、人形机器人、液冷、AI服务器	统一主题 ID、别名、定义和边界
ENTITY_03_03 产业链环节	正极材料、设备、整机、零部件、渠道	产业链 ID、上下游关系、所属主题
细分赛道不一定属于唯一的标准行业，产业链环节也不能简单等同于行业分类。

例如，“液冷”是技术／产业主题，“液冷服务器部件”是产业链环节，“电子”可能是标准行业。系统应保留这些层次之间的关联关系。
D. ENTITY_04：主题与催化
类型	定义与示例	标准化重点
ENTITY_04_01 产业趋势主题	AI算力需求增长、固态电池产业化	主题 ID、主题定义、有效期
ENTITY_04_02 政策主题	新能源补贴、产业扶持政策	政策主题 ID、发布机构、适用范围
ENTITY_04_03 公司事件	业绩预告、重大合同、并购、回购	事件 ID、公司 ID、事件时间
ENTITY_04_04 宏观／监管事件	降息、监管规则调整、重要宏观数据发布	事件 ID、事件类别、发生时间
必须区分：
- 事件实体： 某次具体降息、某份公告、某项政策。
- 事件主题： 降息预期、政策支持、新规影响。
- 宏观因子： 利率水平、通胀水平等连续变化的变量。
不能将“降息”一律识别成同一种实体，应结合上下文判断用户指的是事件、预期还是宏观因子。
E. ENTITY_05：资金与市场风格
类型	定义与示例	标准化重点
ENTITY_05_01 资金流向实体	北向资金、融资余额、龙虎榜、ETF申购赎回	资金类型、统计口径、时间区间
ENTITY_05_02 市场风格	高股息、小微盘、价值、成长、低波动	风格定义、分类规则、适用范围
ENTITY_05_03 可比基准实体	沪深300、中证全指、同业指数	基准 ID、比较口径、时间区间
资金流向实体可以是一个数据观察对象，而不一定是具有独立证券代码的金融产品。

例如，“北向资金”是资金流向相关实体，“北向资金净流入额”则是某个指标，不应直接混为一谈。
F. ENTITY_06：宏观与大宗商品
类型	定义与示例	标准化重点
ENTITY_06_01 宏观因子	CPI、PMI、DR007、美元指数、利率、汇率	指标代码、发布机构、频率、单位
ENTITY_06_02 大宗商品／产品品类	碳酸锂、生猪、铜、原油、面板价格	商品品种、规格、市场、报价口径
ENTITY_06_03 区域主题	海南自贸港、长三角、大湾区	区域 ID、空间范围、相关政策
宏观因子和商品品类通常需要额外的观测维度，例如时间、单位、频率、报价市场、规格或地区。

四、动态实体集合设计
除上述 20 种静态实体类型外，还需要支持随用户账户、研究任务或系统上下文变化的动态实体集合。

动态集合不是新的静态实体类型枚举，而是实体来源与集合管理机制。
动态集合	建议标识	含义	数据来源
用户持仓	USER_PORTFOLIO	用户当前持有的证券集合	经授权的账户／持仓数据
用户自选	USER_WATCHLIST	用户关注的证券或主题集合	经授权的自选数据
动态可比对象	DYNAMIC_COMPARABLES	按行业、业务、规模等规则生成的可比对象	标准主数据及筛选规则
任务生成集合	TASK_GENERATED_SET	当前研究过程中筛选得到的对象集合	当前任务的计算与筛选结果
动态集合应至少保留以下信息：
- collection_id：集合标识。
- collection_type：集合类型。
- source：数据来源。
- as_of：集合对应的时间。
- member_entity_ids：集合中的实体 ID。
- filter_definition：生成集合的筛选条件。
- authorization_status：授权状态或访问检查结果。
约束：
1. 不得把用户持仓或自选写死在代码中。
2. 不得在未获得授权或无法读取数据时虚构集合成员。
3. 动态集合应明确数据时间，不能默认当前集合与历史时点一致。
4. 如果无法读取用户持仓，应明确提示并询问是否提供相关信息。
5. 动态集合生成的成员仍需通过实体标准化和有效性校验。

五、核心数据模型
建议至少设计 EntityType、EntityInstance 和 EntityMention 三种数据结构。
5.1 EntityType：实体类型定义
{
  "type_code": "ENTITY_01_01",
  "parent_code": "ENTITY_01",
  "type_name": "A股股票",
  "description": "在中国境内证券交易所上市交易的A股股票",
  "priority": "P0",
  "is_dynamic": false,
  "normalization_keys": [
    "security_code",
    "exchange",
    "security_name"
  ],
  "default_tool_ids": [
    "security_lookup",
    "quote_history"
  ],
  "schema_version": "1.0",
  "status": "active"
}


要求：
- type_code 全局唯一且稳定。
- parent_code 用于构建类型层级。
- normalization_keys 定义该类型的关键标准化字段。
- default_tool_ids 只代表默认推荐工具，不意味着工具必然存在或必须执行。
- 类型定义需要版本管理和启停状态。
5.2 EntityInstance：标准实体实例
{
  "entity_id": "SECURITY_xxx",
  "entity_type_code": "ENTITY_01_01",
  "canonical_name": "示例证券名称",
  "aliases": [
    "示例简称"
  ],
  "identifiers": {
    "security_code": "000000",
    "exchange": "示例交易所"
  },
  "attributes": {},
  "relations": [],
  "source": "illustrative_placeholder",
  "last_verified_at": null,
  "status": "unverified"
}


上述 ID、代码和名称仅用于说明字段结构，不代表真实证券数据。

要求：
- entity_id 是系统内部实体标识，不应直接由用户原始文本拼接而成。
- canonical_name 为标准名称。
- aliases 用于管理简称、历史名称和常见别名。
- identifiers 保存可验证的外部标识。
- relations 表示与其他实体的关联。
- 真实数据必须记录来源和核验状态；不能将示例数据误当成已核验数据。
5.3 EntityMention：用户原文中的实体提及
{
  "mention_id": "MENTION_001",
  "raw_text": "宁德时代",
  "normalized_text": "宁德时代",
  "start_offset": 7,
  "end_offset": 11,
  "candidate_entity_ids": [],
  "resolved_entity_id": null,
  "entity_type_candidates": [
    "ENTITY_01_01",
    "ENTITY_02_01"
  ],
  "confidence": null,
  "resolution_status": "pending"
}


EntityMention 与 EntityInstance 必须分离。

同一个标准实体可能在一句话中被多次提及；一个原始提及也可能对应多个候选实体。因此，不应将原始文本直接覆盖为标准实体记录。

字段说明：
- raw_text：原始提及，不得丢失。
- start_offset、end_offset：原文位置；统一采用字符偏移或统一采用字节偏移，整个项目必须保持一致。
- candidate_entity_ids：候选标准实体。
- resolved_entity_id：最终确定的实体 ID。
- confidence：当前消歧结果的置信度。
- resolution_status：如 resolved、ambiguous、pending、unresolved。

六、实体抽取、标准化与消歧
6.1 处理步骤
建议采用以下处理流程：
1. 解析用户原始问题。
2. 抽取实体提及及其原文位置。
3. 识别候选实体类型。
4. 检索候选标准实体。
5. 根据名称、代码、上下文和关联关系进行排序。
6. 判断是否存在歧义。
7. 输出已确认实体、待确认实体及消歧依据。
8. 将实体结果交给 Scope Builder。
如果没有可用的标准主数据或检索结果，不得仅凭模型猜测就生成一个已验证的真实 entity_id。
6.2 候选实体排序依据
候选实体可以综合考虑：
- 完整名称匹配。
- 别名匹配。
- 证券代码或其他唯一标识匹配。
- 用户上下文。
- 实体之间的关联关系。
- 数据源的权威性和时效性。
建议为每个候选实体记录：
{
  "entity_id": "ENTITY_PLACEHOLDER",
  "match_reason": [
    "alias_match",
    "context_match"
  ],
  "confidence": 0.82,
  "source": "illustrative_source"
}


这里的分值仅为结构示例。实际分值需要结合数据和测试集校准。
6.3 消歧示例
用户提及	潜在问题	处理方式
茅台	可能指上市公司、股票或相关品牌	结合“股价”“公司经营”等上下文判断
宁德	可能是地区、公司简称或其他对象	优先检索候选实体，必要时追问
比亚迪	可能指公司或股票	根据研究任务区分公司实体和证券实体
苹果	可能指水果、Apple 公司或产业链相关对象	结合上下文识别
科技板块	边界不明确，可能对应多种行业分类	根据研究目标和分类体系明确范围
降息	可能指已经发生的事件、降息预期或宏观情景	根据时间与语境确定实体类型
6.4 置信度与追问机制
可先使用以下阈值作为初始配置，再通过测试集调整：
- confidence >= 0.85：高置信度。
- 0.60 <= confidence < 0.85：中置信度。
- confidence < 0.60：低置信度。
注意：这些阈值不是已验证的最优参数。

置信度高也不意味着任何情况下都可以直接确定。 如果候选实体不同会显著改变研究范围，或者涉及用户持仓、具体证券标的等关键对象，仍需要严格校验。

当无法可靠消歧时，系统应：
- 保留候选实体。
- 标记为 ambiguous 或 pending。
- 生成简洁、针对性的澄清问题。
- 在必要实体未确定前，不应假装已经建立完整 Scope。

七、研究 Scope 的输出协议
7.1 Scope 的作用
Scope 是实体识别与实际研究执行之间的中间层，负责将自然语言问题转换为结构化研究任务。

它至少需要描述：
- 本次任务的研究意图。
- 研究实体及其角色。
- 研究范围和时间约束。
- 待确认事项。
- 推荐预挂载的工具。
- 当前处理状态与风险提示。
7.2 建议输出 Schema
{
  "schema_version": "1.0",
  "request_id": "REQUEST_PLACEHOLDER",
  "raw_query": "用户原始问题",
  "intent_list": [
    {
      "intent_code": "INDUSTRY_RELATION_ANALYSIS",
      "description": "分析公司与产业链的关系"
    }
  ],
  "entity_list": [
    {
      "mention_id": "MENTION_001",
      "entity_id": null,
      "entity_type_code": "ENTITY_01_01",
      "raw_text": "宁德时代",
      "role": "primary_subject",
      "resolution_status": "pending",
      "confidence": null

八、实体类型与 Tool 预挂载映射
8.1 基本原则
Tool 预挂载的目标是为后续研究准备可用能力，而不是看到某个实体就执行全部相关工具。

建议综合以下三个因素确定预挂载工具：
1. 实体类型。
2. 用户研究意图。
3. 当前 Scope 中明确的研究维度和约束。
例如，分析个股短期行情和分析公司长期基本面，可能涉及同一只股票，但所需工具明显不同。

九、端到端示例
示例一：持仓中的公司与产业链关系
用户输入：
帮我看看我持仓里的宁德时代，和固态电池产业链有什么关系。

预期处理：
1. 识别动态集合 USER_PORTFOLIO。
2. 识别“宁德时代”，候选类型包括上市公司与A股股票。
3. 识别“固态电池”为细分赛道／主题产业。
4. 根据授权的持仓数据确认用户是否持有该证券。
5. 根据公司资料、公告和产业链信息建立关联。
6. 推荐公司资料、公告检索、产业链查询等工具。
7. 如果持仓数据不可用，明确提示用户，不得假设其持有宁德时代。
示例二：产业主题与政策催化
用户输入：
人形机器人有哪些值得关注的政策催化？

预期识别：
- 实体：人形机器人。
- 类型：ENTITY_03_02。
- 关联实体类型：ENTITY_04_02 政策主题、ENTITY_04_04 宏观／监管事件。
- 建议工具：theme_lookup、policy_search、official_document_search、event_timeline_lookup。
后续研究应区分已发布政策、征求意见稿、市场传闻和研究推断，不能将不同证据等级混为一谈。
示例三：用户持仓风险分析
用户输入：
帮我分析一下我的持仓风险。

预期识别：
- 动态集合：USER_PORTFOLIO。
- Intent：持仓风险分析。
- Scope：需要确认持仓、仓位、分析时间及可用数据。
- 建议工具：portfolio_lookup、portfolio_risk_analysis，以及根据持仓成分动态匹配的行情和风险分析工具。
如果没有获得持仓授权，系统可以询问用户是否愿意提供持仓数据，不能自行编造持仓。
示例四：宽泛研究对象
用户输入：
帮我研究一下科技板块。

预期处理：
- 抽取“科技板块”。
- 识别其属于行业／主题范畴，但暂不强行映射为唯一行业。
- 根据已有分类体系生成候选范围。
- 如果候选范围对结果影响较大，则询问用户更关注哪个领域，或者先给出明确标注的默认研究范围。
示例五：宏观情景与市场风格
用户输入：
如果未来降息，对高股息板块有什么影响？

预期识别：
- 宏观事件／情景：降息。
- 市场风格：高股息。
- 研究任务：宏观情景分析。
- 可能需要的工具：macro_series_lookup、style_performance_lookup、benchmark_lookup。
Scope 应明确这是情景研究，不应把未来降息描述为已发生事实。

十、工程模块划分
建议按职责拆分，具体目录和命名应以现有项目架构为准。
模块	职责
entity_type_registry	管理实体类型、版本、启停状态
entity_mention_extractor	从用户问题中抽取实体提及
entity_candidate_retriever	查询标准实体候选
entity_normalizer	统一名称、代码和标准字段
entity_disambiguator	处理歧义、候选排序和置信度
entity_relation_resolver	建立实体间关联关系
scope_builder	生成结构化研究 Scope
tool_preloader	根据 Scope 推荐和检查逻辑 Tool
schema_validator	校验输入输出字段、类型和状态
audit_logger	记录抽取、消歧、Scope 变更和工具推荐依据
模块边界
- 实体抽取不负责决定最终研究范围。
- 消歧模块不负责直接执行研究工具。
- Scope Builder 不应绕过实体校验直接构造已确认实体。
- Tool Preloader 不应默认调用所有推荐工具。
- Audit Logger 不应记录不必要的敏感数据或凭证。

11.2 实体抽取与消歧测试
- [ ] 能抽取常见证券、公司、行业、主题和宏观实体。
- [ ] 能保留原始文本和位置。
- [ ] 同一实体多次出现时能够正确处理。

- [ ] 没有真实数据源时不会伪造已验证实体 ID。
- [ ] 历史名称、别名及关联实体具备基本测试覆盖。
11.3 Scope 构建测试
- [ ] Scope 输出符合统一 Schema。
- [ ] 必需字段缺失时能够被检测。
- [ ] 待确认实体不会被静默标记为已解决。
- [ ] 原始问题、研究约束和消歧警告不会无故丢失。
- [ ] 允许保存部分完成的 Scope。
- [ ] 不同 Intent 对应合理的研究范围与工具推荐。
11.4 Tool 预挂载测试
- [ ] 每个工具 ID 都能在工具注册表中验证，或明确标记未配置。
- [ ] 工具推荐具有可解释的原因。
- [ ] 不同研究意图能够调整工具推荐结果。
- [ ] 用户持仓相关工具执行前会检查授权。
- [ ] 预挂载与实际调用严格区分。
- [ ] 不会因为识别到实体就自动触发未经授权的外部操作。
11.5 验收原则
测试通过必须以实际执行结果为准。不能仅依据代码静态检查或模型口头说明就宣称功能通过。
