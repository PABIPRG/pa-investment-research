## 0. 结论摘要

1. **产品主链（委托）在后端仍是 0。** 全仓（排除 `env/`、`node_modules/`）检索 `mandate`、`condition_plan`、`tracking_dependencies`、`notification_decision`、`research_job`，没有任何业务实现。V1.3 第 5 章描述的委托核心、Hook 契约、持久任务、联系资格，全部是待建。
2. **研究能力层完成度最高。** `research_entities/` 已有实体/别名/消歧/Scope/45 个工具/证据/报告/刷新，约 3,700 行 + 19 个测试文件；但它是独立 `:8300` 服务，未注册进前端 operation、未注册为 DSH 工具、也未与委托核心连接。
3. **投递层强、决策层弱。** 通知中心已有 SQLite 幂等、去重、租约投递、重试、死信、多渠道；但没有“该不该发、为什么发、合并到哪条、静默与暂缓”的决策层，也没有委托/版本/资格关联。
4. **现状与目标有四个结构性冲突**（与 2026-10-19 的差距分析一致，V1.3 未改变）：
   - 存储：本地 JSON + 单用户 `default` ↔ 事务型业务状态 + 版本 + 作用域；
   - 条件：二值阈值、缺失字段被过滤后 AND 仍可触发 ↔ 三值 + 未知传播 + 故障独立；
   - 事件：自选/持仓广播命中 ↔ 按委托依赖精确路由；
   - 证据：报告字符串/扁平决策 ↔ 文档、观测、证据链接、版本与引用位置。
5. **首期不应照搬 10 月 19 日清单里的完整 B7「条件方案」体系。** V1.3 已把“触发约定”收敛进委托版本，投资假设/条件方案降为后续增强。先做**委托 + 联系决策**，再抽条件节点。
6. **建议首个开发切片**：`mandate.created → company.event_available → research.run_completed → notification delivery result → mandate.paused/resumed`。这条链打通，才算产品成立；其余事件源按同一契约扩展。

### 3.3 依赖编译算法（revise 时只重算受影响部分）

输入：新 revision 的 goal/scope/triggers/contact_policy。
输出：`tracking_dependencies` 集合 + 需要新建/取消/保留的任务。

```
1. 规范化 scope
   - 固定集合：entity_id 列表 + 版本
   - 动态集合（我的持仓/自选）：collection_id + 成员解析规则 + 授权依据
   - 未消歧对象：不生成依赖，生成 requirement
2. 规范化 triggers
   - 事件型：hook_type + subject + event_type + feature_key + 过滤条件
   - 时间型：交易日历 + 时区 + 到期规则 + 到期实例
   - 条件型：数值/语义条件 + 比较口径 + 数据要求 + 未知处理
3. 生成依赖键 dependency_key = hash(hook_type, subject_id, event_type, feature_key, scope_key, rule_version)
4. 与旧 revision 的依赖做 diff
   - 新增 → 写依赖，必要时补一次基准
   - 删除 → active=false，取消尚未领取的任务
   - 未变 → 保留，不重跑
5. 仅名称/备注变化：不重编译；联系偏好变化：只重验资格
```

### 3.4 事件匹配与“是否需要研究”

```
receive(event) → inbox 去重 → 规范化 subject_ids
  → 查 active dependencies(subject, hook_type, event_type)
  → 对每个 mandate：
       版本有效？未暂停/结束？范围命中？时效命中？额度未超？
       否 → 记录 skip + reason，不建任务
       是 → 建 job（去重键 = mandate_id+revision+event_id+action）
  → 直接提醒类：不建研究任务，只建到期实例
```

要点：
- 事件到达 ≠ 需要研究；研究完成 ≠ 应当推送。
- 同一财报从公告/新闻/公司事件多路到达时，按来源文档标识与版本合并；无法确认同一来源时不强行去重。
- 行业新闻只做语义相似时，先进“候选复核”，不直接产生机会提醒。

### 3.5 三值条件与状态转换算法

条件节点是程序配置，不是模型临时生成的自然语言：

```
eval(node, snapshot):
  required inputs → 缺失原因（未披露/获取失败/不支持/过期）
  AND: 任一 false → false；全部 true → true；其余 unknown
  OR : 任一 true → true；全部 false → false；其余 unknown
  NOT: unknown → unknown
  异常：单独记 error，不混入 unknown
```

时间状态：`first_enter / sustained / re_enter / exit`；按交易日历与时区计算；迟到事件按 `occurred_at` 归位，修订事件重评受影响节点。阈值必须来自用户约定或已登记方法，模型不能临时补成生效规则。

### 3.6 持久任务与恢复

- 领取：`UPDATE ... WHERE status='pending' AND next_run_at<=now` + `lease_token/lease_expires_at`；持过期租约者不能提交结果。
- 启动幂等：`job_id + attempt_id`；回执丢失先查询/对账，不盲目重跑。
- 取消：`cancel_generation++`；旧结果只留历史，不获得新联系许可。
- 预算：达到后保存部分结果 + 具体恢复条件，不自动重跑整份分析。
- 恢复：`runtime.recovered` 扫描未完成任务、inbox 游标、到期日程；按类型有界补偿，不全量重跑。
- 迟到结果：版本/租约不匹配 → 归档，不覆盖新状态。

### 3.7 Hook 落地清单（按优先级）

| 优先级 | Hook | 产生方 | 首期行为 |
|---|---|---|---|
| P0 | `mandate.created` | 委托命令 | 需要初始研究则建任务；当场研究可作基准 |
| P0 | `company.event_available` | 公告/财报适配器 | 匹配公司与资料依赖，建复核任务 |
| P0 | `research.run_completed` | DSH 回调 | 保存结果/基准，进入联系评估 |
| P0 | `research.run_failed` / `lease_expired` | 任务执行器 | 对账、有限重试/WaitingData |

### 3.8 与 DSH 的边界（对接前必须和前端约定）

后端只做**确定性**部分，DSH 做**理解与解释**：

| 事项 | 后端 | DSH |
|---|---|---|
| 意图理解、澄清、研究规划 | 不接管 | 负责 |
| 实体候选与消歧 | 提供工具 | 组织调用、让用户确认 |

**需要冻结的接口**（建议先写 OpenAPI/JSON Schema）：

3. 事件信封（§5.6.3 字段）；

5. 工具清单（实体 45 工具 + 计算工具）的输入输出 Schema。

## 4. 后端重点二：消推（联系决策）算法

### 4.1 两段独立判断

1. **执行前**：这个变化是否需要复核该委托？→ 决定是否建任务。
2. **执行后**：结果是否满足联系约定？→ 决定是否进入投递。

事件到达、研究完成、投递成功是三件事，不能互相替代。

### 4.2 联系评估流水线

```
run_result
  → ① 结果完整性：有没有结构化结果/证据批次；执行故障单独记 error
  → ② 条件评估：数值按已登记规则比较；语义按 DSH 判断 + 证据对应校验
        输出 met / unmet / unknown / error
  → ③ 联系约定：用户是否约定了“什么情况下联系”
        - 明确到期提醒：到点即发，不要求新发现
        - 定时交付：按约交付，无变化也说明本次结果
        - 周期检查：无值得关注变化 → 安静记录
  → ④ 资格复核：当前 revision、暂停/结束、主体权限、结果是否属于当前版本
  → ⑤ 抑制与合并：冷却、静默时段、暂缓、重复、跨渠道去重、同类合并
  → ⑥ 形成 contact_decision（send/suppress/defer/aggregate + reason_code）
  → ⑦ 通知模块投递；发送前再次核验资格
  → ⑧ 保存投递结果；未知结果先查询/核对，不承诺绝对只送一次
```

### 4.3 抑制与合并规则（程序配置，可测试）

| 规则 | 行为 | 必须记录 |
|---|---|---|
| 去重 | 同一 `dedupe_key` 在窗口内只保留一条，更新计数/最近时间 | 命中哪条既有通知 |
| 冷却 | 同一委托+条件在冷却期内不重复发 | 冷却起止与依据 |
| 静默时段 | 用户配置的时段内延后到下一个允许时刻 | 原定发送时间与延后原因 |
| 暂缓（snooze） | 用户对某条提醒暂缓，到期前不重发 | 暂缓对象与到期时间 |
| 合并 | 同委托多条进展合并为一条摘要 | 保留每项委托的联系依据 |
| 版本失效 | revision 变更后旧结果不获得发送许可 | 旧 revision 与当前 revision |
| 权限撤销 | 撤销后阻断后续副作用 | 撤销事件与阻断点 |
| 渠道不可用 | 通知模块拒绝投递，不回退到“研究没发生” | 渠道错误与重试状态 |

### 4.4 现有通知中心需要改什么

保留：投递、重试、死信、渠道配置、已读归档、设备订阅。
新增在其上游：

1. `contact_decisions` 表与 `NotificationDecisionService`；
2. 发送前 `recheck(mandate_id, revision, decision_id)` 钩子；
3. 静默时段、暂缓、合并窗口的偏好与状态；
4. 通知 payload 增加 `mandateId / mandateRevision / decisionId / reasonCode / evidenceRef / returnUrl`；
5. 投递结果回调写回 `contact_records`，并发出 `notification.delivery_result`；
6. 用户可见的“为什么没发”查询接口（至少给委托查询页）。

### 4.5 可观测指标

- 每类 Hook 的接收/匹配/跳过/建任务/完成/失败数量；
- 任务积压、租约回收、重试次数、预算耗尽；
- 条件结果分布（met/unmet/unknown/error）；
- 抑制原因分布、静默延后时长、合并条数；
- 投递成功率、未知结果数、重复投递数；
- 单次委托成本与单条有效提醒成本。

### 5.1 存储与 Repository（B0）

| 缺什么 | 做法 |
|---|---|

策略自进化复用已覆盖：自进化闭环每轮完成后，把“本轮完成”与每个升级/降级/淘汰/变异动作落成统一事件信封并投递委托核心；事件先写本地 outbox，投递成功才标记，失败保留待发，`event_id` 由轮次与策略确定，重复登记与重复投递都幂等。委托侧新增两个 Hook（`strategy.condition_changed`、`strategy.evolution_completed`），只有用户在委托里显式写了触发器才会收到事件——旧策略、旧自选不会自动转成生效委托（V1.3 §6.1）。`StrategyEvolutionRunner` 收到策略事件后只读查询策略池状态、影子归因与待确认预案，产出 `metrics`（影子天数、动作数、阶段变化、预案数、影子收益）与中文摘要；数据不足时写 `shadow_data_insufficient` 缺口并保持安静，能力不可达时任务失败等待重试，不写成“没有变化”。**执行器不应用任何进化写动作**：升级/降级/淘汰/变异仍由用户在 trading-core 侧凭预案令牌确认，或由已授权的闭环调度完成。研究能力服务（`:8300`）同时新增三个只读工具，可用性标记为 `external_service`，trading-core 离线时返回 `unavailable` 而不伪造结论；这三项不进入工具缓存，避免旧预案被当成当前结论。新增 13 项测试。

## 8. 风险与已知坑

| 风险 | 后果 | 应对 |
|---|---|---|
| 双白名单只构建一侧 | 请求被静默拒绝，无报错 | 每次加 operation 双构建 + 联调用例 |
| JSON 并发写 | 委托/事件状态互相覆盖 | 业务状态一律走 SQLite 事务；JSON 只做迁移源 |

| 旧通知出口未接管 | 绕过委托、重复发送 | 最小闭环后立即切换并加回归用例 |
| 模型临时补阈值 | 用户约定被静默改写 | 阈值必须来自用户约定或登记方法 |
| 时区/交易日历 | 到期错位、漏提醒 | 统一 UTC 存储 + Asia/Shanghai 计算 + 实例标识 |

| 研究实体未提交/未跑测 | 接入后发现回归 | Slice 0 先核验 |
| baostock 高频登录 | 临时 IP 封禁 | 复用会话、失败回补（已有经验） |
