## 1. 结论摘要

1. **产品对象模型发生变化，而非页面级迭代。** 当前产品的核心对象是「策略 + 报告 + 任务」；第二代的核心对象是「研究委托（mandate）—研究问题—假设/证据—条件方案—提醒决策—用户反馈」。这条主链在后端几乎不存在。
2. **现有资产可复用约 40%–50%。** 行情/新闻/事件采集、多智能体分析、回测与影子、自进化、KYC/风险画像、统一通知中心（SQLite 租约投递）、104 个 operation 白名单、Electron 桌面壳均可承接。
3. **后端主要工作量不在模型，而在四项基础设施：**
   - 统一实体身份与可定位证据；
   - 委托/条件/任务的持久化状态与恢复；
   - 三值条件语义与事件依赖路由；
   - 提醒决策与「用户回应—实际操作」反馈。
4. **必须先解决四个结构冲突：**

   | 冲突 | 现状 | 目标 |
   |---|---|---|
   | 存储与作用域 | 本地 JSON + 单用户 `default` | 事务型业务状态 + user/account 作用域 |
   | 条件语义 | 二值阈值，缺失条件被过滤后 AND 仍可触发 | 三值（真/假/未知）+ AND/OR/NOT |
   | 事件语义 | 「自选 + 持仓」广播命中 | 按委托/方案依赖精确路由 |
   | 证据形态 | 报告字符串、扁平决策行 | 文档、观测、证据链接、版本与引用位置 |

5. **首期只打通一个个股委托闭环。** 口语 → 实体 → 委托 → R01 初次研究 → P01 历史位置观察 → 事件唤醒 → 提醒 → 回应。不要一开始铺满 T01–T12 / C01–C12。

## 2. 目标产品形态

### 2.1 范式转变

| 维度 | 当前产品（0.1.0-rc.10） | 第二代中短线投研伙伴 |
|---|---|---|
| 产品定位 | 投研工作台：看盘、分析、生成策略、回测、影子、进化 | 研究伙伴：接受委托、跨会话持续研究、按约定条件跟踪、适时提醒 |
| 核心对象 | 策略（candidate/active/watch/retired）、报告、任务 | 研究委托、研究问题、假设版本、证据、条件方案、提醒决策、用户回应 |
| 用户路径 | 用户主动打开页面或对话，发起一次性分析 | 用户一句口语 → 系统建档 → 后台持续取证 → 有变化时主动找到用户 |
| 研究形态 | `analyze` / `brief` 一次性产出 | R01 初次研究 → R02 披露复核 → R03 持仓条件检查，可重复执行 |
| 条件与提醒 | 阈值告警 + 事件命中自选/持仓 | 用户条件方案（版本化、三值评估、依赖订阅）+ 提醒决策（发送/汇总/抑制/延后） |
| 验证对象 | 策略回测、影子、进化 | 判断复核 + 策略验证 + 用户框架 + 提醒效果，四类分开评价 |
| 前台结构 | 工作台、智能分析、盯盘、策略研究、自进化、产业链、设置 | 持仓与自选、聊天、用户框架、框架验证与演进、通知 |
| 模型角色 | 生成策略假设、写报告 | 有限意图识别、材料提取、开放分析；事实、状态、规则与通知权限归程序 |
| 后台运行 | 进程内 APScheduler + JSON 状态 | 持久任务（租约/检查点/预算/恢复）+ 事件驱动 Core |
| 部署形态 | 本地单用户桌面 | 部署形态与服务承诺需一起确定（本地或服务端） |

### 2.2 目标用户旅程

以设计文档示例为例：

```text
“帮我关注科士达，看看现在的位置，什么时候值得进一步考虑买入，有什么风险。”
  ↓ 有限意图：关注对象 / 历史位置 / 风险复核 / 入场条件 / 是否持续跟踪
  ↓ 实体解析：科士达 → 公司 + 证券；歧义时返回候选，不默选
  ↓ 读取用户事实：持仓、约束、已有委托；缺失保持未知
  ↓ 能力检查：可执行部分 + 受阻部分 + 具体缺口
  ↓ 建立委托与研究问题（已明确部分可先生效）
  ↓ R01 初次研究：身份、历史基线、价格分位、回撤、问题清单、研究订阅
  ↓ 条件明确且被采纳后进入 P01 历史位置观察
  ↓ 后台：行情更新/公告发布 → 依赖路由 → 条件重算或研究复核
  ↓ 提醒：“与你关注的科士达有关；发生了什么；依据与限制；可选动作”
  ↓ 用户回应：暂缓/继续观察/调整方案/暂停 → 反馈，不静默改写用户约定
```

关键产品语义：

- 「关注」可以只建立研究订阅，**不强制生成买卖方案**；
- 模型新提出的阈值、仓位上限、风险偏好修改属于**候选**，需用户明确采纳后生效；
- 研究发现与确定性条件是两种提醒来源，共用提醒决策，但**不能把模型分析包装成程序已证实的买卖信号**；
- 点击、接受不等于成交，实际操作单独记录。

### 2.3 前台五类能力

| 前台 | 需要稳定呈现 |
|---|---|
| 持仓与自选 | 当前事实、来源、修订与跟踪关系 |
| 聊天 | 已接受范围、已完成部分、具体缺口、下一次触发条件 |
| 用户框架 | 偏好、关注目的、判断、约定及其变更依据 |
| 框架验证与演进 | 候选与生效分开，显示验证范围和限制 |
| 通知 | 为什么此刻提醒、原委托、依据和可选操作 |

### 2.4 目标能力分层

| 层 | 清单 | 首期重点 |
|---|---|---|
| 基础工具 T01–T12 | 实体、用户事实、框架、行情、财务、披露、新闻、关系、历史证据、验证入口、业务命令 | 包装已有接口，统一身份、来源与输入输出 |
| 计算组件 C01–C12 | 覆盖、期间对齐、分位、回撤、相对表现、指标变化、估值位置、仓位暴露、事件匹配、三值组合、时间状态、提醒门槛 | 先做 C01/C03/C04/C09/C10/C11/C12 |

| 用户条件方案 P01–P05 | 历史位置、关键披露、持仓风险、到期复核、复合机会 | 先 P01 + P03 |
| 能力目录 | 工具、组件、流程的版本、Schema、权限、预算、生命周期、缺口 | 代码声明 + 存储发布版本 |

## 3. 现状盘点（基线）

### 3.1 产品与技术栈

- **产品形态**：Electron 桌面端「投研智能体」，本地单用户，三个独立 Python 服务：
  - `trading-core`（:8000）：分析、持仓、简报、回测、策略、影子、进化、KYC、通知；
  - `market-watch`（:8100）：盯盘、行情、新闻、事件、阈值告警；
  - `industry-chain`（:8200）：产业链图谱与研报抽取。
- **前端页面/路由**：研究工作台（`dashboard`）、智能分析（`analysis`）、实时盯盘（`opportunity`）、个股详情（`stock-detail`）、我的投研/组合（`portfolio`，主对话表面）、策略研究（`framework`）、自进化（`tasks`）、产业链（`knowledge`）、设置；通知中心与投研报告为顶栏弹层/抽屉。
- **调用契约**：浏览器只提交 `{ operation, input }`，由 Host 白名单映射到固定后端与路径；当前 `InvestmentDataOperation` 共约 104 项（trading-core 80、market-watch 14、industry-chain 10）。
- **后端路由**：trading-core 105 条（含通知 16、数据迁移 7），market-watch 33 条（含迁移 7），industry-chain 10 项 operation。

### 3.2 现有能力按域

| 域 | 现有实现 | 成熟度 |
|---|---|---|
| 持仓/自选/成交 | `holdings.json`、`trades.json`、`watchlist.json`；手工导入、券商同步、成交去重 | 较完整，单用户 |
| 风险与画像 | `risk_profile` 全局唯一事实源、KYC 问卷/解析/调整、行为画像、组合风险与预警 | 较完整 |
| 分析 | 多智能体 Graph（分析师 → 多空辩论 → 经理 → 交易员 → 风控）异步任务 + SSE | 较完整 |
| 简报 | 盘前/盘后/当前，LLM + 模板降级，按 `period+date` 幂等 | 较完整 |
| 策略闭环 | 事件 → 假设 → 候选入库 → 回测（样本内 70/30）→ active → 影子 → 自进化 | 较完整 |
| 事件 | market-watch 9 类事件、三方向、LLM + 规则降级、按自选/持仓命中 | 部分有 |
| 条件 | market-watch 阈值规则 + 持仓风险止盈止损（含版本/代际） | 部分有，二值 |
| 通知 | 统一通知中心：SQLite、幂等、去重、租约投递、退避、死信、多渠道 | 投递较强，决策较弱 |
| 任务 | 回测/影子 JSON 任务账本与重启恢复；分析/简报任务纯内存 | 部分有 |
| 存储 | `JsonStore` 原子写 + 文件锁；通知 SQLite | 单用户本地 |
| 能力目录 | 无；20 个 `tc_*` 工具（可选插件）+ 11 个默认投研工具 | 没有 |

### 3.3 现有实现的关键事实

- 聊天底层是通用 dsh 会话；投研侧仅有会话级上下文（`research_chat_contexts`：`strategy_id` + 单个 `instrument`），不是对话记忆，也没有跨会话委托。
- 后端不持久化聊天消息，对话历史由宿主侧维护。
- 策略「active」、回测完成、验证结论（`passed/not_passed/insufficient`）与用户采纳是不同概念，当前首次回测完成即无条件 `candidate → active`。
- 财务与估值只有「最新一期快照」；Tushare 基本面接口不可用、AKShare 路径为占位；无报告期、公告日、采集时间、PIT 历史序列与 PE/PB 分位。
- 新闻正文不落盘，事件无标准实体 ID、无披露时间、无内容哈希、无版本；`events_ledger` 是按 `type|direction` 聚合的符号池，不是逐事件账本。
- 产业链研报正文落盘，但无内容哈希、字符偏移、原始 URL 与抓取时间。
- 三套独立名称索引（行情、事件、产业链），无统一实体与别名表。

## 4. 差距分析

### 4.1 产品面差距

| 目标前台 | 现状 | 差距 |
|---|---|---|
| 聊天（主要协作入口） | 通用会话 + 投研工具 + 会话级策略/标的上下文 | 无跨会话记忆、无委托、无研究目标、无追问/主动续接 |
| 持仓与自选 | 持仓、成交导入、券商同步、自选、持仓风险 | 无账户作用域、无可靠事实变更事件、无委托/条件关联视图 |
| 用户框架 | 只有 KYC、风险画像、偏好复盘 | 无偏好字典与版本、无关注点及依据、无研究问题/判断/约定视图 |
| 框架验证与演进 | 策略回测、影子、自进化 | 缺判断复核、用户方案版本、用户采纳、实际操作关联 |
| 通知 | 统一通知中心，投递与已读归档完整 | 缺发送/抑制/延后决策记录、合并、静默、发送前复核 |
| 伙伴 IP / 主动发现 | 品牌与专家角色、定时简报 | 无状态驱动形象、无主动发起对话；主动发现不在首期 |

### 4.6 三个必须显式处理的语义冲突

1. **条件语义**：`market-watch/market_watch/rules.py` 当前把缺失字段过滤掉再做 AND/OR，AND 规则可能在必需项缺失时仍然触发，也没有「未知」状态。新方案必须：
   - AND：任一必需项为假 → 假；全部为真 → 真；其余 → 未知；
   - OR：任一项为真 → 真；全部为假 → 假；其余 → 未知；
   - NOT：未知仍为未知；
   - 执行错误独立保存，不混入「未知」。
2. **状态语义**：策略 `active`、回测任务完成、验证结论通过、用户采纳是四个不同状态。接入时分别映射，不能把自动激活当作「用户已采纳」。
3. **事件语义**：现有事件是「新闻抽取结果 + 自选/持仓命中」，不是「按委托依赖路由的业务事件」；同名 `events_ledger` 只是符号池，不能替代新事件总线。

### 4.7 可直接复用的资产

|---|---|
| 行情/新闻/事件/产业链采集 | 包装为 T04/T05/T07/T08/T09 连接器 |

### 5.2 B0 业务状态底座

**目标**：让委托、条件、任务、事件与提醒具备事务、版本、并发控制和恢复能力。

**功能点**

- 引入关系型存储与迁移机制（PG 为目标；本地部署形态需单独决策，见 §8）。
- 定义 Repository 接口，覆盖用户事实、委托、条件、任务、事件、证据、提醒、反馈。
- 所有私有对象带 `user_id`；本地部署也先写入固定用户标识，避免二次迁移。
- 业务写入与 `event_outbox` 同事务提交；跨存储（如通知 SQLite）使用可恢复日志 + 幂等消费者。
- 外键、唯一键、索引：用户归属、方案版本、任务去重键、事件幂等键。
- 服务端从认证上下文取 `user_id`；私有对象关联必须校验同一用户。
- 迁移：字段映射、数量与关键值核对、恢复演练、单写者切换、回退读取方案。

**验收**

- 业务写入后进程退出，事件可通过日志或对账恢复，不永久漏跟踪。
- 并发提交条件/偏好时 revision 冲突被拒绝并可重读。
- 跨用户引用对象被服务层与数据层同时拒绝。

### 5.3 B1 主数据与实体解析

**目标**：T01 提供唯一、可消歧、可追溯的实体身份。

**功能点**

- `entities`：公司、证券、发行主体关系、市场、板块、资产类型、上市状态。
- `entity_aliases`：简称、曾用名、英文名、常见错写。
- `source_mappings`：东财、新浪、baostock、tushare 等来源 ID 映射。
- T01 工具：名称/代码/链接 → 公司 + 证券 + 候选列表 + 置信度 + 歧义原因。
- 歧义时不默认取第一项，返回候选供确认。
- 事件、行情、策略、产业链、新闻统一引用标准实体 ID。
- 提供批量解析与反查接口，替换三套临时名称索引。

**验收**

- 用户名称有歧义时提供正确候选，不默选；已明确请求不丢失。
- 同一公司在事件、行情、图谱、委托中解析为同一实体。

### 5.4 B2 证据与数据契约

**目标**：让每个研究结论都能回到来源、时点与原文位置。

**功能点**

- `source_documents`：原始发布者、提供方、正文/片段、发布时间、采集时间、内容哈希、URL、存储引用、来源版本。
- `observations`：对象、原始值、标准值、单位、报告期、披露时间、采集时间、源记录 ID、连接器版本、质量状态、缺失项。
- `evidence_links`：支持/反驳/待核实、引用文档 ID 与偏移或段落。
- 统一数据 envelope：`as_of / coverage / missing_reason / source / version / quality`；缺失原因区分「未披露 / 获取失败 / 不支持 / 过期」。
- T04/T05/T08/T09 包装统一契约；行情保留专用序列存储。
- T07 拉取公告/新闻正文入库；无正文时明确「仅线索」。
- T10 历史证据检索：先精确 ID 与全文检索，向量检索只做派生索引。
- PIT 财务（P1）：`report_period / announce_date / collected_at / metric / value / source / revision`。
- 估值历史序列与分位（P1）：无历史披露时点数据时不做历史策略验证。
- 同一上游经不同接入路径取得的内容，按来源去重，不算两份独立证据。
- 共享数据与用户私有信息隔离；取消订阅后减少采集需求。

**验收**

- 任一研究发现可定位到文档、段落与采集时间。
- 同一材料转载不增加证据强度。
- 财务「当时可知」与「事后修订」可区分。

### 5.5 B3 委托与用户框架

**目标**：把「一句话」变成可暂停、可恢复、可追溯的跨会话目标。

**功能点**

- `research_mandates`：目标、范围、来源消息、状态、期限、revision。
- `mandate_subjects`：委托与实体关联；一个公司可同时存在学习与持仓管理两类目的。
- `research_questions`：问题、状态、完成条件、预算、恢复条件。
- `research_hypotheses` / `hypothesis_versions`：命题、支持、反证、适用范围、版本。
- `preference_definitions / user_preferences / preference_changes`：结构化偏好、Schema 版本、校验器、来源消息、确认时间、过期时间、revision。
- `user_interests / interest_evidence`：关注目的、explicit/inferred、候选/生效/暂停/撤销、依据。
- `framework_revisions`：变更对象、依据、采纳记录。
- T03 读取接口：委托 → 偏好、关注、问题、方案、版本。
- 模型提议但未确认的变更存为业务命令草案或提案，不直接覆盖当前值。
- 用户纠正关注目的后撤销相应推断并刷新派生索引；卖出不自动代表不再关注。

**验收**

- 跨会话可以继续原研究，且能回答「为什么关注这家公司」。
- 推断关注可衰减，用户确认的关注不因近期未点击被撤销。
- 偏好过期停止应用但保留历史。

### 5.6 B4 意图、命令与能力目录

**目标**：限制模型输出边界，明确「能做什么、缺什么」。

**功能点**

- 意图 Schema：对象、需求类型、持续性、槽位、原话片段；服务端补 `user_id`，模型不能编造内部 ID。
- 实体解析与能力检查串联：可执行部分、受阻部分、具体缺口。
- 业务命令层（T12）：创建/暂停/恢复委托、采纳候选条件、修改偏好；统一校验、幂等键、权限、写入后事件。
- `capability_definitions / capability_versions / capability_gaps`：
  - `capability_id` 与版本；`kind`（工具/组件/流程/受控模型步骤）；
  - 输入输出 Schema；适用范围与依赖；读写权限与副作用；
  - 超时、次数、成本预算、重试类型；
  - 生命周期（草案/试验/已发布/退役）与测试证据；
  - 缺口类型（缺数据/缺工具/缺方法/用户含义不清）与恢复条件。
- 能力目录是模型候选集的唯一来源；「计划开发」不能作为可执行工具暴露。
- 模型输出与证据不符时拒绝提交判断，保留错误与复核记录。

**验收**

- 模型生成不存在的工具时调用被拒绝，登记能力缺口，不伪造成功。
- 只支持部分需求时，已支持任务继续，缺口有具体恢复条件。

### 5.7 B5 研究执行与持久任务

**目标**：研究可以跨进程、跨重启、按预算继续。

**功能点**

- `research_jobs / research_job_steps`：
  `mandate_id、plan_version_id、trigger_event_id、input_snapshot_id、capability_version、status、next_run_at、lease_token、lease_expires_at、attempt_count、checkpoint、budget、last_error、cancel_generation`。
- 状态机：Pending / Running / WaitingData / WaitingUser / Paused / Failed / Completed / Cancelled。
- 租约：领取、续租、过期回收；持过期租约者不能提交状态。
- 检查点：从步骤恢复，避免重复业务副作用。
- 预算：达到后保存部分结果与具体恢复条件，不自动重复整份分析。
- 任务去重键：事件 + 节点版本 + 范围；消息至少一次，处理必须幂等。
- 暂停/取消优先于重试；取消代数递增，旧结果只留历史。
- R01：T01–T05，按覆盖补 T06–T09；C01/C03/C04；产出身份、历史基线、问题清单、研究订阅。
- R02（P1）：T07/T08/T10，必要时 T06；C01/C02/C06/C09；产出相对旧判断的新增支持、反证、待核实项。
- R03（P1）：T02/T03/T05；C08/C10–C12；产出条件结果、风险与提醒候选。
- 无新证据时安静结束并更新恢复条件；模型失败时确定性结果仍保存。
- 长期受阻时提出替代指标、缩小问题、暂停或结束的具体方案。

**验收**

- Worker 中途退出后从检查点恢复，无重复业务副作用。
- 应用重启后委托与任务状态可查，暂停立即停止新调度。
- 达到预算后保留部分结果与恢复条件。

### 5.8 B6 计算组件

**首期实现**

- **C01 覆盖与新鲜度**：必需字段、时点、有效期 → 覆盖与缺失原因；未披露/获取失败/不支持/过期分别返回。
- **C03 价格分位**：同口径历史序列与窗口 → 分位与样本量；固定并列值规则、最小样本、修订行为。
- **C04 回撤与持续时间**：当前与历史回撤；明确价格回撤或组合净值回撤。
- **C09 事件与关系匹配**：标准实体 + 事件类型 + 关系路径 → 命中记录与理由；关联只触发复核，不推出经营影响。
- **C10 三值条件组合**：AND/OR/NOT + 未知传播；执行错误独立保存。
- **C11 时间窗口与状态转换**：交易日历、持续满足、首次进入、重新进入；处理迟到与修订事件。
- **C12 重复与提醒门槛**：变化前后、已提醒状态 → 发送/抑制/延后理由；冷却、静默、失效、版本检查可测试。

**后续**

- C05 相对表现（基准、比较期、交易日、收益口径一致）。
- C08 仓位与暴露（区分成本/市值、证券资产/总资金；缺失不猜）。
- C02 期间对齐与单位转换（不混用单季与累计、合并与母公司）。
- C06 指标变化（分母为零、负数、不可比时明确不适用）。
- C07 估值位置（无历史时点数据不做历史策略验证）。

**验收**

- 两个必需条件中一个缺失时，AND 不得宣布满足，缺失原因可追溯。
- 风险未知不能被当作「已排除风险」。

### 5.9 B7 条件方案

**功能点**

- `condition_plans / plan_versions / plan_evaluations`：版本不可原地改写，评估关联输入快照与能力版本。
- 条件节点是程序配置：方法 ID、版本、输入、输出字段、比较符、阈值、参数校验。
- 早期使用有限节点集合；复杂方案编译后置。
- 方案生效要求：方法可用、数据覆盖、参数合法、用户明确约定；缺少判断时不得宣布整体满足。
- 依赖生成器：由流程与组件声明生成 `tracking_dependencies`，模型不临时猜关联。
- P01 历史位置观察：价格分位或回撤进入约定范围；提示观察条件满足，不称为买点。
- P02 关键披露复核：公司发布某类材料或指标变化；先触发研究，不直接判断利好利空。
- P03 持仓风险检查：持仓可信、阈值与作用范围明确；返回依据与可选动作。
- P04 到期研究复核：到期检查证据与问题；无变化安静留痕。
- P05 复合机会观察：仅支持已实现条件；必需判断未知时不宣布整体满足。
- 方案与通用策略分开存储；关注兴趣不能直接生成买卖方案；回测通过不代表用户采纳。

**验收**

- 方案版本不可被原地覆盖；评估结果可回溯到输入快照。
- 条件成立不等于立即交易；用户未采纳的方案不产生提醒。

### 5.10 B8 事件与追踪 Core

**功能点**

- `domain_events`：标准事件、来源、主体、事件类型、指标、披露时间、采集时间、证据引用、版本。
- `event_keys`：`event_id、subject_id、event_type、feature_key`。
- `tracking_dependencies`：`user_id、mandate_id、可选 plan_version_id、node_id、subject_id、event_type、feature_key、scope_key、active、rule_version`。
- `event_matches / event_consumptions`：匹配类型、关系路径、理由、消费状态与错误。
- `event_outbox`：业务提交侧可靠发布。
- 依赖来源：价格位置组件、财务变化组件、披露复核订阅、持仓条件、到期复核、关系研究。
- 事件身份：优先结构化来源字段；自由文本经名称抽取、别名查询、消歧得到候选实体；不确定匹配保留原文片段与原因，进入研究队列。
- 关系扩展限定类型、方向、有效期、最大层数，保存具体路径。
- 增量游标 + 补偿检查；迟到/修订事件保存原版本并重评受影响节点。
- 关系增加/修订/失效时发送关系变更事件并重建依赖。
- 改造 `market-watch`：结构化事件补齐实体 ID、披露时间、采集时间、内容哈希；现有 9 类作为事件类型映射子集。
- 语义候选（政策、行业新闻）先进入研究候选，核实前不触发机会提醒。
- 记录已知漏报与召回评估；正常增量匹配与定期复核配合。

**验收**

- 同一事件重复或迟到时幂等处理，修订触发正确重评。
- 关联关系新增或撤销后，依赖同步更新，旧路径失效。
- 行业新闻仅语义相似时先作为候选，不直接触发机会提醒。

### 5.11 B9 提醒决策

**功能点**

- `notification_decisions`：关联评估、变化前后、用户与方案版本、发送/抑制/延后理由、去重键、暂缓时间、失效时间。
- 处理档位：安静记录 / 汇总 / 轻敲 / 风险提醒 / 能力或数据问题。
- 重复规则：首次进入、显著变化、重新进入、约定升级。
- 冷却、静默时段、暂缓（snooze）、跨设备去重为程序配置。
- 发送前检查：委托、方案、权限、数据时效、用户暂缓状态。
- 风险检查独立运行；机会方案要求风险门槛时，风险未知不等于已排除。
- 每条主动提醒回答：与哪项委托有关、发生了什么、依据与限制、可选动作。
- 与现有通知中心对接：通知中心继续负责渠道投递、重试、死信；决策层只负责是否发送、何时发送、合并到哪条。
- 用户可见「为什么没发」的解释字段。

**验收**

- 用户暂停后，旧任务完成不覆盖新状态、不进入新投递。
- 同一条件重复成立时按规则抑制或合并，不无限催促。
- 通知失败重试不重复执行评估。

### 5.12 B10 反馈与演进

**功能点**

- `user_responses`：回应类型、来源通知/聊天、时间；未回应不算接受。
- `action_links`：用户确认、直接操作关联、系统推测分别标识；真实成交、手工记录、影子交易、资产修订分开。
- `validation_runs`：统一索引现有回测/影子结果，不建第二套回测系统。
- `outcome_reviews`：判断复核（当时命题、后续事实、支持/反证）。
- `improvement_proposals`：候选改进、验证范围、采纳记录。
- 四类评价分离：投资判断、策略与执行、用户框架、提醒效果。
- 定性研究用当时判断与后续披露复核，不强行套用收益回测。
- 数值策略使用同口径历史、样本外与影子验证；缺少历史可得数据时只做前向观察。
- 共享能力更新保留实现与模型版本；新版本影响既有语义时提出迁移候选。
- 保留失败候选与基线，避免只展示最优者。

**验收**

- 用户接受建议但无交易记录时，只记录回应，不产生虚构成交或收益。
- 用户纠正关注目的后，当前关注与派生索引更新，不自动改变持仓。

### 5.13 B11 API 与工具契约

**新增 operation 域（发布后视为兼容契约）**

| 领域 | 建议 operation |
|---|---|
| 委托 | `trading-core.mandates-list/get/create/update/pause/resume/close` |
| 研究问题 | `research-questions-list/create/update` |
| 假设 | `research-hypotheses-list/get` |
| 研究执行 | `research-runs-create/status/cancel` |
| 研究订阅 | `research-subscriptions-list/create/pause/cancel` |
| 条件方案 | `condition-plans-list/get/create/update/archive` |
| 方案版本 | `plan-versions-list/get/activate` |
| 方案评估 | `plan-evaluations-list` |
| 用户框架 | `preferences-get/update`、`interests-list/create/update`、`framework-revisions-list` |

**接入要求**

- 在 `InvestmentDataOperation` 增加稳定 operation，在 Host broker `SPECS` 建立固定映射与 input 白名单。
- 写请求只重建允许字段，不整包透传；成功、失败、取消路径均释放 lease。
- **必须重跑 `build:lib:host` 与 `build:lib:client`**，否则一侧白名单会静默拒绝。
- 模型工具从能力目录生成候选集，替换当前分散的手写工具清单。
- 长任务统一 `job_id → 状态 → 结果 → 可选 SSE`，并提供重启后查询。
- 新增端点补成功、空数据、非法参数、上游失败、超时与重复提交测试。

### 5.14 B12 迁移与兼容

- 保留现有持仓、自选、会话、策略、通知 ID，增加委托与方案关联。
- 旧聊天不批量变为已确认约定；旧 active 策略不自动绑定用户；旧行为不推导新风险偏好。
- JSON、SQLite 与新库过渡期通过可靠日志和幂等消费者交接，不采用无恢复机制的双写。
- 新写入方启用前完成字段映射、数量与关键值核对、恢复演练和单写者切换。
- 回退：停新调度、取消待发送业务、保留新记录、按兼容方案读取，不丢弃新用户数据。
- 现有 `data_transfer` 快照迁移保留，但需补 collection/schema 演进与字段级迁移。

### 5.15 B13 可观测与降级

- 观测指标：来源新鲜度、解析失败、任务积压、租约恢复、缺口持续时间、被抑制原因、重复投递、模型成本。
- 模型不可用时：数值规则、到期检查、任务恢复、通知去重继续运行；语义分析明确进入等待。
- 先安静运行验证事件匹配、计算与提醒决策，再按用户或委托开启主动通知。
- 系统任务日志进入运维渠道，不直接转换为用户提醒。
- 健康检查继续校验服务身份；就绪快照补充新能力档位。

## 7. 分期实施与验收

### 7.1 阶段划分

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| **P0 基础闭环** | B0、B1、B3、B4、B5（仅 R01）、B6（C01/C03/C04/C10/C11/C12）、B7（P01）、B8（最小依赖路由）、B9、B11、B12 | 一个真实样例跨会话跟踪；重启恢复；暂停有效；证据可追溯；AND 缺一项不误判；模型不可用仍能跑数值条件 |
| **P1 研究扩展** | T06 PIT 财务、T07 正文证据、R02、R03、P02/P03/P04、B10 反馈 | 材料可定位；未知处理正确；已知事件召回可测；判断有支持与反证 |
| **P2 验证演进** | 策略/判断与个人方案绑定、前向观察、候选比较与采纳、失败基线 | 结果有版本与基线；不静默覆盖用户约定；采纳与成交分离 |
| **P3 主动发现** | 固定来源筛选、兴趣匹配、摘要与拒绝反馈 | 候选与目标相关；新增价值可测；额外打扰受控 |

### 7.2 P0 工程验收用例

| 用例 | 应观察到的结果 |
|---|---|
| 用户名称有歧义 | 提供正确候选，不默选；已明确请求不丢失 |
| 模型生成不存在的工具 | 调用被拒绝，保存能力缺口，不伪造成功 |
| 只支持部分需求 | 已支持任务继续，缺口有具体恢复条件 |
| 两个必需条件中一个缺失 | AND 不得宣布满足，缺失原因可追溯 |
| 行业新闻仅语义相似 | 先作为候选，未核实前不直接触发机会提醒 |
| 同一事件重复或迟到 | 幂等处理，修订触发正确重评 |
| 关联关系新增或撤销 | 依赖同步更新，旧路径失效 |
| 用户暂停且旧任务随后完成 | 旧结果不覆盖新状态，不进入新投递 |
| Worker 中途退出 | 租约与检查点恢复，无重复业务副作用 |
| JSON/资产提交后事件发布失败 | 日志或对账恢复事件，不能永久漏跟踪 |
| 模型服务关闭 | 已有数值与时间规则继续运行，语义任务明确等待 |
| 通知失败重试 | 评估不重复执行，渠道尝试可追溯 |
| 用户接受建议但无交易记录 | 只记录回应，不产生虚构成交或收益 |
| 用户纠正关注目的 | 当前关注及派生索引更新，不自动改变持仓 |
| 跨用户引用对象 | 服务与数据访问检查拒绝，公共材料复用不泄露私有事实 |
| 页面与 IP 状态 | 展示真实进度，停止时退出动作，可从通知回到原研究 |

### 7.3 模型与投研效果验收

- 固定真实口语样例、歧义样例、缺数据样例、反证样例、能力不支持样例；保留不参与调优的测试集。
- 分别测量：意图正确率、实体正确率、无效工具调用、证据提取准确性、反证遗漏、任务完成度、单位委托成本。
- 提醒评估：相关性、及时性、重复与打扰、已知重要事件漏报；明确分母、标注标准与观察窗口。
- 不能只统计点击率或用模型自评发布新能力。
- 新数据源、计算组件、研究流程在固定问题和其他条件不变时比较增益。

## 8. 关键决策与风险

### 8.1 进入实施前需要拍板

| # | 问题 | 备选与建议 |
|---|---|---|
| 1 | PG 的部署形态 | 云端 PG（多用户，最符合文档）/ 本地托管 PG / SQLite 同构。建议先定 Repository 接口，云部署用 PG、本地桌面用同构 SQLite，业务代码不绑定方言；若坚持 PG，需先确定本地承载与升级方案。 |
| 2 | 多用户是否进入首期 | 文档所有表都有 `user_id`。建议即使本地单用户也先写入固定用户标识与账户字段。 |
| 3 | 首条闭环范围 | 建议「个股委托 + R01 + P01 + 一类数值条件 + 提醒 + 回应」。 |
| 4 | 数据承诺边界 | 财务 PIT 与估值分位是最大短板；首期只承诺行情/价格/量能/公告线索，不承诺完整经营判断。 |
| 5 | 后台运行边界 | 本地应用关闭即停止跟踪，不能承诺持续服务；7×24 需要服务端部署。 |
| 6 | 提醒默认策略 | 默认频率、静默时段、风险升级、合并窗口、跨设备去重。 |
| 7 | 模型基线与成本 | 固定任务集、质量阈值、降级方案与预算。 |

### 8.2 主要风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 数据覆盖不足 | 财务 PIT、估值历史、公告正文缺失会让「研究结论」退化为行情分析 | 首期明确能力边界；C01 每次返回覆盖与缺失原因 |
| 事件召回不完整 | 增量游标窗口、LLM 抽取漏报 | 人工标注事件集、已知漏报登记、定期有限复核 |
| 模型输出不可控 | 意图/实体/材料提取错误 | 输出 Schema 校验、证据回指、有限修复、能力目录白名单 |
| 存储迁移风险 | JSON/SQLite 与新库并存 | 单写者切换、可靠日志、对账补偿、回退演练 |
| 提醒打扰 | 条件频繁成立、重复事件 | C12 决策层、冷却/静默/合并、发送前复核 |
| 用户约定被静默改写 | 模型或进化直接改偏好/方案 | 候选与生效分离，变更需用户采纳，保留 revision 历史 |
| 任务重复副作用 | 至少一次投递与重启恢复 | 幂等键、租约、检查点、取消代数 |
| 本地部署限制 | 宿主关闭后无法跟踪 | 部署形态与服务承诺一起确定，向用户明确说明 |
