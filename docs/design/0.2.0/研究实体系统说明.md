## 0. 一页结论

研究实体系统解决的是“**把用户的自然语言投研问题，稳定地变成一组可执行的工具调用，并把结果留成可回放的证据和可引用的报告**”。

它的处理链固定为五段：

```
自然语言问题
  → 意图识别 + 实体抽取
  → 实体消歧（落到 entity_id）
  → Scope（研究范围：主体/主题/约束/待执行工具）
  → 工具执行（授权、缓存、证据落库）
  → 报告（确定性模板 或 大模型撰写 + 引用校验）
```

关键设计取舍：

1. **实体与意图解耦**：意图决定“要回答什么问题”，实体决定“针对谁”。同一问题可以同时命中多个意图。
2. **不猜、不编**：无法消歧就返回候选和澄清问题；数据源不可用就标记 `unavailable`；没有可靠数据源的工具明确标为 `unconfigured`，不用相近指标冒充。
3. **证据先行**：报告只能引用已落库证据；大模型输出必须通过引用与数字校验，否则回退到确定性报告。
4. **主数据有来源、有年龄**：每个实体带 `source` 与 `last_verified_at`，每次导入写 `source_imports`；过期数据会在 Scope 里显式告警。
5. **前端尚未接入**：截至 2026-10-20，研究实体是独立服务（:8300），Electron 前端没有 `research` backend ID、没有对应 operation、没有页面。第 11 章给出完整接入方案。

## 1. 系统定位与边界

### 1.1 它负责什么

| 能力 | 说明 |
| --- | --- |
| 实体主数据 | 维护 20 类研究实体（证券、公司、行业、主题、资金风格、宏观大宗）的名称、别名、标识、关系与来源 |
| 实体识别 | 从中文问题里找出实体提及（trie 词典 + 代码模式 + 动态集合） |
| 实体消歧 | 在多个候选中选择，或返回候选让用户确认 |
| Scope 构建 | 把问题整理成结构化研究范围：意图、实体、角色、时间/市场约束、待执行工具 |
| 工具编排 | 按实体类型与意图预加载 45 个逻辑工具，按依赖与必需性排序 |
| 工具执行 | 统一授权、超时、缓存、异常归一化、证据落库、审计 |
| 证据回放 | 任意 `request_id` 可回看当时执行了哪些工具、拿到什么、缺什么 |
| 报告生成 | 确定性模板报告；可选 DeepSeek 辅助撰写并做引用/数字校验 |
| 主数据维护 | CLI/API 导入、定时刷新、新鲜度查询、过期告警 |

### 1.2 它不负责什么

- **不做交易**：不生成买卖指令、不连接券商、不写策略引擎。
- **不是行情网关**：实时行情、资金流等由工具调用外部公开接口或兄弟服务，研究实体只做编排与留证。
- **不替代市场盯盘服务**：事件监控规则写入依赖 market-watch（:8100），本系统只发起和记录。
- **不做前端渲染**：只输出 JSON/Markdown；页面交互由前端实现（当前尚未接入）。
- **不虚构实体**：实体只能来自已登记数据源；词典没有的公司/行业不会被“推测”出来。

### 1.3 运行形态

```
Electron 前端（当前未接入）
        │  （未来）requestData({ operation, input })
        ▼
investment Python runtime / Host operation 白名单
        │
        ▼
research_entities (FastAPI, 127.0.0.1:8300)
        ├── SQLite: data/research_entities.sqlite3
        ├── industry-chain (127.0.0.1:8200)   ← 产业链关系
        ├── market-watch  (127.0.0.1:8100)   ← 事件流/监控
        ├── akshare / 新浪 / 东财 / 巨潮 / 同花顺 / 政府网（公网数据）
        └── DeepSeek（仅 llm 模式报告，可选）
```

## 2. 核心概念

| 概念 | 模型 | 含义 |
| --- | --- | --- |
| Intent | `IntentItem` | 研究意图，如“个股分析”“行业研究”。一个问题可命中多个，按置信度排序，取前 3。 |
| Entity Type | `EntityTypeDef` | 静态实体类型（20 个），决定归一化键与默认工具。 |
| Entity / EntityInstance | `EntityInstance` | 一个具体研究实体，如 `SEC:CN:A:600519`。 |
| Mention | `EntityMention` | 问题中一次实体提及，含原文、偏移、候选与解析状态。 |
| Collection | `EntityCollection` | 动态集合（持仓、自选、可比组、任务生成集），成员来自运行时授权数据。 |
| Scope | `ResearchScope` | 一次研究的完整范围与执行计划，是工具层与报告层的输入。 |
| Tool | `ToolDefinition` | 逻辑工具（45 个），描述能力、可用性、授权要求与适用实体类型。 |
| Evidence | `EvidenceItem` / `EvidenceBundle` | 工具执行留下的可回放结果与缺口汇总。 |
| Report | `ReportDraft` | 基于证据生成的结构化报告，含章节、引用、缺口、告警。 |

### 2.1 状态语义（必须区分）

**Scope 状态**（`ResearchScope.status`）：

| 状态 | 含义 | 前端应有的行为 |
| --- | --- | --- |
| `scope_ready` | 实体全部解析且无阻塞问题，可执行 | 允许“开始研究” |
| `pending_clarification` | 存在歧义/授权等需要用户回答的问题 | 展示 `clarification_questions` |
| `pending_entity_resolution` | 实体未解析或有阻塞项，但没有可回答的问题 | 展示候选，让用户选择 |
| `scope_incomplete` | 问题中没识别出任何实体 | 引导用户补充标的/行业 |

**工具可用性**（`ToolDefinition.availability`）：

| 值 | 含义 | 实际行为 |
| --- | --- | --- |
| `configured` | 有可执行处理器 | 正常执行；失败按状态归一化 |
| `external_service` | 依赖兄弟服务在线 | 服务未启动时返回 `unavailable`，不伪造 |
| `unconfigured` | 无可复现数据源 | 返回明确原因（当前仅 `supply_demand_lookup`） |

**证据状态**：`ok` / `empty` / `unavailable` / `error` / `needs_authorization`。

**来源新鲜度**：`fresh` / `stale` / `never_imported` / `failed`。

### 3.1 分层（六边形）

```
│  disambiguator.py（消歧）       │ toolbox/registry.py（处理器） │
│  normalizer.py / merge.py      │ toolbox/context.py（外部调用）│

                │                              │

│ storage_sqlite / storage_memory│ │ akshare / 新浪 / 东财 ...  │

└───────────────────────────────┘
```

组合根是 `factory.py`：唯一知道“当前用 SQLite、词典在哪、要不要联网”的地方。上层只依赖 `ports.py` 的协议。

### 3.2 一次 `/research/run` 的完整生命周期

1. **解析 Scope**（`ResearchEntityService.resolve_scope`）
   - 意图分类（关键词权重 + 组合规则）
   - trie 实体抽取 + 代码正则 + 动态集合触发
   - 每个 mention 检索候选 → 消歧 → `resolved` / `ambiguous` / `unresolved`
   - 由“实际解析出的实体”反推实体类型集合
   - 检查实体来源是否过期，生成 `stale_source_warnings`
   - 工具预加载（类型默认工具 ∩ 意图工具，过滤类型不兼容项）
   - ScopeBuilder 分配角色、提取时间/市场约束、判定状态
   - 持久化 scope / mentions / audit
2. **执行工具**（仅当 `scope_ready`）
   - 按预加载计划取 `configured` 工具，去重
   - 需要授权的集合工具只有在 `authorized` 时加入
   - 线程池并行执行（默认 4 worker）
   - 每个工具：授权检查 → 缓存查询 → 处理器调用 → 状态归一化 → 写证据 → 写审计
3. **汇总**
   - `summarize_results()` 统计各状态数量
   - `evidence_bundle(request_id)` 汇总证据与缺口
4. **报告**（独立请求）
   - 读取该 request 的所有证据
   - `deterministic`：模板化章节
   - `llm`：DeepSeek 输出 JSON → 校验引用与数字 → 不合格回退
   - 持久化报告，可导出 Markdown

### 4.2 动态集合（不是实体类型）

| 集合 | 名称 | 授权 | 默认工具 | 成员来源 |
| --- | --- | --- | --- | --- |
| `USER_PORTFOLIO` | 用户持仓 | 需要 | portfolio_lookup, portfolio_risk_analysis | 授权后的持仓 JSON |
| `USER_WATCHLIST` | 用户自选 | 需要 | watchlist_lookup, event_monitor_setup | 授权后的自选 JSON |
| `DYNAMIC_COMPARABLES` | 动态可比对象 | 不需要 | peer_group_builder, benchmark_lookup | 按行业/规模规则生成 |
| `TASK_GENERATED_SET` | 任务生成集合 | 不需要 | — | 当前研究过程筛选结果 |

动态集合被识别时会作为 `constraints`/工具来源进入 Scope，而不会成为静态实体。本地集合适配器**只读取实际存在且可读的文件**，文件不存在就返回空，绝不编造成员。

### 4.4 实体字段

`EntityInstance` 主要字段：

- `entity_id`、`entity_type_code`、`canonical_name`
- `aliases`（别名/法定名称/简称）
- `identifiers`（代码、交易所、板块等）
- `attributes`（上市日期、法人代表、经营范围等，因类型而异）
- `relations`（与其它实体的关系：上市主体、子公司、上下游等）
- `status`：`active` / `inactive` / `merged` / `imported_unverified`
- `source`：`<source_id>:<version>`，用于追溯
- `last_verified_at`

### 4.5 存储

默认 SQLite（WAL 模式）：

- `PRAGMA journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`
- 写事务使用 `BEGIN IMMEDIATE`，支持嵌套事务深度计数
- 迁移按文件名顺序执行，记录在 `schema_migrations`
- `meta` 表保存 `index_version`，索引失效时重建

表结构：

| 表 | 用途 |
| --- | --- |
| `entity_types` | 类型注册表落库 |
| `entities` | 实体主表（名称、状态、来源、核验时间） |
| `entity_aliases` | 别名，带索引用于检索 |
| `entity_identifiers` | 代码/交易所等标识，联合索引 |
| `entity_relations` | 实体关系（from/to/type/方向） |
| `entity_collections` / `collection_members` | 动态集合及成员 |
| `scope_requests` | 每次 Scope 解析的原始问题、状态、结果 JSON |
| `mentions` | 实体提及与解析结果 |
| `audit_events` | 审计事件（敏感键脱敏） |
| `evidence_items` | 工具证据（含原始数据、状态、耗时、缓存命中） |
| `reports` | 报告 JSON 与元信息 |
| `source_imports` | 每次导入的来源、版本、数量、状态、告警、错误、时间 |

`RESEARCH_ENTITIES_STORAGE=memory` 使用内存仓储，仅用于测试与临时演示；`postgres` 会明确报“尚未实现”，不会静默降级。

### 4.6 导入、合并与溯源

导入流程（`ResearchEntityService.import_source`）：

1. 调用数据源 `fetch_entities()` 得到 `SourceBatch`（记录、版本、抓取时间、告警）
2. `records_to_entities()` 归一化并派生 `entity_id`
3. 按 `entity_id` upsert；`merge.py` 合并别名/标识/属性/关系
4. 状态只升不降：`imported_unverified` 不会覆盖已有的 `active`
5. 写审计事件
6. 成功写一条 `source_imports`（`status=success`，含 `imported_count` 与 `warnings`）
7. 失败时先写 `status=failed` 的导入记录，再抛错；**上一份成功数据保持不变**

所有实体都带 `source`（来源+版本），因此可以回答“这条数据是谁、什么时候导入的”。

## 5. 从自然语言到 Scope

### 5.1 意图识别

17 个意图（含兜底 `GENERAL_RESEARCH`）：

`STOCK_ANALYSIS`、`INDUSTRY_RELATION_ANALYSIS`、`INDUSTRY_RESEARCH`、`COMPANY_COMPARISON`、`THEME_RESEARCH`、`POLICY_CATALYST_SEARCH`、`PORTFOLIO_ANALYSIS`、`PORTFOLIO_RISK_ANALYSIS`、`MACRO_SCENARIO_ANALYSIS`、`EVENT_ANALYSIS`、`DISCOVERY_SCREENING`、`QUOTE_CHECK`、`COMPANY_RELATION_ANALYSIS`、`COMPANY_GOVERNANCE_ANALYSIS`、`CAPITAL_FLOW_ANALYSIS`、`BENCHMARK_ANALYSIS`、`GENERAL_RESEARCH`。

规则：

- 关键词带权重，支持组合规则（如“行业 + 代表公司”同时抬升行业研究与个股分析）
- 置信度 `min(0.95, 0.45 + 0.12 × 原始得分)`
- 返回前 3 个意图，按置信度降序
- 没有任何命中时回退 `GENERAL_RESEARCH`

意图与实体相互独立：意图不绑定实体，实体也不决定意图。

### 5.2 实体抽取

三路来源：

1. **词典 trie**：`resources/gazetteers.json` 覆盖 11 类词条（行业、主题、产业链、政策、宏观、商品、区域等），支持别名
2. **代码模式**：6 位股票代码、6 位基金代码、指数代码、可转债代码，带交易所推断
3. **动态集合触发词**：“我的持仓”“自选”“对比同行”等，触发集合而非实体

抽取结果保留 `raw_text` 与在原文中的偏移，供前端高亮和用户确认。

### 5.3 检索与消歧

对每个 mention：

1. `retriever` 按精确名称、别名、标识代码、相似度检索候选
2. `disambiguator` 结合类型、来源、上下文角色排序
3. 判定：
   - 唯一高置信 → `resolved`
   - 多候选且无法区分 → `ambiguous`，返回候选列表
   - 无候选 → `unresolved`
4. `EntityMention` 模型强校验：偏移合法、`resolved` 的实体必须属于候选集合

同一实体多次提及时会去重合并，保留最高置信度与最具体角色。

示例（真实响应摘录）：

```json

      "mention_id": "MENTION_001",
      "entity_id": "SEC:CN:A:600519",
      "entity_type_code": "ENTITY_01_01",
      "raw_text": "贵州茅台",
      "role": "primary_subject",
      "resolution_status": "resolved",
      "confidence": 0.98,
      "canonical_name": "贵州茅台"
    },
    {
      "mention_id": "MENTION_002",
      "entity_id": "IND:CN:白酒Ⅱ",
```

### 5.4 角色与约束

角色由实体类型决定：

| 角色 | 典型类型 |
| --- | --- |
| `primary_subject` | A股股票、上市公司 |
| `research_theme` | 行业、主题、产业链、趋势、政策、区域 |
| `benchmark` | 指数、可比基准、市场风格 |
| `event` | 公司事件、宏观事件 |
| `macro_factor` | 宏观因子、大宗商品 |

约束提取：

- **时间范围**：正则识别“近 3 天”“过去一个月”“2025 年以来”等
- **市场范围**：A股 / 港股 / 美股（默认按实体推断）
- **其它约束**：动态集合、比较对象等

### 5.5 状态与告警

状态判定顺序：

1. 没有任何 mention → `scope_incomplete`
2. 有 `ambiguous`/`unresolved` 且能生成澄清问题 → `pending_clarification`
3. 有阻塞项但无可回答问题 → `pending_entity_resolution`
4. 全部解析且无阻塞 → `scope_ready`

模型层硬约束：`scope_ready` 不允许同时存在未解析实体或澄清问题。

告警来源：

- 实体来源已过期（见第 8 章），如“主数据来源 akshare_security 已 10 天未刷新…”
- 最新刷新失败且上次成功也已过期：“刷新失败…当前使用上一次成功导入的数据”
- 实体来自未核验的本地证券名称表
- 意图工具与实体类型不兼容而被过滤

真实响应中的告警示例：

```json
"warnings": [
  "行业研究的工具 theme_lookup 与当前实体类型不兼容，未挂载",
  "行业研究的工具 industry_chain_lookup 与当前实体类型不兼容，未挂载",
  "部分实体来自未核验的本地证券名称表，标准名称与关系尚未核验。"
]
```

### 5.6 工具预加载

`tool_preloader.py` 的合并规则：

1. 每个已解析实体类型的 `default_tool_ids`
2. 每个命中意图的 `required_tool_ids` 与 `optional_tool_ids`
3. 取并集后过滤：工具声明的 `supported_entity_types` 必须与当前实体类型有交集（空表示不限制）
4. 动态集合授权后追加其默认工具
5. 排序：必需工具优先，其次按注册顺序
6. 每个工具生成原因（`reason`）、必需性（`required`）、挂载实体、状态与执行模式

`execution_mode` 当前为 `preload_only`：Scope 阶段只规划，不执行；执行由 `/research/run` 或工具接口显式触发。

### 6.3 执行流程

`ToolExecutor.execute_tool()`：

1. **注册校验**：未知工具直接报错；`unconfigured` 返回明确原因
2. **授权闸门**：`requires_authorization` 且未传 `authorized=true` → `needs_authorization`，不访问任何数据
3. **缓存**：按工具 TTL 查进程内缓存；命中则保留原始 `fetched_at` 并标 `cache_hit=true`
4. **实体加载**：从仓储读取 `entity_ids`，转换为工具参数
5. **处理器调用**：`toolbox/registry.py` 的 `HANDLERS` 映射到 `bond/equity/fund_index/local/macro/service` 处理器
6. **异常归一化**：
   - 数据源不可达/超时/接口缺失 → `unavailable`
   - 无记录 → `empty`
   - 未预期异常 → `error`（带类型与消息，不外泄堆栈）
7. **写缓存**（不可缓存工具除外）
8. **`_finish`**：补耗时、写审计、写证据（含 `source`、`record_count`、`warnings`、`error`、`authorization`）

`execute_for_scope()` 额外规则：

- 只执行预加载计划中 `status=configured` 的工具
- 按 `(tool_id, 实体集合)` 去重
- 需要授权的集合工具只有 `authorized=true` 才加入
- 没有预加载计划时，回退到实体类型的默认工具

并行度默认 4（`max_workers`），可通过构造参数调整；第三方库调用在 `ToolContext` 内串行化，避免线程安全问题。

### 6.4 缓存

- 进程级 `TTLCache`，最大 512 条
- 每个工具独立 TTL（行情类较短，主数据类较长）
- `NON_CACHEABLE_TOOLS` 不缓存（如持仓、监控写入、官方文件检索）
- 缓存键包含工具 ID、实体 ID 集合与规范化参数
- `/health` 返回 `cache.entries/hits/misses`

| 依赖 | 用途 | 不可用时的行为 |
| --- | --- | --- |
| akshare | 行情、财务、基金、指数、宏观、商品、库存 | 工具返回 `unavailable`，证据记录原因 |
| 新浪 / 东方财富 / 中证指数 | 行情与指数 | 主备切换 |

## 7. 报告层

### 7.1 两种模式

| 模式 | 实现 | 特点 |
| --- | --- | --- |
| `deterministic` | `reporting/builder.py` | 固定章节：研究范围、证据摘要、数据表、缺口、结论；完全可复现 |
| `llm` | `reporting/llm_report.py` | 用 DeepSeek 生成结构化 JSON；经引用与数字校验；失败自动回退 |

### 7.2 确定性报告

- 只使用该 `request_id` 已落库的证据
- 表格限制：最多 10 行、10 列、单元格 80 字符、JSON 单元格 800 字符
- 每张表标注工具、来源、抓取时间
- 明确列出缺口（`gaps`）与告警（`warnings`）
- 证据不足时结论只陈述事实与缺口，不给投资建议

### 7.3 LLM 报告与校验

- 系统提示词明确禁止编造数据、禁止超出证据推断
- 输出为结构化章节 + 声明（`fact` / `inference` / `risk` 等）
- `validation.py` 校验：
  - 引用必须指向真实存在的证据 ID
  - `fact` 必须带引用
  - 数字必须能在证据中找到对应值
  - `unavailable` / `error` 的证据不能支撑事实
- 校验失败或调用失败：丢弃不合格声明；整体失败则回退确定性报告
- 报告写入 `reports` 表，保存 `mode`、引用、缺口、告警

### 7.4 Markdown 导出

`GET /research/reports/{request_id}/latest?format=markdown` 返回 `text/markdown; charset=utf-8`，包含：

- 标题与元信息（请求、模式、生成时间）
- 各章节与表格
- 引用列表（证据 ID、工具、来源、抓取时间）
- 缺口与告警

## 8. 主数据导入与刷新

### 8.1 数据源

| source_id | 内容 | 来源 | 默认刷新阈值 | 备注 |
| --- | --- | --- | --- | --- |
| `gazetteer_json` | 11 类词典（行业/主题/链/政策/宏观/商品/区域等） | `resources/gazetteers.json` | 90 天 | 随代码发布，sha256 作版本 |
| `universe_json` | 证券 + 公司 + 行业 | `backend/industry-chain/data/a_share_universe.json` | 30 天 | 标记 `imported_unverified`；重名会告警 |
| `akshare_security` | 股票/基金/指数/转债名称表 | akshare | 7 天 | 默认关闭；部分失败只告警 |
| `exchange_profile` | 交易所上市公司名录（沪主板/科创、深 A、北交所） | akshare 交易所接口 | 7 天（默认阈值） | 免费；上交所/北交所含法定名称；深市不编造法定名称 |

未登记来源使用默认阈值 7 天。

### 8.2 新鲜度模型

每个来源的状态由 `source_imports` 的真实记录推导：

- `last_success_at`：最近一次 `status=success`
- `last_attempt_at` / `last_status` / `last_error`：最近一次尝试（无论成败）
- `age_hours` 基于 `last_success_at`
- 状态优先级：**从未成功 → `never_imported`；最新尝试失败且上次成功已过期 → `failed`；超过阈值 → `stale`；否则 `fresh`**
- 最新尝试失败但上次成功仍在有效期内 → 仍为 `fresh`，但 `last_status=failed` 会暴露失败

`/research/sources` 返回所有来源与 `stale_sources`（`needs_refresh=true` 的 ID）。

### 8.3 刷新

`MasterDataRefresher.refresh(force=False, with_akshare=None)`：

1. 先算刷新前新鲜度
2. `with_akshare` 决策：
   - 显式传参优先
   - `RESEARCH_ENTITIES_AKSHARE_SOURCE=false` → 不联网
   - 否则仅当历史上确实成功导入过 `akshare_security` 才联网（避免离线环境被动联网）
3. 只选择 `force` 或 `needs_refresh` 的来源
4. 全部新鲜 → `{ran: false, reason: "所有主数据均在有效期内"}`
5. 获取跨进程文件锁（`<db>.refresh.lock`；超过 1 小时的遗留锁自动接管）
6. 导入并返回每个来源的 `imported` 与 `warnings`
7. 锁被占用 → `{ran: false, reason: "主数据刷新已被占用…"}`

**失败不会清空旧数据**：导入记录写 `failed`，实体保持上一次成功版本，Scope 会提示数据年龄。

### 8.4 后台调度

- API 启动时创建 `RefreshScheduler`（daemon 线程），默认每 **6 小时**检查一次
- 首次启动立即尝试一次
- 间隔由 `RESEARCH_ENTITIES_REFRESH_INTERVAL_HOURS` 控制，下限 1 小时
- 默认仅在 SQLite 仓储上启用；`RESEARCH_ENTITIES_REFRESH_ENABLED` 可强制开关
- 调度线程捕获所有异常，不会因一次失败退出

## 11. 前端接入：现状与使用方法

### 11.1 现状（必须先看）

截至 **2026-10-20**，研究实体**还没有接入 Electron 前端**，具体证据：

- `frontend/packages/investment-research/python-runtime/src/types.ts`：
  `InvestmentBackendId = 'trading-core' | 'market-watch' | 'industry-chain'`，**没有 `research`**
- 同目录 `data.ts` 的 `InvestmentDataOperation` 与 `REQUEST_SPECS` 中**没有任何 `/research/*` 路由**
- `frontend/packages/client/ui-investment-research/` 中没有研究实体页面
- `frontend/packages/investment-research/runtime.ts` 的后端目录/健康身份/项目发现只覆盖上述三个后端

因此当前只有三种使用方式：

1. 直接用 HTTP 调 `:8300`（研究/运维脚本）
2. 用 CLI
3. 在 Python 里 `from research_entities...` 嵌入

**不要**假设前端已经有入口，也不要在前端直接写 `fetch('http://127.0.0.1:8300/...')` —— 这违反现有安全模型（浏览器只能提交 operation，不能提交地址/端口/路径）。

### 11.2 目标接入架构（按 SOP 类型 C）

```
React 页面
  → ctx.investmentResearchRuntimeClient.requestData({ operation, input })
  → Client Remote facade
  → Host @Remote('request-data')
  → Host operation 白名单（固定 backendId + method + path + 输入校验）
  → investmentPythonRuntime.acquire('research')
  → 研究实体服务 127.0.0.1:8300
```

职责边界：

- 浏览器只认 **operation 名 + 受约束的 JSON 输入**
- Host 决定 operation → 固定后端、固定方法、固定路径
- 后端地址、端口、路径永远不进入浏览器

### 11.3 需要新增的契约

| 层 | 文件 | 改动 |
| --- | --- | --- |
| Backend ID | `python-runtime/src/types.ts` | 增加 `'research'` |
| Operation 联合类型 | 同上 | 增加 7 个 operation（见 11.4） |
| 固定路由映射 | `python-runtime/src/data.ts` | 每个 operation 的 method/path/body 校验 |
| 后端目录 | `python-runtime/src/runtime.ts` | 项目发现、健康身份 `research-entities`、默认端口 8300、managed/external |
| Host 白名单 | Host 侧 `request-data` 实现 | operation 闭集校验 + 参数校验 |
| Client facade | `client/investment-research-runtime` | 通常无需新增方法，通用 `requestData` 即可 |
| UI | `client/ui-investment-research/src/client/` | 研究实体页面与组件 |
| 双构建 | — | **必须同时重跑 `build:lib:host` 与 `build:lib:client`**，否则双白名单会静默拒绝 |

> 经验：只改一侧构建会导致请求被静默拒绝且无明显报错。加 operation 后务必双构建。

### 11.4 建议的 operation 设计

| operation | 后端调用 | 输入 | 用途 |
| --- | --- | --- | --- |
| `research.resolve-scope` | POST `/research/scope` | `{query, persist?}` | 输入即预览：意图、实体、澄清问题 |
| `research.run` | POST `/research/run` | `{query, request_id?}` | 一步执行（耗时接口） |
| `research.entities-search` | GET `/research/entities/search` | `{q, type_code?, limit?}` | 实体搜索/自动补全 |
| `research.tool-run` | POST `/research/tools/run` | `{tool_id, entity_ids, params?, authorized?}` | 单独补数据 |
| `research.evidence` | GET `/research/evidence/{request_id}` | `{request_id, include_data?}` | 证据回放 |
| `research.report-build` | POST `/research/reports` | `{request_id, mode, persist?}` | 生成报告 |
| `research.sources` | GET `/research/sources` | `{}` | 数据源健康面板 |

可选只读 operation：`research.tools`、`research.entities-types`、`research.report-latest`。

命名遵循 SOP：`<backend-id>.<business-action>`，发布后视为兼容契约；后端改路径不改 operation。

输入校验建议：

- `query`：非空字符串，长度上限 2,000
- `request_id`：`^REQ_[a-f0-9]{32}$`
- `tool_id`：注册表存在
- `entity_ids`：字符串数组，上限 50
- `mode`：`deterministic | llm`
- `limit`：1–100
- 拒绝未知字段（与后端 `extra=forbid` 一致）

### 11.5 分步实施

**第 1 步：运行时接入**

1. `InvestmentBackendId` 增加 `'research'`
2. `runtime.ts` 增加项目发现（参考其他后端），健康检查要求 `service === "research-entities"`
3. 默认端口 8300；支持 `managed`（由 Host 启动 uvicorn）与 `external`（用户已启动）
4. 外部模式下健康检查失败要显示“服务未启动”，而不是空白页

**第 2 步：operation**

1. 在 `InvestmentDataOperation` 增加 11.4 的 operation
2. 在 `REQUEST_SPECS` 写死 method/path，并在 `body` 中做字段级校验
3. Host 白名单增加对应条目
4. 重跑 `build:lib:host` + `build:lib:client`
5. 补契约测试：每个 operation 都有固定 backend/method/path；未知 operation 被拒绝

**第 3 步：UI**

建议先做一个最小闭环：

1. **输入页**：输入框 + “解析”按钮 → `research.resolve-scope`
2. **Scope 确认卡**：
   - 意图标签（可能多个）
   - 实体列表（类型、标准名、置信度）
   - 告警（数据源过期等）
   - 若 `pending_clarification`：展示问题与候选；若 `scope_incomplete`：提示补充
3. **执行**：`scope_ready` 时启用“开始研究” → `research.run`
4. **结果页**：工具状态摘要、证据列表（可展开原始数据）、缺口
5. **报告**：“生成报告”（默认 deterministic，可切 llm）→ 展示章节与引用 → “导出 Markdown”

**第 4 步：数据源健康（可选但推荐）**

设置页展示 `/research/sources`：来源、状态、上次成功、年龄、阈值、最近错误；提供“立即刷新”按钮（`POST /research/sources/refresh`，需要新 operation 或放在运维页）。

### 11.6 UI 交互与状态设计

**推荐两段式**：先 `resolve-scope`，再 `run`。原因：

- Scope 解析很快（<1s），可以实时预览
- `/research/run` 可能 30s+，先让用户确认实体/范围，避免“等半天发现认错了标的”
- 澄清问题能在执行前解决

**加载状态**：

| 阶段 | 文案 | 超时 |
| --- | --- | --- |
| 解析中 | 正在识别研究范围… | 15s |
| 执行中 | 正在收集数据（{已完成}/{总数}）… | 120s |
| 报告生成中 | 正在生成报告… | 60s |

当前后端**没有 SSE/进度推送**，`/research/run` 是同步阻塞接口。前端只能用：

- 不确定进度条（indeterminate）+ 阶段文案
- 超时后允许“取消等待”，但注意后端请求可能仍在执行
- 后续可增加 `POST /research/run/async` + `GET /research/runs/{id}`（见第 14 章）

**错误状态**：

| 情况 | UI 处理 |
| --- | --- |
| 服务未启动/健康检查失败 | “研究服务未启动”，提供重试；外部模式下提示启动命令 |
| `scope_incomplete` | 提示补充股票/行业名称 |
| `pending_clarification` | 渲染 `clarification_questions`，选择后重新解析 |
| 工具 `unavailable` | 在结果卡标注“数据源暂不可用”，不显示空表 |
| 工具 `needs_authorization` | 展示授权说明与“允许读取持仓/自选”按钮，重新执行时传 `authorized=true` |
| 报告 404 | “该请求还没有报告”，展示“生成报告”按钮 |
| 422 | 前端校验 bug，显示字段错误 |

**展示原则**：

- 永远显示数据来源与抓取时间
- `stale`/`failed` 来源用黄色/红色标记，不隐藏
- `unverified` 实体标注“未核验”
- 缺口（`gaps`）与告警（`warnings`）默认展开，不折叠到角落
- 不把 `unavailable` 渲染成 0 或空表

### 11.7 调用示例（前端）


### 11.8 安全与授权

- **operation 闭集**：Host 不接受任意路径；新增 operation 必须走代码与测试
- **用户事实授权**：`portfolio_lookup`、`portfolio_risk_analysis`、`watchlist_lookup`、`event_monitor_setup` 需要显式 `authorized=true`
  - 前端必须在用户点击“允许”后才传 `true`
  - 未授权时工具返回 `needs_authorization`，不读取任何文件
- **写入类操作**：`event_monitor_setup` 会写入 market-watch，必须二次确认
- **不返回密钥**：研究实体本身不读取 LLM 密钥；LLM 报告通过 `llm_call` 注入，密钥由上层管理
- **本地集合最小读取**：只读存在且可读的持仓/自选文件，不猜测路径

### 11.9 接入验收清单

## 14. 已知限制与后续路线

### 14.1 已知限制

| 限制 | 影响 | 现状 |
| --- | --- | --- |
| 前端未接入 | 用户无法在 UI 使用 | 本文第 11 章给出方案 |
| `/research/run` 同步阻塞 | 长请求无进度、易超时 | 无 SSE/异步任务 |
| 6 个实体类型无静态实例 | 事件、实控人、子公司等只能靠动态工具 | 02_02/02_03/04_03/04_04/05_01/05_03 |
| `supply_demand_lookup` 未配置 | 大宗供需无法回答 | 明确返回原因，不冒充 |
| PostgreSQL 未实现 | 只能 SQLite/内存 | `postgres` 明确报错 |
| 深市无法定名称 | 深市公司 `legal_name` 缺失 | 免费源限制，不编造 |
| 非领域异常不写导入记录 | 某些编程错误只会抛异常 | 只保证 `ResearchEntityError` 写入 |
| ExchangeProfile 无独立阈值 | 使用默认 7 天 | 可后续登记 |
| 词典覆盖有限 | 新主题/小公司可能识别不到 | 需扩充 `gazetteers.json` 或导入更多主数据 |
| LLM 报告依赖 DeepSeek 可用性 | 不可用时回退 | 已实现回退 |
| 工具结果口径不完全统一 | 同花顺行业与本地行业分类不同 | 工具描述与报告中已标注“需复核” |

### 14.2 建议路线

**P1（接入）**

1. 完成前端类型 C 接入（第 11 章）
2. 增加 `POST /research/run/async` + `GET /research/runs/{id}`，返回阶段与已完成工具数
3. 前端加入 Scope 确认与澄清交互

**P1（数据）**

4. 扩充事件/实控人/子公司主数据（公告或交易所披露）
5. 为 `exchange_profile` 登记独立阈值
6. 增加实体详情接口（单实体完整属性/关系）

**P2（能力）**

7. PostgreSQL 适配器
8. 工具级超时与重试可配置化
9. 报告模板可配置（章节顺序、指标卡）
10. 实体变更历史（当前只有导入记录与审计，没有逐字段 diff）
