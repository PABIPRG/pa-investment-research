## 1. 一句话定位

**研究实体系统是陪伴型投研伙伴的“事实底座”：它把用户口语里的公司、股票、行业、主题、政策、商品，变成全系统唯一、可消歧、可追溯的研究对象，并让每一次研究结论都能回到“查了什么、什么时候查的、数据从哪来”。**

如果陪伴型投研伙伴是一个人，那么：

- **对话界面**是它的嘴和耳朵；
- **研究流程与策略引擎**是它的分析方法；
- **提醒与通知**是它的主动性；
- **研究实体系统**是它的**常识与记忆索引**——它决定了伙伴“认不认得你说的东西”“会不会把两个同名对象搞混”“说的每句话有没有出处”。

没有这一层，伙伴可以聊得很热闹，但无法长期陪伴：换一个会话就忘了“科士达”指哪家公司，报告里的数字说不清来源，事件、行情、产业链各用一套名字，用户也就无法真正信任它。

---

## 2. 为什么陪伴型投研伙伴需要它

### 2.1 陪伴的前提是“持续认得同一个对象”

陪伴型产品的核心承诺是：**用户说过一次的事，系统能记住并持续跟踪**。

但“记住”不是把原话存下来，而是把原话里的对象固定成稳定身份：

| 用户说法 | 系统需要知道 |
| --- | --- |
| “茅台”“贵州茅台”“600519” | 都指向同一个证券实体和同一个公司主体 |
| “白酒”“白酒行业”“白酒Ⅱ” | 指向标准行业实体，而不是某个概念板块 |
| “帮我看看科士达” | 科士达是公司 + 证券；若存在重名/相近名，先给候选 |
| “我的持仓”“自选里的那只” | 这是用户私有集合，必须获得授权才能读取 |
| “固态电池”“人形机器人” | 这是跨行业主题，不是标准行业 |

如果每次对话都重新猜一遍，系统就无法建立“研究委托—持续跟踪—适时提醒”的闭环。研究实体系统就是把这个“猜”变成一次可确认、可复用、可追溯的解析。

### 2.2 信任的前提是“说得出依据”

投研伙伴最容易失去信任的方式，不是答错，而是**答得很像真的**：

- 报告里出现一个数字，用户问“哪来的”，系统答不上来；
- 数据是三个月前的，界面看起来却像实时；
- 某个数据源挂了，系统默默用相近指标替代；
- 大模型写了一段顺滑的结论，但证据里根本没有支持它的数据。

研究实体系统的产品原则是：**每个结论都要能回到一次真实的工具调用；每次调用都留下来源、时间、状态和缺口。** 这就是“可定位证据”的第一层——虽然还不是完整到段落级的证据链，但已经能回答“查了什么、何时查的、是否成功”。

### 2.3 一致的实体身份是跨模块协作的前提

当前产品里，行情、事件、产业链各自维护名称索引，容易出现“同一公司在不同页面不是同一个对象”。当伙伴要跨会话、跨模块工作时，这种不一致会直接变成产品缺陷：

- 盯盘提醒说“科士达”，研究页却找不到同一标的；
- 产业链图谱里的公司，无法与持仓、委托关联；
- 事件命中后，无法判断它属于哪个研究委托；
- 报告引用的行业与行情使用的行业口径不同。

研究实体系统提供统一的实体 ID 与别名表，让事件、行情、策略、产业链、委托、报告引用同一个对象。这是从“工具箱”走向“伙伴”的基础设施。

## 3. 它在陪伴型投研伙伴中的位置

### 3.1 四层结构

```
┌──────────────────────────────────────────────────────────────┐
│ 陪伴层（用户感知到的伙伴）                                     │
│   对话 · 持仓与自选 · 研究委托 · 条件方案 · 提醒与回应          │
└───────────────────────────┬──────────────────────────────────┘
                            │ 需要“这是谁”“依据是什么”
┌───────────────────────────▼──────────────────────────────────┐
│ 研究流程层                                                     │
│   初次研究 R01 · 披露复核 R02 · 持仓条件检查 R03               │
│   分析报告 · 策略研究 · 框架验证                               │
└───────────────────────────┬──────────────────────────────────┘
                            │ 需要统一对象与可回放证据
┌───────────────────────────▼──────────────────────────────────┐
│ 研究实体层（本系统）                                            │
│   实体身份 · 别名/代码 · 消歧候选 · Scope 范围                  │
│   工具编排 · 证据留痕 · 来源新鲜度 · 报告引用校验               │
└───────────────────────────┬──────────────────────────────────┘
                            │ 调用
┌───────────────────────────▼──────────────────────────────────┐
│ 数据与连接层                                                   │
│   行情 · 财务 · 公告 · 新闻事件 · 产业链 · 宏观 · 用户私有数据  │
└──────────────────────────────────────────────────────────────┘
```

研究实体层**不是第五个前台页面**，而是夹在“伙伴行为”和“数据源”之间的能力层。它同时向上提供两种价值：

1. **身份服务**：把自然语言对象变成稳定实体，供聊天、委托、提醒、策略共用；
2. **研究执行服务**：把“研究这个问题”拆成可执行工具，留下证据，供报告与复核使用。

### 3.2 与产品各模块的关系

| 产品模块 | 研究实体系统提供什么 | 没有它会怎样 |
| --- | --- | --- |
| 聊天 / 伙伴对话 | 实体识别、歧义候选、Scope 确认、能力边界说明 | 答非所问、默认选错标的、承诺做不到的能力 |
| 持仓与自选 | 把持仓标的映射为标准实体；授权后读取用户集合 | 持仓与研究会话对不上号 |
| 研究委托（mandate） | 委托主体的稳定 ID；后续研究引用同一对象 | 跨会话跟踪失效，提醒无法路由到正确委托 |
| 分析报告 | 工具证据、来源、抓取时间、缺口、引用校验 | 报告像“无源之水”，无法复核 |
| 盯盘 / 事件 | 标准实体 ID，供事件命中与订阅路由 | 事件只能按“自选+持仓”广播，无法精确到委托 |
| 策略研究 | 标的与行业身份统一，研究结论可回指证据 | 策略回测对象与研究报告对象不一致 |
| 产业链 | 公司/行业/链环节实体对齐 | 图谱与持仓、研究彼此割裂 |
| 通知 | “为什么此刻提醒”的依据与限制 | 提醒缺少上下文，用户不知道为什么被打扰 |
| 设置 / 数据健康 | 数据源新鲜度、刷新状态、过期告警 | 用户不知道看到的是不是旧数据 |

### 3.3 在第二代产品蓝图中的坐标

第二代差距分析把“统一实体身份与可定位证据”列为四项必须补齐的基础设施之一，对应 **B1 主数据与实体解析** 与 **B2 证据与数据契约**。

当前研究实体系统已经交付的是：

| 蓝图能力 | 当前状态 | 说明 |
| --- | --- | --- |
| 统一实体 ID | ✅ 已实现 | 20 类实体、别名、标识、关系、来源 |
| 名称/代码 → 实体 | ✅ 已实现 | 词典 + 代码模式 + 候选与置信度 |
| 歧义不默选 | ✅ 已实现 | 返回候选与澄清问题 |
| 跨模块统一引用 | 🟡 部分 | 系统内部统一；尚未替换行情/事件/产业链的临时索引 |
| 工具级证据 | ✅ 已实现 | 每次工具调用记录来源、时间、状态、数据、缺口 |
| 文档级证据（原文/段落/偏移） | ⬜ 未实现 | 属于 B2 的后续阶段 |
| 观测级证据（PIT、修订、质量状态） | ⬜ 未实现 | 财务“当时可知”尚未落地 |
| 研究委托关联 | ⬜ 未实现 | 当前只有单次请求，没有 mandate 对象 |
| 前端可见 | ⬜ 未接入 | 仍是独立服务，用户暂时无法在界面使用 |

这张表很重要：**它既说明系统已经是可用的底座，也明确它还不是完整的陪伴闭环。** 产品沟通中不应把“已实现实体解析”说成“伙伴已经能持续跟踪”。

## 4. 用户会怎样感知到它

研究实体系统大多在后台工作，但用户会在五个关键时刻直接感知到它的存在。

### 4.1 场景一：第一次提到一个对象

> 用户：“帮我看看科士达。”

系统行为：

1. 识别“科士达”为公司 + 证券；
2. 若有重名或相近标的，返回候选，而不是默认取第一个；
3. 展示研究范围：对象、意图（个股分析）、将查什么；
4. 用户确认后才开始研究。

产品价值：**第一次就把对象认对**，避免后面整篇报告都建立在错误标的上。

产品要求：

- 候选必须展示“标准名 + 代码 + 类型 + 为什么是它”，不能只给一个下拉框；
- 用户确认过的对象要能复用，不要每次重复问；
- 明确区分“公司”和“股票”：公司资料与股价行情是两件事。

### 4.2 场景二：用户说得比较口语、范围不完整

> 用户：“白酒最近怎么样？”

系统行为：

1. 识别“白酒”为标准行业，而不是某个概念板块；
2. 意图可能是行业研究，也可能是行情查看；
3. Scope 里明确市场范围、时间范围（若用户没说，则保持“未指定”，不擅自补）；
4. 若问题不足以执行，说明缺什么，而不是硬答。

产品价值：**把模糊问题变成可执行范围，同时保留“未指定”的诚实。**

产品要求：

- 未识别的对象要明说“没找到”，并给出相近候选或补充建议；
- 不要为了显得聪明而自动扩展范围（例如把“白酒”扩成“消费板块”）；
- 展示“我准备这样理解你的问题”，让用户有机会纠正。

### 4.3 场景三：涉及用户私有数据

> 用户：“我的持仓风险怎么样？”

系统行为：

1. 识别这是用户事实类请求；
2. **先请求授权**，未授权时明确告知“需要读取持仓”，不读取任何文件；
3. 授权后读取持仓并映射为标准实体；
4. 只对确实存在的持仓做分析，不虚构成员；
5. 结果中说明数据时点与来源。

产品价值：**私有数据的使用是可见、可控、可拒绝的。**

产品要求：

- 授权必须是一次明确的用户动作，不能默认勾选；
- 拒绝授权时，功能降级要清楚（“无法分析持仓，但可以分析某只股票”）；
- 不把“没有持仓数据”渲染成“持仓为空”。

### 4.4 场景四：报告与结论

> 用户读完报告，问：“这个结论的依据是什么？”

系统行为：

1. 报告中的事实性陈述绑定证据；
2. 每条证据可展开：工具、来源、抓取时间、记录数、状态；
3. 数据源不可用时，报告明确写“未获取到”，而不是留空或编造；
4. 大模型撰写的部分必须通过引用与数字校验，否则回退到确定性报告。

产品价值：**报告是可复核的研究材料，不是一段无法验证的文案。**

产品要求：

- 报告要区分“事实”“推断”“风险”，不能混在一起；
- 引用不是装饰，要能点开看到证据；
- 缺口和告警默认可见，不能折叠到角落；
- 导出 Markdown 时保留引用与时间。

### 4.5 场景五：数据变旧或数据源失败

> 用户：“这个数据是最新的吗？”

系统行为：

1. 每个实体带来源与最后核验时间；
2. 每个数据源有新鲜度状态（新鲜/过期/从未导入/刷新失败）；
3. Scope 与报告显式提示“某来源已 X 天未刷新”“上次刷新失败，当前使用旧数据”；
4. 失败不清空旧数据，但必须让用户知道旧。

产品价值：**不把旧数据伪装成实时数据。**

产品要求：

- 过期提示要出现在使用数据的地方，而不是只藏在设置页；
- 数据源健康页要能看懂：哪个源、多久没更新、阈值是多少、最近错误是什么；
- 允许用户手动刷新，并明确刷新可能耗时。

## 5. 产品能力地图

### 5.1 用户可感知的能力

| 能力 | 用户看到什么 | 当前可用性 |
| --- | --- | --- |
| 实体识别 | 问题中的公司/股票/行业被正确标出 | 后端可用，前端未接入 |
| 歧义澄清 | 多个候选及选择理由 | 后端可用，前端未接入 |
| 研究范围确认 | 意图、对象、时间/市场范围、将执行的工具 | 后端可用，前端未接入 |
| 能力边界说明 | 哪些能查、哪些查不了、为什么 | 后端可用（工具状态/缺口） |
| 证据回放 | 查了什么、来源、时间、结果状态 | 后端可用，前端未接入 |
| 报告与引用 | 结构化报告、引用、缺口、Markdown 导出 | 后端可用，前端未接入 |
| 数据源健康 | 来源新鲜度、过期告警、手动刷新 | 后端可用，前端未接入 |

### 5.2 后台支撑能力

| 能力 | 作用 |
| --- | --- |
| 20 类实体主数据 | 证券、公司、行业、主题、产业链、事件、资金风格、宏观大宗 |
| 4 类动态集合 | 持仓、自选、可比组、任务生成集 |
| 17 类研究意图 | 个股、行业、主题、政策、持仓、宏观、事件、资金、基准等 |
| 45 个逻辑工具 | 行情、财务、公告、公司、行业、基金、指数、债券、宏观、商品、政策 |
| 工具编排 | 按实体类型与意图预加载、排序、去重 |
| 授权与安全 | 私有数据必须显式授权；写入类操作二次确认 |
| 证据与审计 | 每次执行留痕，敏感字段脱敏 |
| 主数据刷新 | 免费数据源导入、定时刷新、跨进程锁、失败保留旧数据 |
| 报告校验 | 引用存在性、数字可追溯、失败回退 |

### 5.3 当前明确“不做”的事

产品需要在对话与界面中诚实表达这些边界：

- 没有可靠数据源的能力（如大宗供需平衡表）**不做猜测性回答**；
- 不把库存、价格等相近指标包装成供需数据；
- 不对未上市公司编造主体信息；
- 不把“模型分析”说成“程序已验证的买卖信号”；
- 不承诺实时行情级别的一致性（工具有缓存与超时）；
- 不在未授权时读取任何用户私有数据。

## 6. 产品设计原则

### 原则一：先确认，再研究

研究对象错了，后面所有分析都无意义。因此产品流程应是：

```
口语输入 → 识别与候选 → 范围确认 → 执行 → 证据 → 报告
```

而不是“一句话直接出报告”。确认成本很低（一次点击），纠错成本很高（重读一份错误报告）。

### 原则二：不猜、不编、不默选

- 找不到实体：说找不到，给候选；
- 存在歧义：给候选，不默认第一个；
- 数据不可用：说不可用，不用相近指标替代；
- 数字没有证据：不写进事实性结论。

### 原则三：每个结论都能回到来源

产品语言中，“有依据”应具体到：

- 哪个工具/数据源；
- 什么时候抓取；
- 成功、为空、不可用还是出错；
- 有没有缓存；
- 缺了什么。

### 原则四：授权可见、可拒绝、可降级

用户私有数据不是“系统默认知道”，而是“用户允许后才知道”。拒绝授权不应导致整个功能不可用，而应明确降级范围。

### 原则五：诚实比聪明重要

陪伴型产品的长期信任来自“知道自己不知道”。宁可说“这项数据暂时查不到”，也不要用相似指标糊弄过去。

### 原则六：研究是过程，不是一次性问答

Scope、证据、报告都应可回放、可再次引用。这样伙伴才能在后续会话中说：“上次我们查过，当时的数据是这样，现在有这些变化。”

## 7. 体验设计建议

> 以下为前端接入后的建议形态，当前系统尚未提供页面。

### 7.1 研究范围确认卡（核心组件）

一次研究开始前，展示一张“我准备这样研究”的卡片：

```
┌─────────────────────────────────────────────┐
│ 研究范围                                     │
│                                             │
│ 对象                                         │
│  • 贵州茅台   A股股票 600519   置信度 98%    │
│  • 白酒Ⅱ      标准行业          置信度 93%    │
│                                             │
│ 研究意图                                     │
│  • 行业研究   • 个股分析                     │
│                                             │
│ 范围                                         │
│  • 市场：A股                                 │
│  • 时间：未指定                              │
│                                             │
│ ⚠ 部分实体来自未核验名称表                    │
│                                             │
│ [调整对象]            [开始研究]             │
└─────────────────────────────────────────────┘
```

设计要求：

- 实体必须显示类型与代码，避免“同名不同物”；
- 置信度低或存在候选时，主按钮应变为“请先确认”；
- 告警与缺口不能隐藏；
- 允许用户删除/替换对象后重新解析。

### 7.2 歧义澄清

```
“你说的‘平安’是指？”
  ○ 平安银行（000001，银行）
  ○ 中国平安（601318，保险）
  ○ 都不是，我重新说
```

要求：

- 候选带代码与行业，帮助非专业用户区分；
- 不默认高亮第一项；
- 用户选择后记住本次会话，但不要擅自变成长期偏好。

### 7.3 执行过程

当前后端是同步执行，前端只能展示阶段与不确定进度：

```
正在收集数据…
已连接：行情、财务、公告
暂不可用：资金流向（数据源超时）
```

要求：

- 明确“预计需要几十秒”，避免用户以为卡死；
- 不可用项实时可见，不要等全部结束才说；
- 提供“取消等待”，并说明后台可能仍在执行；
- 不要用虚假的百分比进度条。

### 7.4 结果与证据

结果页建议分三层：

1. **摘要**：完成了什么、缺了什么；
2. **证据列表**：每个工具一张卡，状态、来源、时间、记录数；
3. **原始数据**：按需展开，默认不铺满屏幕。

状态必须可区分：

| 状态 | 展示 |
| --- | --- |
| 成功有数据 | 正常卡片 |
| 成功但为空 | “未查询到记录”，不是 0 |
| 数据源不可用 | “暂不可用 + 原因”，不是空表 |
| 需要授权 | “需要读取持仓/自选”，提供授权按钮 |
| 执行错误 | “查询失败”，提供重试 |

### 7.5 报告

报告页建议：

- 顶部：标题、生成时间、模式（模板/大模型辅助）、数据截止时间；
- 正文：事实、推断、风险分区；
- 引用：编号可点开，跳转到证据卡；
- 缺口与告警：默认展开；
- 操作：导出 Markdown、基于同一请求重新生成、继续追问。

### 7.6 数据源健康

设置页或研究页角落提供“数据状态”入口：

```
数据源            状态     上次成功        阈值
本地词典          新鲜     2 小时前        90 天
证券池            新鲜     2 小时前        30 天
证券名称表        新鲜     2 小时前        7 天
交易所名录        新鲜     2 小时前        7 天
```

要求：

- 用用户能理解的语言解释“过期”意味着什么；
- “刷新失败”要保留上一次成功时间；
- 手动刷新要有确认与耗时提示。

## 8. 与「研究委托」闭环的关系

第二代产品的核心闭环是：

```
口语 → 实体 → 委托 → 初次研究 → 条件观察 → 事件唤醒 → 提醒 → 回应
```

研究实体系统负责其中前三段的基础：

| 环节 | 研究实体系统的作用 | 尚缺 |
| --- | --- | --- |
| 口语 → 实体 | 识别、消歧、候选、置信度 | 多轮上下文中的指代消解 |
| 实体 → 研究范围 | 意图、角色、约束、工具计划 | 与用户框架/偏好的结合 |
| 研究范围 → 委托 | 提供稳定的主体与范围 | 委托对象、版本、暂停/恢复 |
| 初次研究 | 执行工具、留证据、出报告 | 文档级证据、PIT 财务 |
| 条件观察 | 提供实体 ID 供条件绑定 | 条件三值评估、依赖路由 |
| 事件唤醒 | 实体 ID 可用于事件匹配 | 事件结构化与订阅关系 |
| 提醒 | 提供“依据与限制” | 提醒决策、抑制、汇总 |
| 回应 | 证据可回放 | 反馈记录与偏好更新 |

**产品结论：研究实体系统是闭环的必要条件，但不是充分条件。** 它先解决“认对人、说清依据”，再谈“持续跟踪、主动提醒”。路线图应遵循这个顺序，避免在身份与证据还不稳时过早承诺“伙伴感”。

## 9. 成功指标

### 9.1 北极星指标（建议）

**“有依据的研究结论占比”**：报告中每条事实性结论都能绑定有效证据的比例。

这个指标同时约束“敢不敢说”和“说不说得清”，比“报告数量”更能反映陪伴质量。

### 9.2 过程指标

| 维度 | 指标 | 目标方向 |
| --- | --- | --- |
| 实体识别 | 实体解析成功率（用户未修改即确认） | ↑ |
| 消歧质量 | 歧义场景下候选包含正确项的比例 | ↑ |
| 误选率 | 未确认即执行且对象错误的比例 | ↓（应接近 0） |
| 范围质量 | Scope 首次确认通过率 | ↑ |
| 证据覆盖 | 有数据工具的证据落库率 | ↑ |
| 报告可信 | 引用校验通过率 | ↑ |
| 数据新鲜 | 使用过期数据而未提示的次数 | 0 |
| 边界诚实 | “不可用”被正确展示的比例 | ↑ |
| 效率 | Scope 解析耗时、研究执行耗时 | ↓ |
| 授权 | 私有数据请求中显式授权的比例 | 100% |

### 9.3 护栏指标

- 用户因“对象认错”而重新提问的比例；
- 报告中无法解释来源的数字出现次数（应为 0）；
- 数据源失败后被静默忽略的次数（应为 0）；
- 未授权读取私有数据的次数（应为 0）；
- 用户对“数据过期”提示的忽略率（过高说明提示位置/文案有问题）。

## 10. 路线图建议

### 阶段 P0：底座（已完成）

- 20 类实体、别名、标识、关系；
- 实体抽取、候选、消歧；
- Scope 与研究意图；
- 45 个工具编排与执行；
- 工具级证据、审计；
- 确定性报告 + 大模型报告校验；
- 主数据导入、新鲜度、定时刷新；
- 209 个离线测试。

产品含义：**“认对人、说清依据”在服务端已经成立，但用户还看不见。**

### 阶段 P1：让用户用上（当前应做）

1. 前端接入（backend ID、operation、页面）；
2. 研究范围确认卡与歧义澄清；
3. 执行过程状态与不可用提示；
4. 证据抽屉与报告引用跳转；
5. 数据源健康面板；
6. 授权流程（持仓/自选）。

验收标准：用户可以从一句话开始，确认对象，看到证据，导出带引用的报告；任何不可用与过期都可见。

### 阶段 P2：接入陪伴闭环

1. 研究委托对象：把一次研究升级为可暂停、可恢复的委托；
2. 实体与委托关联：一个公司可同时属于“学习”和“持仓管理”两类目的；
3. 事件结构化：事件带标准实体 ID、披露时间、内容哈希；
4. 条件方案绑定实体：条件命中时能说明“属于哪个委托”；
5. 提醒携带依据与限制；
6. 用户回应与偏好更新。

### 阶段 P3：深化证据与覆盖

1. 文档级证据（公告/新闻正文、段落定位）；
2. PIT 财务（当时可知 vs 事后修订）；
3. 观测级质量状态（缺失原因、覆盖范围）；
4. 更多实体类型与数据源覆盖；
5. 实体变更历史与影响分析。

## 11. 风险与产品对策

| 风险 | 用户感受 | 产品对策 |
| --- | --- | --- |
| 实体识别错误 | “它说的不是我想的那个” | 先确认后执行；候选带代码与类型；允许一键纠正 |
| 数据源不稳定 | “怎么又查不到” | 明确不可用原因；主备切换；健康面板；不静默替代 |
| 研究耗时长 | “是不是卡住了” | 阶段文案；预计耗时；取消等待；后续异步任务 |
| 大模型编造 | “看着很真但没依据” | 引用与数字校验；不合格回退；事实/推断分区 |
| 过度承诺能力 | “你不是能查吗” | 能力目录与缺口说明；对话中主动说边界 |
| 数据过期 | “拿旧数据糊弄我” | 使用处提示；来源年龄；刷新入口 |
| 私有数据顾虑 | “它怎么知道我的持仓” | 显式授权；可拒绝；最小读取；不默认开启 |
| 术语门槛 | “标准行业是什么” | 实体卡展示通俗名称 + 代码；解释口径差异 |
| 多模块口径不一致 | “两个页面数字不一样” | 统一实体 ID；报告标注口径；逐步替换临时索引 |

## 12. 常见问题（产品口径）

**Q：研究实体系统是一个新页面吗？**

不是。它是能力层。用户感知到的是“对话/研究流程里对象认得准、依据说得清”，而不是一个叫“研究实体”的菜单。

**Q：它和产业链、行情、事件系统的区别是什么？**

产业链、行情、事件是数据与关系；研究实体系统负责“这些数据说的是同一个对象”，并把它们组织成一次可执行、可留证的研究。它不替代这些系统，而是让它们能被统一引用。

**Q：为什么现在界面上还看不到？**

服务端能力已经可用，但前端尚未接入（没有后端 ID、operation 和页面）。这是当前 P1 的工作，不是能力缺失。

**Q：它能让伙伴“记住”用户吗？**

它能记住“用户研究过哪个实体、当时查了什么、结论依据是什么”。但“记住用户的偏好、委托、判断框架”属于委托与用户框架层，尚未实现。两者需要配合，不能混为一谈。

**Q：为什么有些问题它会直接说查不到？**

因为对应能力没有可靠数据源。产品选择“明确说查不到”，而不是用相近指标编一个答案。这是信任设计的一部分。

**Q：报告是大模型写的吗？**

两种模式：确定性模板报告，以及大模型辅助报告。后者必须通过引用与数字校验，不合格会自动回退到模板报告。

**Q：数据多久更新一次？**

本地词典约季度、证券池约月度、证券名称表与交易所名录约每周；服务每 6 小时检查一次是否需要刷新。界面应显示每个来源的实际年龄，而不是只写“定期更新”。

## 13. 总结

研究实体系统的产品价值，可以压缩成三句话：

1. **让伙伴认对人**：把口语里的对象变成全系统唯一、可消歧的身份。
2. **让结论有出处**：每次研究留下来源、时间、状态与缺口，报告可回放、可引用。
3. **让边界可相信**：查不到就说查不到，数据旧就说旧，没授权就不读。

它不直接产生“伙伴感”，但决定了伙伴感能不能长期成立。当前它已经是一个可用的服务端底座；下一步的关键不是继续堆能力，而是**让用户看得见、用得上、信得过**——即完成前端接入与确认/证据/健康三类体验，再进入研究委托与持续跟踪的闭环。
