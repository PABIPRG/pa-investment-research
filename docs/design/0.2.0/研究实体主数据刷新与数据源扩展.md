# 研究实体主数据刷新与数据源扩展

文档类型：工程设计、实现与运维说明
适用模块：`backend/dsh-trading-core/research_entities`
目标读者：维护研究实体服务的工程与运维人员

---

## 1. 背景与目标

研究实体库的证券主数据来自三类导入：

| 来源 ID | 内容 | 获取方式 |
| --- | --- | --- |
| `gazetteer_json` | 本地行业/主题/政策/宏观等词典 | 随代码发布的 JSON |
| `universe_json` | A 股证券池与上市公司 | 产业链模块的本地 JSON |
| `akshare_security` | A 股、基金、指数、可转债名称表 | 联网调用 akshare |
| `exchange_profile`（本次新增） | 交易所上市公司名录、部分法定名称 | 联网调用 akshare |

在此之前，这些数据只能靠人工执行 `import-universe` 导入，系统既不知道数据是什么时候导入的，也无法判断是否已经过期。目标是补齐两件事：

1. **可追溯**：每次导入尝试（成功或失败）都留痕，可查询来源、版本、条数与错误。
2. **可刷新**：按来源新鲜度自动或手动刷新，过期状态能在 API、CLI 与研究 Scope 中显式暴露，而不是悄悄使用旧数据。

同时在不引入付费数据的前提下，用免费的交易所名录补充上市公司法定名称。

### 1.1 明确不做的事

- 不伪造导入时间、数据版本或「已核验」状态；导入数据仍为 `imported_unverified`。
- 不在没有可靠数据源时硬造供需平衡表；`supply_demand_lookup` 保持 `unconfigured`。
- 不为深交所名录编造公司全称（免费接口不提供该字段）。
- 不自动覆盖人工核验过的实体状态。

## 2. 总体设计与数据流

```text
                    ┌──────────────────────────────┐
                    │  RefreshScheduler（可选线程） │
                    │  每 6 小时 / 启动时检查一次   │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
CLI `refresh` ─────►│      MasterDataRefresher      │
HTTP POST /refresh  │  1. 读取各来源新鲜度          │
                    │  2. 只选择过期的来源          │
                    │  3. 获取文件锁                │
                    │  4. import_sources            │
                    └──────────────┬───────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ ResearchEntityService.import_source     │
              │  fetch → records_to_entities → upsert   │
              │  成功/失败均写 source_imports + audit   │
              └────────────────────┬────────────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ source_imports（SQLite）                 │
              └────────────────────┬────────────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │ freshness.source_freshness    │
                    │ → API/CLI 状态、Scope 过期警告 │
                    └──────────────────────────────┘
```

设计原则：

- **导入记录与实体写入同一套仓储端口**，不引入第二套存储。
- **新鲜度只依据真实导入记录**，不依据文件修改时间、进程启动时间等间接信号。
- **刷新是可降级能力**：读取新鲜度失败、加锁失败都只影响刷新与警告，不阻断 Scope 解析和工具执行。
- **联网是显式选择**：akshare 相关来源默认关闭；只有参数或环境变量开启时才访问外网。

## 3. 数据模型与存储

### 3.1 新增表 `source_imports`

迁移文件：`research_entities/migrations/005_source_imports.sql`

```sql
CREATE TABLE IF NOT EXISTS source_imports (
    import_id TEXT PRIMARY KEY,
    source_id TEXT NOT NULL,
    source_version TEXT NOT NULL DEFAULT '',
    imported_count INTEGER NOT NULL DEFAULT 0,
    status TEXT NOT NULL,
    warnings_json TEXT NOT NULL DEFAULT '[]',
    error TEXT,
    imported_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_source_imports_source
    ON source_imports(source_id, imported_at);
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `import_id` | 每次导入尝试的唯一 ID，格式 `IMPORT_<uuid hex>` |
| `source_id` | 数据源标识，如 `akshare_security` |
| `source_version` | 数据源内容指纹；失败时为空 |
| `imported_count` | 本次 upsert 的实体条数；失败为 0 |
| `status` | `success` / `failed` |
| `warnings_json` | 部分成功时的告警（如单个品种失败、名称重复） |
| `error` | 失败原因，格式 `异常类型: 消息` |
| `imported_at` | UTC 导入时间 |

> 该表记录的是「导入尝试」，不是「实体被验证」。实体表原有的 `last_verified_at` 不会被填充，避免把导入伪装成核验。

### 3.2 领域模型

`research_entities/models.py` 新增：

```python
SourceImportStatus = Literal["success", "failed"]

class SourceImport(_StrictModel):
    import_id: str
    source_id: str
    source_version: str = ""
    imported_count: int = 0
    status: SourceImportStatus
    warnings: list[str] = []
    error: str | None = None
    imported_at: datetime
```

### 3.3 仓储端口

`research_entities/ports.py` 的 `EntityRepository` 新增两个方法：

```python
def record_source_import(self, record: SourceImport) -> None: ...
def list_source_imports(self, *, limit: int = 500) -> list[SourceImport]: ...
```

- SQLite 实现：`research_entities/adapters/storage_sqlite.py`
- 内存实现：`research_entities/adapters/storage_memory.py`
- 两者行为一致，由 `tests/test_research_entities_contract.py` 的契约测试共同覆盖（含倒序与 `limit`）。

### 3.4 写入时机

`ResearchEntityService.import_source()`：

1. 调用 `source.fetch_entities()`。
2. 转换为实体并 `upsert_entities`。
3. 写入原有 `audit_events`（`stage=import`）。
4. 写入 `source_imports`，`status=success`，包含版本、条数与告警。

失败路径：

- `fetch_entities` / 转换 / upsert 抛出领域异常 `ResearchEntityError` 时，记录 `status=failed`、`error="类型: 消息"`，然后重新抛出。
- 批量入口 `import_sources()` 捕获 `SourceUnavailable`，返回 `ImportResult(imported=0, warnings=[原因])`，CLI 与调度器据此报告失败。
- 非领域异常（例如依赖库抛出的 `ValueError`）不做伪装记录，直接向上抛出，由调用方暴露。

**兼容性**：`_record_import` 通过 `getattr` 检查仓储是否实现新方法，旧的自定义仓储不会因缺少该方法而崩溃。

## 4. 新鲜度判定

实现：`research_entities/freshness.py`

### 4.1 阈值

| 来源 | 默认阈值 | 理由 |
| --- | --- | --- |
| `akshare_security` | 168 小时（7 天） | 证券名录变化较快 |
| `exchange_profile` | 168 小时（7 天） | 与证券名录同步刷新 |
| `universe_json` | 720 小时（30 天） | 本地证券池，随代码更新 |
| `gazetteer_json` | 2160 小时（90 天） | 静态词典，变化最少 |
| 其他来源 | 168 小时（7 天） | 兜底 |

阈值是代码常量（`SOURCE_MAX_AGE_HOURS` / `DEFAULT_MAX_AGE_HOURS`）。单次 CLI 刷新可用 `--max-age-hours` 覆盖；后台调度使用默认阈值。这样避免为了调阈值而引入一堆环境变量，也保证定时任务行为可预测。

### 4.2 状态机

```
无任何记录                        → never_imported
有失败记录、无成功记录            → failed
有成功记录，年龄 ≤ 阈值           → fresh
有成功记录，年龄 > 阈值，最近尝试成功 → stale
有成功记录，年龄 > 阈值，最近尝试失败 → failed
```

注意：

- 最新一次尝试失败、但上一次成功仍在有效期内 → 状态仍是 `fresh`，`last_status` 显示 `failed`，不产生过期告警。数据确实还新，不应误报。
- 「最近尝试失败且数据已过期」优先显示 `failed`，因为用户更需要知道刷新出了问题。
- 从未导入不是新鲜，`needs_refresh=True`。

### 4.3 返回结构

`source_freshness(repository, now=None, max_age_hours=None, limit=500)` 返回列表，每项字段：

| 字段 | 含义 |
| --- | --- |
| `source_id` | 来源标识 |
| `state` | `fresh` / `stale` / `never_imported` / `failed` |
| `state_label` | 中文标签：新鲜 / 已过期 / 从未导入 / 刷新失败 |
| `needs_refresh` | 是否应参与刷新 |
| `last_success_at` | 最近一次成功导入时间（UTC ISO） |
| `last_attempt_at` | 最近一次尝试时间 |
| `last_status` | 最近一次尝试的状态 |
| `last_error` | 最近一次尝试的错误 |
| `source_version` | 最近一次成功的版本指纹 |
| `imported_count` | 最近一次成功的条数 |
| `age_hours` | 距最近一次成功的小时数；无成功为 `null` |
| `max_age_hours` | 本次判定使用的阈值 |
| `warnings` | 最近一次尝试的告警 |

### 4.4 Scope 过期标记

实体的 `source` 形如 `akshare_security:<version>`，按第一个冒号拆分得到来源 ID。`resolve_scope` 在构建 Scope 时调用 `stale_source_warnings()`：

- 只检查「已解析实体实际依赖的来源」，不会因为库里存在某个过期来源就全局告警。
- 告警文案：
  - 过期：`主数据 akShare_security 已 10.0 天未刷新（阈值 168 小时），相关实体信息可能过期。`
  - 刷新失败：`主数据 X 最近一次刷新失败（URLError: ...），当前使用的是上一次成功导入的数据。`
  - 从未导入：`实体来源 X 没有导入记录，无法判断数据新鲜度。`
- 新鲜度查询异常会被吞掉并返回空列表，Scope 解析不受影响。

告警进入 `ResearchScope.warnings`，会随 Scope 一起落库、出现在 API 响应和报告上下文中。

## 5. 刷新机制

实现：`research_entities/refresh.py`

### 5.1 `MasterDataRefresher`

```python
refresher = build_refresher(service=service, max_age_hours=None)
result = refresher.refresh(force=False, with_akshare=None)
```

执行流程：

1. 读取刷新前新鲜度快照。
2. 决定是否包含 akshare 来源：
   - `with_akshare` 显式传入时以其为准。
   - 否则若 `RESEARCH_ENTITIES_AKSHARE_SOURCE` 显式为 false/0/no/off → 不联网。
   - 否则只有历史上存在 `akshare_security` 成功导入记录时才联网；否则只刷新本地来源。
3. 构建数据源，逐个判断 `force or 无记录 or needs_refresh`，只保留需要刷新的来源。
4. 若没有来源需要刷新，直接返回，不写记录、不碰网络。
5. 获取文件锁，调用 `service.import_sources(selected)`。
6. 重新计算新鲜度并返回。

返回结构：

```json
{
  "ran": true,
  "reason": null,
  "results": [
    {"source_id": "exchange_profile", "source_version": "b5a2f09405af4d6e",
     "imported": 5575, "warnings": []}
  ],
  "sources": [ ... 刷新后的新鲜度列表 ... ]
}
```

跳过时：

```json
{"ran": false, "reason": "所有主数据均在有效期内", "results": [], "sources": [ ... ]}
```

加锁失败时：

```json
{"ran": false, "reason": "主数据刷新已被占用：<lock path>", "results": [], "sources": [ ... ]}
```

### 5.2 文件锁

- 路径：与 SQLite 数据库同目录，`research_entities.refresh.lock`；内存仓储为 `None`（不加锁）。
- 实现：`O_CREAT | O_EXCL` 独占创建，写入 PID。
- 锁文件存在且年龄超过 3600 秒视为崩溃遗留，自动删除后重试一次。
- 作用：避免 API 调度器与手动 CLI 同时导入 3 万多条数据。
- 正常结束或异常都会在 `finally` 中删除锁文件。

### 5.3 `RefreshScheduler`

| 属性 | 值 |
| --- | --- |
| 线程 | daemon，名称 `research-master-refresh` |
| 默认间隔 | 6 小时（`RESEARCH_ENTITIES_REFRESH_INTERVAL_HOURS`） |
| 最小间隔 | 60 秒（代码钳制） |
| 启动行为 | API lifespan 启动后立即检查一次，此后按间隔循环 |
| 停止行为 | API 关闭时 `stop()`，最多等待 5 秒 |
| 异常处理 | 单次刷新异常只记录 warning 日志，线程不退出 |

调度器只负责「检查是否过期」；数据仍新鲜时不会产生任何网络请求或写入。

### 5.4 与 API 生命周期的关系

`research_entities/api.py` 在 `create_app()` 中：

- 只有持久化 SQLite 仓储默认启用调度器；内存仓储（测试、临时会话）默认关闭。
- 可用 `RESEARCH_ENTITIES_REFRESH_ENABLED=true/false` 显式覆盖。
- 调度器实例挂在 `app.state.refresh_scheduler`，刷新器挂在 `app.state.refresher`，便于测试和排障。
- 使用 FastAPI lifespan 管理启动/停止，不依赖已废弃的 `on_event`。

### 5.5 联网前置条件

`factory.build_sources(include_akshare=True)` 在构建 akshare 来源前会：

1. `install_no_proxy()`：进程内把 `NO_PROXY` / `no_proxy` 补上 `*`，避免系统代理劫持行情接口请求。
2. `install_curl_ca_bundle()`：Windows 下 certifi 证书位于非 ASCII（中文用户名）路径时，把 `cacert.pem` 复制到 ASCII 目录并设置 `CURL_CA_BUNDLE` / `SSL_CERT_FILE`。

因此定时刷新和 `import-universe --with-akshare` 都不依赖启动命令里手动设置代理变量。

## 6. 免费数据源扩展：交易所上市公司名录

实现：`research_entities/adapters/sources/exchange_profile.py`

### 6.1 数据来源

| 板块标识 | akshare 函数 | 参数 | 记录数（2026-10-20 实测） |
| --- | --- | --- | --- |
| `sh_main` | `stock_info_sh_name_code` | `symbol="主板A股"` | 约 1,700 |
| `sh_star` | `stock_info_sh_name_code` | `symbol="科创板"` | 科创板名录 |
| `sz_a` | `stock_info_sz_name_code` | `symbol="A股列表"` | 约 2,900 |
| `bj` | `stock_info_bj_name_code` | 无 | 约 350 |

合计一次导入 5,575 条 `ENTITY_02_01` 记录（含与既有公司实体合并的部分）。

### 6.2 字段映射

| 目标字段 | 取值 |
| --- | --- |
| `entity_id` | 由 `company_code` 推导，如 `CO:CN:A:600000` |
| `canonical_name` | 证券简称（上交所/深交所/北交所） |
| 别名 | 公司全称（仅当全称存在且不等于简称） |
| `attributes.legal_name` | 公司全称（仅上交所/北交所名录提供） |
| `attributes.listing_board` | `sh_main` / `sh_star` / `sz_a` / `bj` |
| `attributes.listing_date` | 上市日期，`YYYY-MM-DD` |
| `identifiers` | `company_code`、`security_code`、`exchange` |

列名兼容多版本：代码列支持 `证券代码` / `A股代码` / `代码`，简称列支持 `证券简称` / `A股简称` / `简称`，全称列支持 `公司全称` / `证券全称`。

### 6.3 不编造原则

- 深交所免费名录没有公司全称：`legal_name` 不写、不生成别名。
- 缺少必要列的交易所：写入 warning，不生成猜测数据。
- 单行代码非 6 位数字或名称为空：跳过该行。
- 数据状态仍为 `imported_unverified`；法定名称的权威来源仍是 `company_profile`（巨潮，实时查询）。

### 6.4 失败与版本

- 单个交易所失败：记录 warning，其余交易所照常导入。
- 四个名录全部失败或没有产生任何记录：抛出 `SourceUnavailable`，由服务层记录 failed 尝试。
- 版本指纹：对所有记录的 `类型:代码:简称:全称` 排序后做 SHA-256，取前 16 位。内容不变则版本不变，便于比对。

### 6.5 与既有实体的合并

- 同一 `CO:CN:A:<code>` 由 `universe_json` / `akshare_security` 已创建时，`upsert` 走 `merge_entity`：
  - 保留原有属性；
  - 追加公司全称别名；
  - 补充 `legal_name`、`listing_date`、`listing_board`；
  - `source` 更新为 `exchange_profile:<version>`。
- 解决的实际问题：用户输入「上海浦东发展银行股份有限公司」这类法定全称时，原先无法命中；现在可解析到 `CO:CN:A:600000`（浦发银行）。已实测验证。

### 6.6 启用方式

`exchange_profile` 与 `akshare_security` 同属联网来源，只在以下情况加入导入：

- CLI：`import-universe --with-akshare` 或 `refresh --with-akshare`；
- API 调度：`RESEARCH_ENTITIES_AKSHARE_SOURCE` 未显式关闭，且历史上有 `akshare_security` 成功导入；
- 代码调用：`build_sources(include_akshare=True)`。

## 7. 接口与命令

### 7.1 HTTP API

#### `GET /research/sources`

查看所有来源的新鲜度。

```json
{
  "refresh_enabled": true,
  "refresh_interval_hours": 6.0,
  "stale_sources": [],
  "sources": [
    {
      "source_id": "exchange_profile",
      "state": "fresh",
      "state_label": "新鲜",
      "needs_refresh": false,
      "last_success_at": "2026-10-20T09:00:26.307455+00:00",
      "last_attempt_at": "2026-10-20T09:00:26.307455+00:00",
      "last_status": "success",
      "last_error": null,
      "source_version": "b5a2f09405af4d6e",
      "imported_count": 5575,
      "age_hours": 0.09,
      "max_age_hours": 168,
      "warnings": []
    }
  ]
}
```

`refresh_enabled` 表示当前进程是否启用了后台调度器，不代表数据源本身是否可用。

#### `POST /research/sources/refresh`

手动触发一次刷新。

- 参数：`force`（query，布尔，默认 `false`）。为 `true` 时忽略新鲜度，强制重新导入所有已配置来源。
- 响应：`MasterDataRefresher.refresh()` 的返回结构（见 5.1）。
- 该接口是同步执行：包含 akshare 时可能需要数分钟；适合本机运维调用，不建议前端在普通交互路径中调用。

curl 示例（本机）：

```bash
curl --noproxy '*' -X POST "http://127.0.0.1:8300/research/sources/refresh"
curl --noproxy '*' -X POST "http://127.0.0.1:8300/research/sources/refresh?force=true"
```

### 7.2 CLI

在 `backend/dsh-trading-core` 下执行：

```bash
# 查看新鲜度
./env/Scripts/python.exe -m research_entities.cli sources-status

# 刷新过期来源（按默认阈值）
./env/Scripts/python.exe -m research_entities.cli refresh

# 强制重新导入所有来源（含 akshare）
./env/Scripts/python.exe -m research_entities.cli refresh --force --with-akshare

# 本次只刷新本地来源
./env/Scripts/python.exe -m research_entities.cli refresh --no-akshare

# 自定义过期阈值（仅本次生效）
./env/Scripts/python.exe -m research_entities.cli refresh --max-age-hours 24
```

| 命令 | 说明 |
| --- | --- |
| `sources-status` | 输出 `stale_sources` 与完整来源状态；退出码恒为 0 |
| `refresh` | 刷新过期来源；有来源导入 0 条且带 warning 时退出码为 1，否则为 0 |
| `--force` | 忽略新鲜度强制导入 |
| `--max-age-hours N` | 覆盖所有来源阈值 |
| `--with-akshare` / `--no-akshare` | 互斥；覆盖本次 akshare 开关 |

### 7.3 研究 Scope

`resolve_scope` / `POST /research/scope` 的 `warnings` 中会出现来源级过期提示。示例：

```
主数据 akshare_security 已 10.0 天未刷新（阈值 168 小时），相关实体信息可能过期。
```

前端不需要新增字段，沿用 Scope 的 `warnings` 即可。

## 8. 配置项

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `RESEARCH_ENTITIES_AKSHARE_SOURCE` | 未设置（视为关闭） | 控制 `build_sources()` 是否默认加入 akshare 来源；显式 `false/0/no/off` 也会阻止定时刷新联网 |
| `RESEARCH_ENTITIES_REFRESH_ENABLED` | SQLite 仓储自动开启；内存仓储自动关闭 | 显式开关后台调度器：`true/1/yes/on` 或 `false/0/no/off` |
| `RESEARCH_ENTITIES_REFRESH_INTERVAL_HOURS` | `6` | 调度检查间隔；非法值回退 6，最小 1 小时 |
| `RESEARCH_ENTITIES_STORAGE` | `sqlite` | 仓储类型；调度器默认只在 sqlite 下启用 |
| `RESEARCH_ENTITIES_SQLITE_PATH` | 数据目录下的 `research_entities.sqlite3` | 数据库路径；锁文件与其同目录 |

说明：

- `RESEARCH_ENTITIES_AKSHARE_SOURCE=false` 是「离线承诺」：不仅手动导入不加 akshare，定时刷新也不会联网。
- 只要历史上成功导入过 akshare，且未显式关闭，定时刷新会继续维护这部分主数据；否则只刷新本地来源。
- 过期阈值不是环境变量，需修改代码常量或使用 CLI `--max-age-hours`。

## 9. 运维 SOP

### 9.1 首次部署 / 新数据目录

```bash
./env/Scripts/python.exe -m research_entities.cli sources-status
# 预期：全部 never_imported

./env/Scripts/python.exe -m research_entities.cli refresh --with-akshare --max-age-hours 168
# 预期：导入 gazetteer_json / universe_json / akshare_security / exchange_profile
```

### 9.2 日常巡检

```bash
./env/Scripts/python.exe -m research_entities.cli sources-status
```

重点关注：

- `stale_sources` 是否非空；
- `last_status=failed` 的来源；
- `warnings` 中是否出现新的名称冲突或接口不可用。

API 方式：`GET /research/sources`，`stale_sources` 为空即正常。

### 9.3 出现失败时

1. 看 `last_error` / `warnings`，判断是网络、代理还是上游接口变化。
2. 修复后执行 `refresh`（只重试过期/失败来源）；必要时 `--force`。
3. 失败不会清空旧数据，实体仍可正常使用，Scope 会给出「使用上一次成功导入的数据」提示。

### 9.4 离线环境

```bash
set RESEARCH_ENTITIES_AKSHARE_SOURCE=false
```

或在启动脚本中设置。此后：

- 手动导入只含本地来源；
- 定时刷新只检查并刷新 `gazetteer_json` / `universe_json`；
- `exchange_profile` / `akshare_security` 保持已有数据，不发起网络请求。

### 9.5 关闭后台刷新

```bash
set RESEARCH_ENTITIES_REFRESH_ENABLED=false
```

关闭后仍可手动使用 CLI 或 `POST /research/sources/refresh`。

### 9.6 排障

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `refresh` 返回「刷新已被占用」 | 另一进程正在导入，或锁文件残留 | 等待导入结束；确认无进程后删除 `data/research_entities.refresh.lock` |
| akshare 来源 `last_error` 含代理/SSL 错误 | 系统代理或证书路径 | 确认启动环境未覆盖 `NO_PROXY`；工厂会自动安装代理绕过与 ASCII 证书路径 |
| `database is locked` | 长事务或外部工具占用 | 等待重试；SQLite 已配置 WAL 与 5 秒 busy timeout |
| `never_imported` 长期不消失 | 该来源未启用（如 akshare 关闭） | 属预期；需要时手动 `--with-akshare` 导入 |
| 调度器未启动 | 使用内存仓储，或显式关闭 | 检查 `refresh_enabled` 与存储配置 |

## 11. 边界与后续事项

### 11.1 当前边界

1. **深交所法定名称缺失**：免费名录不提供，未编造；权威值仍由 `company_profile` 实时查询。
2. **`supply_demand_lookup` 仍未配置**：没有可复现的免费供需平衡表数据源，保持 `unconfigured` 并明确披露，不用库存/价格冒充。
3. **部分实体类型仍无本地实例**：`ENTITY_02_02`、`02_03`、`04_03`、`04_04`、`05_01`、`05_03`。工具可通过关联实体或参数触发，但按类型直接列清单会为空。
4. **阈值是静态常量**：需要按来源调整时改代码或单次 CLI 覆盖，暂不支持环境变量。
5. **刷新是同步执行**：API 手动刷新在请求线程中完成，大数据量时会占用一个工作线程。
6. **PostgreSQL 适配器未实现**：当前只有 SQLite 与内存仓储；调度器只对 SQLite 默认启用。
7. **非领域异常不留 failed 记录**：依赖库抛出的非 `ResearchEntityError` 异常会直接上抛，不会写入 `source_imports`。

### 11.2 建议的后续方向

- 若获得授权的付费或官方供需数据，再实现 `supply_demand_lookup`。
- 若需要深交所法定名称，可评估巨潮批量接口或交易所官方文件下载，但必须控制请求量与频率。
- 若引入股权关系/事件流数据源，再补充 `02_02` / `02_03` / `04_03` 等实体实例。
- 多进程部署时，文件锁仍有效，但建议改为仓储级 advisory lock；当前单机单实例场景无此必要。
