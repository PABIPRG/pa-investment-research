# PAB-29：升级 Action 自动更新部署器

## 目标与授权边界

用户继续只操作镜像构建与应用升级两个 Action。升级在 Production 审批后自动同步所需的 `deploy.py`，核对摘要后进入现有备份、切换和健康检查。`connectivity` 保留为可选的只读诊断。

已确认在独立 worktree `pab29-deployer-auto-update`、基准 `3713ea719f3ca1a5779dde8f630da4451e76547c`、分支 `codex/pab29-deployer-auto-update` 实施。代码与本地验证已授权；服务器安装、触发工作流、提交、推送、PR 和合并分别遵守授权边界。

## 实现与信任边界

1. 新增一次安装的 root 固定更新器、无参数 shell 入口及独立最小 sudoers 条目。保留 aly 现有 Python 3.11 部署入口、原 sudoers 和应用配置。更新器本身及权限配置仍由管理员维护，不允许自动自修改。
2. CI 仅传入部署工作流源码的完整提交 SHA 与预期 SHA-256。更新器不接受调用者提供的源码、URL、目标路径或 shell 命令。
3. 更新器通过验证 TLS 的固定 GitHub API 独立核实提交位于固定公仓 master 历史，读取固定路径 `ops/pa-investment/deploy.py`，核对文件类型、长度、Git blob 与 SHA-256，并编译检查语法。服务器需要访问 api.github.com；使用公开读取，不保存凭据。请求与总执行时间均设上限，失败时停止升级。
4. 镜像版本与部署器版本分别固定。服务器记录上次实际安装的部署器源码提交，拒绝祖先回退或分叉；同一版本重复请求保持幂等。升级旧应用镜像不要求退回旧部署器。
5. 更新与部署共用 deploy.lock，存在 active.json 时禁止更新。替换前保存旧源码和更新日志，使用同目录临时文件、fsync、原子替换；更新日志用于恢复源码与版本记录之间的中断。普通失败尝试立即恢复旧脚本，恢复失败则保留日志闭锁；进程被强制终止时由下一次更新恢复。部署器发现未完成更新时拒绝启动应用升级。
6. 原有哈希检查仍在更新后、交付 registry token 前执行。更新失败不会进入停服或镜像切换。

## 实施顺序与验证

1. 为固定来源、摘要不符、版本倒退、重复执行、活动部署、并发锁、替换失败、中断恢复编写先失败用例。
2. 实现更新器与一次性安装入口，并接入现有升级工作流。补充待恢复脚本更新的部署闭锁。
3. 更新运维说明，明确一次性安装、日常两个 Action、失败处置、备份与回退位置。
4. 运行部署相关 Python 测试、Shell 语法、actionlint 与 diff 检查。测试只使用隔离临时文件、模拟 GitHub 响应，不访问 aly、不调用真实 Docker。
5. Linux CI 的归档恢复、服务器一次性安装、真实 GitHub 出站连通、Production 审批后完整升级和业务验收列为待验证。代码完成或本地通过不能标记生产修复完成。

## 回退

未进入应用部署时只恢复部署器源码与版本记录，不改应用容器或数据。一次性安装前备份新增入口的已有文件；撤销入口时停用独立 updater sudoers。若应用已开始升级，继续按现有 active.json、备份和人工恢复流程处理，更新器不回退应用数据。
