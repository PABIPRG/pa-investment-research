# PAB-29 镜像拉取失败后的部署器改进

## 事实与目标

2026-09-24 的生产部署在 `preparing` 阶段拉取不可变 GHCR 镜像时，两次镜像层下载出现 `unexpected EOF`，随后触发 900 秒拉取时限。旧容器和对外健康端点保持正常，人工核实后归档了 `active.json`。本次改动降低短时传输中断造成的失败成本，保留停服前拉取、不可变 digest、短期凭据和失败闭锁。

## 现有能力与决策

| 用户动作 | 现有入口 | 权威状态与副作用 | 缺口 | 决策 |
| --- | --- | --- | --- | --- |
| 核对候选镜像 | `ci.py preflight` | 构建 run、发布清单、GHCR config ID | 已覆盖来源与身份 | 复用 |
| 拉取镜像 | `DockerDriver.pull_private_image` | Docker 本地镜像缓存；旧服务未停 | 单次拉取、统一错误文案 | 扩展 |
| 记录部署失败 | `transact` 的 `status.json`、`active.json` | 阶段、失败标记、后续部署闭锁 | 安全的准备阶段失败也需人工解除 | 扩展 |
| 核对服务器部署器版本 | Actions SSH 预检 | 服务器 root 安装的脚本 | PR 合并不更新已安装脚本 | 扩展 |

所有判断均由脚本中的确定性检查完成，不使用模型推断。Docker 原始 stderr、凭据、环境文件及容器环境变量不进入公开日志或状态记录。

## 实施顺序

1. 对精确 digest 的 `docker pull` 做至多两次完整尝试；每次最多 900 秒，失败后短暂退避。仅重试拉取，不重试登录、身份校验、停服、备份或切换。保留临时 `DOCKER_CONFIG`，结束后删除。将超时、非零退出和尝试次数记为安全字段。
2. 只有在拉取最终失败且重新核实旧容器 ID、镜像、健康、唯一卷写入者、备份空间、Compose 与 `.env` 完全未变、对外健康端点正常时，才把 `preparing` 失败状态和核验证据保存在记录目录，并解除 `active.json`。核验异常、诊断记录写入失败、中断或其他阶段失败继续保留恢复标记。
3. 部署工作流先比较仓库 `deploy.py` 与服务器已安装脚本的 SHA-256。版本不一致时在调用部署入口前失败，不发送 registry token。将 deploy job 上限增加到足以覆盖两次拉取及现有备份上限。
4. 更新恢复手册，明确合并 PR 后须由管理员更新服务器脚本、保留 `aly` 已适配的 Python 3.11 wrapper 和 sudoers，并先走 connectivity，再批准 deploy。

## 验证与回退

- 先用失败测试覆盖超时/退出分类、一次失败后成功、两次失败、登录不重试、凭据临时目录清理、准备阶段自动解锁与核验失败闭锁、工作流版本门禁。
- 运行 `ops/pa-investment` 聚焦单测、Shell 语法与 workflow 静态检查；审查状态记录中没有凭据和环境正文。
- PR 合并后，服务器安装、连接核验及再次生产部署是独立操作，需对应授权。若新逻辑失败，保留旧容器和失败记录；如已进入停服阶段，继续使用原有人工恢复手册，不自动回退数据。
