## 一、发版前核对

1. 发布修复经 PR 合并到公仓 master。版本来源为 frontend/package.json，Electron 等共享版本通过 constraints 检查。
2. 检查目标标签和 Release，不覆盖已发布版本。版本号已发布后，任何修复必须提升版本。
3. 准备面向用户的发布说明、平台文件映射、首次使用流程和已知限制；不要只保留自动生成的 PR 列表。
4. GitHub 仓库已开启不可变 Release；github-release Environment 已配置 reviewer、master 部署限制及 INVESTMENT_RELEASE_GUARDS_READY=true。
5. 区分本地候选包、PR 临时产物和正式发布附件。不能将工作区手工修改的包直接当成某个主线提交的发布包。

本次用户接受迁移问题延期，不代表该缺陷已修复。正式签名、公证和未完成的实际平台验收必须如实标明。

## 二、触发发布

在 Actions 选择 **Release investment desktop → Run workflow**：

- Branch：master
- expected_version：与源码完全一致，本次为 0.1.0-rc.11
- channel：prerelease

或执行：

```bash
gh workflow run investment-release.yml \
  --repo PABIPRG/pa-investment-research \
  --ref master \
  -f expected_version=0.1.0-rc.11 \
  -f channel=prerelease
```

工作流读取版本并锁定当时的完整 SHA。正在构建时 master 后续合并不会改变本轮源码，不应重复点击 Run workflow。

## 三、构建与审批

预检通过后，对 macOS ARM64、macOS Intel、Windows x64 分别构建 ZIP，执行后端打包隐私检查和包内冒烟。三个平台都通过才进入 Publish GitHub Release。

出现 **Review deployments** 时，核对运行号、SHA、版本及构建结果，选择 github-release，再批准。没有出现按钮通常表示构建尚未完成或前置步骤失败，不能据此判断需要再触发一轮。

发布 job 会汇总三个 ZIP，生成并验证 SHA256SUMS，生成构建来源证明，创建标签和草稿 Release、上传资产，最后转为已发布 Pre-release。

## 四、发布后的验收

- [ ] 工作流成功，Release 标为 Pre-release，标签指向锁定 SHA。
- [ ] 三个 ZIP 和 SHA256SUMS 齐全，可从 Release 页面下载。
- [ ] 下载附件的 SHA256 与校验文件一致，构建来源证明对应本次工作流。
- [ ] 在 GitHub Release 的 Edit 页面填写面向用户的发布说明，附上[首次使用与数据迁移指南](../user-guide/首次使用与数据迁移.md)的仓库链接；删除发布前草稿提示，保留自动生成的变更列表及工作流归属标记。
- [ ] 实际设备验证完整解压、首次启动、模型配置、持仓/研究入口；记录平台、系统版本、包哈希和结果。
- [ ] 未验证的平台或功能明确标为未验证，不以构建成功替代用户验收。
- [ ] 将下载链接、运行号、提交与验收证据写回 PAB-15；延期问题保持可追踪，不自动标 Done。

发布说明更新属于元数据维护，不替换 ZIP、移动标签或重新发布同版本。对应用有改动时走新版本。

## 五、失败处理

| 失败位置 | 处理 |
|---|---|
| 版本输入不匹配 | 核对源码版本，不用输入参数冒充版本升级 |
| 标签真实冲突或版本已发布 | 使用新版本，不删除已有正式资产或移动标签 |
| 任一平台构建/扫描/冒烟失败 | 根据日志修复后重新验证，不发布缺平台或未验证的包 |
| 等待 Environment 审批 | 核对负责人和运行内容后批准，不关闭保护措施 |
| 上传或发布中断 | 先查 Release 的 draft、目标 SHA 与归属标记；脚本只允许清理由同一 SHA 工作流拥有的草稿 |
| 已经成功发布但发现应用问题 | 保留原始发布记录，评估新版本修复；不得覆盖旧 ZIP |

如果只是瞬时基础设施错误，确认后可重跑相同提交；如果修复了工作流或代码，必须从合并后的主线新触发，重跑旧失败运行不会自动使用新代码。
