# 成交明细导入 — 前端接入说明

> 面向前端开发。后端实现细节见 [券商接入方案.md](券商接入方案.md) §成交明细导入；这里只讲**前端要调什么、拿到什么、怎么渲染错误**。

## 一句话

把券商客户端里的「历史成交」读成结构化的本地明细，并给出交易频率、集中度、数据覆盖度三个指标。

前端要做的就三件事：**判断按钮该不该出现** → **走「预览 → 确认」两步** → **把指标和错误态渲染出来**。

## 路由总览

| 方法 | 路径 | 作用 |
|------|------|------|
| GET | `/holdings/source?surface=web\|electron` | 能力发现：这一屏该不该显示「同步成交明细」 |
| POST | `/trades/sync` | 读客户端成交明细。默认只预览，带 token 才是提交 |
| POST | `/trades/clear` | 清空本地成交明细。同样是预览 → 提交 |
| GET | `/trades` | 读本地已有的明细 + 指标。**不碰客户端**，随时可调 |

三条写入路由的错误形态与持仓那三条完全一致（`readiness` / `blocking_reason` / `reason`），**前端可以直接复用持仓同步那套错误分支**，不用再写一份。

## 一、按钮该不该出现

调 `GET /holdings/source`，看 `available_actions` 里有没有 `read_trades`：

```json
{
  "provider": "easytrader",
  "label": "同花顺（Windows）",
  "platform": "win32",
  "surface": "electron",
  "available": true,
  "reason": null,
  "installation": "installed",
  "process": "running",
  "accessibility": "not_applicable",
  "automation": "not_applicable",
  "session": "unknown",
  "readiness": "ready",
  "blocking_reason": null,
  "available_actions": ["manual", "recheck", "read", "read_trades"],
  "account_mode": "real",
  "supported_account_modes": ["real", "simulated"]
}
```

**一定要把 `surface` 传对**（`web` 还是 `electron`）。后端据此判断：

- `available_actions` 里有 `read` —— 能做持仓同步；
- 有 `read_trades` —— 能做成交导入。

没给按钮时**不要自己判断原因**，直接把 `reason` 显示给用户，它已经是给人看的文案了。

下列情况 `read_trades` 不会出现（后端已挡掉，前端不用重复判断）：

| 情况 | 为什么 |
|------|--------|
| 数据源是 `manual` / `qmt` / `joinquant` | 本期没接入成交读取 |
| Windows + `surface=web` | 读成交必须抢前台，网页版没有认证宿主通道 |
| 券商是银河 / 华泰 / 五矿 / 海通 / 国金 / 广发的**专用客户端** | 这六家没有同花顺那套「查询 → 历史成交」左树，本期未接入 |

> 最后一类容易误判：它们的数据源同样是 `easytrader`，**能读持仓不代表能读成交**。别用"数据源是 easytrader"当条件，要看 `available_actions`。

## 二、导入流程：预览 → 确认

### 第 1 步：预览

```http
POST /trades/sync
{}
```

（`action` 默认就是 `preview`，请求体可以整个省略。）

成功时返回**预览态**，`readiness` 是 `"preview"`：

```json
{
  "preview_token": "f3gFtYtEAERlptTsY91DHsXh_BoMa_daEw7MD5efc88",
  "kind": "import",
  "items": [
    {
      "ticker": "600879", "name": "航天电子", "side": "buy", "side_label": "买入",
      "price": 21.51, "quantity": 100.0, "amount": 2151.0,
      "traded_at": "2026-07-13T14:49:48", "trade_id": "79726064",
      "source": "easytrader", "account_mode": "real", "occurred": 1
    }
  ],
  "previous_count": 0,
  "unclassified": 1,
  "account_mode": "real",
  "account_label": "真实操盘",
  "provider": "easytrader",
  "label": "平安证券",
  "read_at": "2026-09-15T10:20:45.039192+00:00",
  "expires_in_seconds": 300,
  "readiness": "preview",
  "session": "ready",
  "surface": "electron",
  "platform": "win32"
}
```

> `read_at` 是带 `+00:00` 偏移的 ISO8601，不是 `Z` 结尾。按本地时区渲染时别忘了转换。

界面要展示的：

- `items` —— **本次读到的**成交（不是合并后的全量，见下面「容易踩的点」）；
- `previous_count` —— 本地已有多少条，用来提示"将新增 N 条"；
- `unclassified` —— 其中有多少条不是普通买卖（送股、红利入账等），建议单独提示；
- `label` / `account_label` —— 从哪家、哪个账户读的；
- `expires_in_seconds` —— 预览有效期 300 秒。

### 第 2 步：提交

```http
POST /trades/sync
{ "action": "commit", "preview_token": "8Kd3..." }
```

返回在预览结构上追加了提交结果：

```json
{
  "preview_token": "f3gF...", "kind": "import", "items": [ ... ],
  "cleared": false,
  "saved": 8, "added": 8,
  "duplicates": 0,
  "unclassified": 1,
  "conflicts": [],
  "record": {
    "source": "easytrader", "account_mode": "real",
    "read_at": "2026-09-15T10:20:45.045907+00:00",
    "fetched": 8, "added": 8, "duplicates": 0, "unclassified": 1, "conflicts": 0,
    "range_start": "2026-06-26", "range_end": "2026-07-20"
  },
  "entries": [ /* 本次真正写进去的那几条 */ ]
}
```

- `added` / `saved` —— 本次新增（两个字段同值，`saved` 是为兼容持仓那边的命名）；
- `duplicates` —— 已存在、被跳过的条数。**这是正常现象不是错误**：同一个交易日会被反复导入；
- `conflicts` —— 去重键相同但内容不同的条目（见下）；
- `entries` —— 本次真正写进去的条目。

**重复导入长这样**（同一批 8 条，其中 6 条之前已导入过）：

```json
{ "saved": 2, "added": 2, "duplicates": 6, "cleared": false,
  "record": { "fetched": 8, "added": 2, "duplicates": 6, ... } }
```

界面建议提示「本次新增 2 条，6 条已存在已跳过」，而不是"同步完成"。

### `conflicts` 怎么处理

```json
[{ "key": ["id", "real", "2026-07-13", "79726064"],
   "changed_fields": ["price"],
   "existing": { ... }, "incoming": { ... } }]
```

`key` 是去重键的原始元组，第一个元素是键的类型：`"id"` 表示客户端给了成交编号（后面是账户、成交日期、成交编号），`"fields"` 表示没有编号、退化成字段组合键。**前端不需要解析它**，原样展示或只用来做列表 key 即可。

含义是：**这笔成交之前存过，但客户端这次给的内容不一样**（价格变了之类）。后端**保留原有条目**，只把差异报出来。

前端不要自动覆盖，也不要弹阻塞式弹窗——列成一条"有 N 笔与已有记录不一致，建议人工核对"的提示，能展开看两个版本即可。

### `preview_token` 的两个约束

1. **一次性**：提交成功后即失效，重复提交会拿到 `preview_conflict`；
2. **300 秒过期**，过期同样是 `preview_conflict`，提示用户重新读取。

提交时后端会重新核对账户口径、数据源、数据目录，以及**本地明细有没有被别处改动过**。任何一项变了都返回 `preview_conflict` —— 这是为了不让用户确认的范围和实际写入的范围不一致。

## 三、清空流程

同样是两步，同一个 token 机制：

```http
POST /trades/clear                      → 预览
POST /trades/clear  { "action": "commit", "preview_token": "..." }   → 执行
```

预览返回：

```json
{ "preview_token": "...", "kind": "clear", "will_remove": 8,
  "last_import_at": "2026-09-15T09:12:33.421Z", "readiness": "preview" }
```

**必须让用户看到 `will_remove` 再确认**（明说"将删除 N 条成交明细"），本地没有明细时会返回 `empty_result`。

## 四、读本地数据与指标

```http
GET /trades
```

不触发任何客户端读取，进页面就可以直接调。

```json
{
  "entries": [ /* 全部成交明细 */ ],
  "imports": [ /* 每次导入的审计记录 */ ],
  "last_cleared": null,
  "profile": { "frequency": {...}, "concentration": {...}, "coverage": {...}, "caveats": [...] }
}
```

### `profile.frequency` — 交易频率

```json
{ "trades": 8, "buy_count": 5, "sell_count": 2, "unclassified_count": 1,
  "active_days": 5, "buy_sell_ratio": 2.5, "trades_per_active_day": 1.6 }
```

> `buy_sell_ratio` 和 `trades_per_active_day` **可能是 `null`**，不是 0。前者表示"没有卖出"，后者表示"没有成交日"。请渲染成 `—`，不要显示 0 —— 「没有卖出」和「买卖均衡」是两回事。

### `profile.concentration` — 集中度（**只统计股票**）

上面那 8 条明细算出来的实际结果：

```json
{ "amount_total": 7759.5, "tickers": 1, "hhi": 1.0, "top_share": 1.0,
  "excluded_non_stock_trades": 3,
  "items": [ { "ticker": "600879", "name": "航天电子",
               "amount": 7759.5, "trades": 5, "share": 1.0 } ] }
```

**注意 `trades: 8` 但 `tickers: 1`、`excluded_non_stock_trades: 3`**：那 8 条里有 3 条是 ETF（159607、159813），被排除在集中度之外，所以只剩「航天电子」这一只股票。这不是 bug，是口径 —— 也正是 `excluded_non_stock_trades` 必须显示的原因，否则用户会以为少算了。

- `items` 已按金额降序排好，直接渲染；
- `excluded_non_stock_trades` —— **被排除在统计之外的条数**（ETF/LOF、可转债、逆回购、B 股）。这个数必须显示出来，否则用户会疑惑为什么条数对不上；
- `hhi` 是赫芬达尔指数（0~1，越大越集中），`top_share` 是第一大占比。

### `profile.coverage` — 数据覆盖度

```json
{ "start": "2026-06-26", "end": "2026-07-20", "span_days": 25, "active_days": 5,
  "read_ranges": [ { "start": "2026-06-26", "end": "2026-07-20" } ],
  "uncovered": [],
  "status": "complete", "note": null }
```

`status` 四种取值，界面上建议用不同颜色：

| status | 含义 | 建议 |
|--------|------|------|
| `complete` | 跨度内每一天都被某次读取覆盖过 | 正常 |
| `partial` | `uncovered` 里有区间**从没被读过** | 提示补数据，把 `uncovered` 列出来 |
| `unknown` | 没有区间记录（旧数据） | 不承诺完整性 |
| `empty` | 一条明细都没有 | 空态引导 |

> **关键区别**：`active_days` 和 `span_days` 的差**不是**缺数据。某天没有成交完全可能因为那天没交易；只有落在 `uncovered` 区间里才是真的没读过。请把 `uncovered` 直接展示（`note` 里有现成文案），别自己用"天数差"推算。

### `profile.caveats` — 口径说明（**必须展示**）

四条字符串数组，讲清楚这些数字的口径边界：交易频率的含义、集中度只算股票、不含成本、不含费用/无 FIFO 配对。

建议放在指标卡片附近（"ⓘ"图标或折叠区），不要丢掉——用户拿这些数字做判断，口径不说清会被误读。

## 五、错误处理

所有错误都是 HTTP 200 + 结构化 body，判断依据是 `readiness`：

```json
{ "readiness": "blocked", "blocking_reason": "client_not_running",
  "reason": "券商客户端未运行：请先启动并登录 平安证券（...）。窗口需保持打开。",
  "available_actions": ["manual", "recheck"] }
```

**`reason` 直接显示**，它已经写成用户能照着做的指引了。

> **例外：请求体本身不合法会返回 HTTP 422**（FastAPI 的校验错误，不是上面这套结构）。两个请求体都是 `extra="forbid", strict=True`：
> - 多传任何字段 → 422；
> - `action` 只能是字符串 `"preview"` 或 `"commit"`，传 `null` 或别的一律 422；
> - `preview_token` 必须是字符串，最长 128。
>
> 正常调用不会碰到，但如果前端做了"把整个响应对象原样回传"这类操作就会中招。提交时只传 `{ "action": "commit", "preview_token": "..." }` 就够了。

`readiness` 只有四种：

| readiness | 含义 | 前端动作 |
|-----------|------|----------|
| `preview` | 正常，等你确认 | 展示预览，给「确认导入」按钮 |
| `blocked` | 有明确原因，用户可修复 | 显示 `reason`，给重试/去手动录入 |
| `partial` | 读到一部分（`partial_read`） | **和 blocked 区分开**：提示"数据不完整，建议重读"，不是"去修客户端" |
| `failed` | 意外错误 | 显示 `reason`（不含内部细节），给重试 |

`blocking_reason` 常见取值：

| 值 | 什么情况 | 前端建议 |
|----|----------|----------|
| `empty_result` | 读到 0 条 / 本地没有可清空的 | 提示核对页面和日期范围，**不要当成成功** |
| `client_not_running` | 客户端没开 | 给「启动客户端」入口 |
| `navigation_required` | 页面没停对 | 提示切到「历史成交」页 |
| `automation_required` | 验证码没自动过 | 提示手工输入验证码后重试 |
| `busy` | 另一次读取正在进行 | 提示稍后重试（持仓和成交共用一把锁） |
| `preview_conflict` | token 过期/已用/本地已变 | **回到预览步骤**重新读取 |
| `account_changed` | 账户切换了 | 重新读取 |
| `unsupported_action` | 该数据源/券商不支持 | 隐藏入口 |
| `unsupported_platform` | 平台不支持 | 隐藏入口 |
| `partial_read` | 部分行无法识别 | 提示重读，**没有写入任何数据** |

## 六、容易踩的点

1. **提交是「去重合并」，不是「整体替换」。** 持仓同步是替换语义，成交不是。`items` 是本次读到的，`GET /trades` 的 `entries` 才是合并后的全量。别把 `items` 当作合并结果渲染。

2. **同一个交易日会被反复导入，这是设计。** 用户今天导一次、明天再导一次，重复的会被 `duplicates` 跳过。界面不要把"有重复"渲染成警告。

3. **`unclassified` 要照实显示。** `side` 只有 `buy` / `sell` / `unclassified` 三种，但 `side_label` 是客户端原文（「红股派息」「送股」等）。展示时**优先用 `side_label`**，`unclassified` 当兜底。

4. **`traded_at` 精度不固定。** 客户端只给到分钟就是 `2026-06-26T11:12`，给到秒就是 `2026-06-26T11:12:51`。格式化时别假设一定有秒。

5. **预览期间别让用户改账户或数据源。** 改了会导致提交时 `preview_conflict`。

6. **`GET /trades` 可以随便调**，它只读本地、不碰客户端、不抢锁。

## 七、本期还没有的能力（别先做 UI）

- **日期范围选择**：第一期由用户在券商客户端里自己设，程序只读整表。前端不需要提供日期选择器。
- **手动录入成交**：`manual` 数据源没有成交入口。
- **单笔盈亏 / 已实现收益**：没有 FIFO 配对，算不出来。
- **费用**：客户端导出里没有手续费列，金额是成交金额，不含佣金/印花税/过户费。
