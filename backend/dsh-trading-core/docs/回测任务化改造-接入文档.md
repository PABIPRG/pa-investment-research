## 0. 一句话总览

本次把「策略回测」从**覆盖式最新证据**升级为「**每次回测一条独立任务记录**」，手动与自动（首测/复测）
统一进同一历史；并新增两个只读历史接口、给手动回测补了显式时间窗口、同步了自进化标签语义。对前端的净变化：

1. `POST /strategies/run` 可选 `start_date`/`end_date` → 手动回测可指定自定义时间范围（不再只能按 2 年预设）。
2. 新接口 `GET /strategies/{sid}/backtests` → 单策略「回测管理」任务历史（手动+自动）。
3. 新接口 `GET /shadow/history` → 影子验证「交易日 × 策略」展平运行记录（影子历史三块视图的第二、三块数据源）。
4. 自进化标签统一：生命周期**不再有独立「变异」分组**（变异=来源标记）；文案见 §5。
5. **候选落池即触发首测（生成即自动回测）**：`POST /strategies/hypothesize` 落库的新候选，立即在后台
   发起默认 lookback 年（2 年）首测，不等每日巡检；见 §3.3。

数据模型层面你只需知道：**策略记录的 `backtest` 仍是「最新一次证据快照」（行为不变），历史回溯改走新的
`strategy_backtests` 集合**。读取用新接口即可，不需要直接碰 JSON 文件。

## 1. 回测任务模型（概念）

- 存储：`adapter/backtest_tasks.py`，集合 `strategy_backtests`（`data/adapter/strategy_backtests.json`，data/ 已 gitignore）。
- **一条任务 = 一次 run 调用**。写入点单一：`StrategyBacktestRunner.run()`（`adapter/strategies.py`）
  启动时 `begin_task`、收尾 `complete_task`/`fail_task`。手动（页面）、闭环 Step C、自动回测巡检三条链路都走这一处。
- 任务状态：`queued → running → completed / failed`。**没有独立创建接口**——你不需要 POST 一条任务记录，
  任务由 `POST /strategies/run`（手动）或后台巡检（自动）触发产生。

任务记录字段（键 = `task_id`；`result` 是最新证据快照，同 `strategy.backtest` 同构）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `task_id` | str | 手动：`POST /strategies/run` 返回的 task_id；自动：uuid |
| `strategy_id` | str | 策略 id |
| `source` | `manual`\|`auto` | 手动=页面发起；auto=闭环 Step C / 自动回测巡检 |
| `window` | `{start, end}` | 实际回测区间 `YYYY-MM-DD`（显式区间 = 请求给的；预设年数 = today−n×366~today） |
| `lookback_years` | float\|null | 预设年数（显式区间时为 `null`） |
| `initial_capital` | float | 初始资金 |
| `status` | `queued`\|`running`\|`completed`\|`failed` | 任务状态 |
| `created_at`/`started_at`/`completed_at` | `YYYY-MM-DD HH:MM:SS` | 时间戳（created/started 在 begin 同刻；completed 在收尾） |
| `verification_status` | `null`\|`pending`\|`passed`\|`failed` | 样本外验证分类（策略侧另有 `archived`，见 §4.3） |
| `thresholds_pass` | null\|bool | 阈值是否达标（与 verification 一致） |
| `failure_reason` | null\|str | 失败原因 |
| `result` | dict | 最新证据快照（含 in_sample/out_of_sample/reason/per_symbol/symbol_errors…） |

> 时序注意：POST `/strategies/run` 返回后，任务行在后台 worker 真正进入 `run()` 时才写入
> （`status=running`）。轮询 `GET /strategies/{sid}/backtests` 即可看到；若入口校验就失败
> （如策略不存在），`fail_task` 仍会补落一条 `status=failed` 行——**失败也会留痕**。

### 1.1 手动回测的调用等价（dsh 工具链）

`POST /strategies/run`（dsh 层 operation = `trading-core.strategy-run`），返回 `{task_id}`。
进度/结果**复用既有任务通道**（与 shadow/backtest 相同）：

- SSE：`GET /analyze/{task_id}/stream`
- 最终结果：`GET /analyze/{task_id}/result`
- 内存态（可选）：`GET /analyze/{task_id}`

**别用 task_id 去当策略名/展示主键之外的东西**：任务行属于策略，聚合入口是下面 2.2。

## 2. 新增/改动的 HTTP 端点

### 2.1 `POST /strategies/run`（改动：显式时间窗口可选）

请求体（`StrategyRunRequest`，新增 `start_date`/`end_date`）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `strategy_id` | str | ✅ | 策略 id（`[A-Za-z0-9._:-]` 安全标识） |
| `lookback_years` | float | 默认 2.0 | 历史回看年数（0.5~10） |
| `oos_frac` | float | 默认 0.3 | 样本外比例 |
| `min_oos_trades` | int | 默认 4 | 样本外最低成交数 |
| `initial_capital` | float | 默认 0 | **0=用 SHADOW_INITIAL_CAPITAL(100000)** |
| `start_date` | str `YYYY-MM-DD` | 可选 | 与 `end_date` **必须同给** |
| `end_date` | str `YYYY-MM-DD` | 可选 | ≤ 今天，`start_date < end_date` |

约束：
- `start_date`/`end_date` 要么同时不传（走 `lookback_years` 预设），要么同时传（**显式区间优先，忽略 lookback_years**）。
- 显式区间时任务行 `lookback_years=null`、`window={start,end}=` 给定值。

返回：`{"task_id": "<32hex>"}`。任务记录的 `source` 恒为 `manual`（请求体不暴露 source）。

### 2.2 `GET /strategies/{sid}/backtests?limit=50`（新增）

单策略回测任务历史，`created_at` **倒序**（最新在前）。策略不存在 → `404`。

```json
{
  "strategy_id": "strat-xxx",
  "count": 3,
  "tasks": [
    {
      "task_id": "...", "strategy_id": "strat-xxx", "source": "manual",
      "window": { "start": "2024-09-03", "end": "2026-09-03" },
      "lookback_years": 2.0, "initial_capital": 100000.0,
      "status": "completed", "created_at": "2026-09-03 15:40:11",
      "started_at": "2026-09-03 15:40:11", "completed_at": "2026-09-03 15:40:58",
      "verification_status": "passed", "thresholds_pass": true,
      "failure_reason": null,
      "summary": {
        "oos_trades": 6, "oos_win_rate_pct": 66.7,
        "reason": "样本外胜率/均收益达标",
        "symbol_error_count": 0
      }
    }
  ]
}
```

要点：
- **列表行是「摘要」，不是全量任务**：`result` 内的大块净值/持仓曲线被剔除，只留 `summary` 里的
  `oos_trades`（样本外成交数）、`oos_win_rate_pct`、`reason`（验证原因/失败原因文案）、`symbol_error_count`。
  想拿完整指标（收益/回撤等）请读该策略的 `backtest`（策略记录最新证据）或对应 `GET /strategies` 明细。
- **`tasks[0]` 就是「最近一次回测」**：详情弹窗顶部“最近一次回测状态行”直接取它即可
  （时间范围 = `window`，来源 = `source`，结果 = `verification_status` + `thresholds_pass`，
  失败 = `status=failed` + `failure_reason`）。
- 空态：`count=0`、`tasks=[]`（新策略还没跑过，或改造前的老策略没有任务行）。

> 兼容改造前老数据：老 active 策略可能没有任务行，但 `strategies.{sid}.backtest.ran_at` 仍记录着
> 最近一次回测时间（用于判断自动复测是否到期）。前端不要假设「有任务行才有回测」。

### 2.3 `GET /shadow/history?strategy_id=&limit=200`（新增）

影子验证运行历史，把 `shadow_equity/{date}` 快照**展平成 交易日×策略 记录行**。
不带 `strategy_id` = 全部策略运行记录（全局表）；带 = 单策略影子历史。日期倒序。

```json
{
  "count": 4,
  "items": [
    {
      "date": "2026-09-03",
      "strategy_id": "strat-xxx",
      "strategy_name": "XX 策略",
      "kind": "rsi_reversal",
      "initial_capital": 100000.0,
      "equity": 112350.5,
      "nav": 1.1235,
      "track_from": "2026-08-20",
      "closed_count": 3,
      "open_positions": 2,
      "symbol_errors": { "688981": "baostock 空" },
      "strategy_error": null
    }
  ]
}
```

字段与规则：
- 来源快照字段：`name/kind/initial_capital/equity/nav/track_from/closed_count/per_symbol/symbol_errors`
  （`shadow.py _snapshot`）；`strategy_error` 取快照顶层 `strategy_errors.{sid}`（策略级异常/数据原因）。
- `open_positions` = `per_symbol` 里 `qty>0` 的**持仓代码数**（后端算好，前端直接用）。
- `symbol_errors` = 该日该策略各代码数据异常 `{code: 原因}`（无异常为空对象）。
- **某日期未参与验证的策略不出行**（与 `GET /shadow/equity` 语义一致）——同一策略不同交易日数量可以不等。
- `limit` 上限 2000；`count` = 满足过滤的总条数（未截断），`items` 是截断后的行。

> 报告按钮不要逐行拼报告任务：影子验证走 scheduler 定时闭环，**没有** task_id/任务行。
> 前端「影子验证报告」统一打开既有投研报告抽屉即可。影子引擎本身零改动，本接口只是读快照。

## 3. 自动回测（后端行为，前端只读观测）

自动回测只产生 `source=auto` 的任务历史 + 刷新策略 `backtest` 证据，**不会**改变页面能感知的
「生命周期状态」——除了闭环本身既有的候选激活（见 3.2）。两条链都写进同一任务历史：

### 3.1 自动回测巡检 `backtest_patrol_daily`（新）

- 开关：`AUTO_RETEST_ENABLED=true`（默认关）；每日时刻 `AUTO_RETEST_TIME`（默认 15:40）；复测间隔
  `AUTO_RETEST_INTERVAL_DAYS`（默认 15）；窗口 `AUTO_BACKTEST_LOOKBACK_YEARS`（默认 2）。
- **参与面**：`status ∈ {candidate, active}` 且 `verification_status ∉ {archived, failed}`。
  watch 是 `evolve.state` 不是 `status`，watch 策略 `status` 仍是 `active` → **自动参与复测**。
  retired（已淘汰/已退役）/ rejected / verification=failed 的**不再建新自动任务**。
- **到期判定**：无最近完成（无 completed 任务行、策略也无 `backtest.ran_at`）→ **首测**；
  距最近完成 ≥ 15 天 → **复测**。有 `queued/running` 进行中 → 跳过（同日不重复）。
- **效果语义（对前端可观测的结果）**：

| 对象 | 回测结果 | 状态变化？ |
|---|---|---|
| candidate 首测 | 通过 | **不激活**，仅 `verification_status=passed`（人工确认生效语义） |
| candidate 首测 | 失败 | 若 `CANDIDATE_AUTO_REJECT=on` → 自动 `reject`；off 则保留 |
| active（含 watch）复测 | 任意 | **只刷新证据 + 写任务历史，绝不改生命周期**（升降级/淘汰仍只由影子进化判定） |

### 3.2 闭环 Step C（既有 `closed_loop_daily`，行为不变，只是现在补了 `source=auto`）

`verification_status` 仍为 pending 的候选，每日由闭环自动回测：通过 → **激活进影子**（`active`）、
失败 → 淘汰（`CANDIDATE_AUTO_REJECT`）。已 passed/failed 的候选天然跳过。

> 影响提示：`AUTO_RETEST_ENABLED` 和 `CLOSED_LOOP_ENABLED` 都可能开着。对前端只需知道——
> **候选可能从 `candidate` 自动变 `active`（仅闭环做），而「自动复测巡检」任何情况下都不改状态**。
> 两者对同一候选不会同日双跑：闭环只碰 pending，巡检只碰无最近完成的；跑过即落 passed/failed，另一条链自动跳过。

### 3.3 候选落池即触发首测（生成即自动回测，新）

**问题**：此前候选落池后，只有「每日巡检（默认关）/ 闭环 Step C（默认关）」会做首测——
默认配置下新生成的策略可能永远没有自动首测。

**改动**：`POST /strategies/hypothesize`（事件→假设→候选入库，即产品「从事件新建策略」）写入新候选后，
立即在**后台异步**发起该候选的**默认 lookback 年首测**（`source=auto`，写回同一任务历史），不等巡检。

- 触发是**生成当下**：`dry_run=false` 落库多少新候选，就入队多少条自动首测；
  响应新增 `auto_first_backtest` 字段（入队条数，通常 = `candidates.length`）。
- **对前端可见的净变化 = 零必改**：新候选从「回测管理」任务列表能立刻看到 `source=auto` 的首测任务
  （queued/running→completed），`verification_status` 从 `pending` 变 `passed/failed`；
  仍刷新策略记录 `backtest` 最新证据。原 hypothesize 响应其它字段不变。
- 结果语义与巡检首测一致：候选首测**通过不自动激活**（`verification_status=passed`，人工确认生效，
  需要进影子时仍走页面「进入影子验证/激活」）；**失败**且 `CANDIDATE_AUTO_REJECT=on` → 自动 `reject`。
- 幂等/去重：`create_candidates` 按事件+kind+symbols 去重，同日重复生成同候选不会双跑；
  已有进行中任务（queued/running）或已完成证据的跳过。
- 自进化产生的子策略（闭环 mutate → Step C）不在本条触发范围内——闭环 Step C 会**同轮**回测并通过即激活。

## 4. 与既有只读接口的关系（避免接重/接错）

| 数据 | 用哪个 | 为什么 |
|---|---|---|
| 策略池 / 明细（含最新 `backtest` 证据、`verification_status`） | `GET /strategies` | 不变 |
| 回测**历史任务** | `GET /strategies/{sid}/backtests` | 新，本改动的重点 |
| 影子**最近一次**运行汇总 | `GET /shadow/status` | 不变（三块视图的第一块） |
| 影子**净值序列**（画净值曲线用） | `GET /shadow/equity` | 不变 |
| 影子**运行记录表**（每交易日每策略一行） | `GET /shadow/history` | 新，三块视图第二、三块 |
| 影子当前持仓 | `GET /shadow/positions` | 不变 |

`verification_status` 取值全集（策略与任务共用的验证分类）：`pending / passed / failed`，
外加策略记录上 retired 时写的 **`archived`**（“已淘汰/已退役”）。任务行的 verification 不会出现 `archived`。

## 5. 自进化语义统一（P5，改的是响应语义 + 前端文案映射）

`GET /evolution/status` 的 `lifecycle` / `counts` **不再含独立 `mutated` 分组**：

```json
{
  "closed_loop_enabled": true,
  "lifecycle": { "active": [], "candidate": [], "retired": [], "watch": [], "rejected": [] },
  "counts": { "active": 0, "candidate": 1, "retired": 0, "watch": 0, "rejected": 0 },
  "per_strategy": [],
  "recent_applied": [],
  "last_applied_at": null
}
```

- **变异 = 来源标记，不是独立运行状态**：变异产生的子策略按真实 `status`（生成时是 `candidate`）
  落桶，记录上带 `source="evolution"` / `mutated_from=<母策略id>`。前端要做来源角标（如「· 变异」）
  就按 `source==='evolution' || mutated_from 非空` 判断；不要为旧格式里的 `mutated` 桶独立建分组导航。
- 文案映射（后端 `per_strategy[].behavior` 已是统一后的文案，前端兜底表请对齐）：

| 概念 | 旧文案 | 统一后 |
|---|---|---|
| 带内无动作 | 带内运行 | **正常运行**（`behavior` 默认值） |
| watch 观察 | — | **观察中**（`GROUP_LABELS.watch`） |
| 已到 tier2 不重复升级 | tier 2 / 带内运行 | **已升级**（后端对该类 no-action 策略 `behavior` 直接返回 `已升级`，并带 `tier>=2`） |
| retired | 已退役 | **已淘汰/已退役** |
| 升/降/淘汰动作 | 升级/降级/淘汰 | 升级 / 降级观察 / 已淘汰·已退役（决策文案见下） |

- `per_strategy[].decision` 取值：`promote / demote / retire / none`；`behavior` 是“运行状态/动作”的
  描述性文案，后端已含：`正常运行 / 已升级 / 降级观察 / 降级观察中 / 待判定 / 升级 / 升级+变异 / 淘汰`。
  前端展示优先级建议：动作行用 `decision→文案`；no-action（`decision=none`）**优先用 `behavior`**
  （能区分 正常运行/已升级/降级观察中/待判定，比统一“正常运行”信息量高）。

## 6. dsh 桥接层契约（python-runtime，已同步）

`frontend/packages/investment-research/python-runtime/src/types.ts` 的 `InvestmentDataOperation` 新增：
`'trading-core.strategy-backtests'`、`'trading-core.shadow-history'`；`'trading-core.strategy-run'` 支持
`start_date`/`end_date` 可选键。`data.ts` `SPECS` 三条均已加 key 校验（前端传多/传错键直接抛 TypeError）。

调用示例：

```ts
// 回测管理任务历史（单策略）
requestData({ operation: 'trading-core.strategy-backtests', input: { strategy_id: sid, limit: 50 } })
// → { strategy_id, count, tasks: [ { task_id, source, window, lookback_years, initial_capital,
//        status, created_at, started_at, completed_at, verification_status, thresholds_pass,
//        failure_reason, summary: { oos_trades, oos_win_rate_pct, reason, symbol_error_count } } ] }

// 新建回测任务：预设窗口
requestData({ operation: 'trading-core.strategy-run', input: { strategy_id: sid, lookback_years: 1 } })
// 新建回测任务：自定义区间（必须 start_date+end_date 同给）
requestData({ operation: 'trading-core.strategy-run', input: { strategy_id: sid, start_date: '2025-01-01', end_date: '2026-08-31' } })

// 影子历史：全部策略运行记录
requestData({ operation: 'trading-core.shadow-history', input: { limit: 200 } })
// 影子历史：单策略
requestData({ operation: 'trading-core.shadow-history', input: { strategy_id: sid } })
```

直连 HTTP 等价：`POST /strategies/run`、`GET /strategies/{sid}/backtests?limit=`、
`GET /shadow/history?strategy_id=&limit=`。

`POST /strategies/hypothesize`（`trading-core.strategies-hypothesize`）响应新增 **`auto_first_backtest`**
（本次落库候选后台自动首测的入队条数，通常 = `candidates.length`），原有 `n_events/hypotheses/candidates`
不变。该 operation 响应不做 key 校验，**前端无需改契约**；若想展示「已自动发起 N 条首测」可直接读它。

**⚠️ 双构建**：新 operation / 新 key 必须 `npm run build:lib:host && npm run build:lib:client`，
否则跑在 host 里的 dsh 与 Electron renderer 的双白名单会静默拒绝请求（返回空/报错但不提示缺字段）。

## 7. 验收自测建议

1. **手动跑一条**：`POST /strategies/run {strategy_id, lookback_years:2}` → 轮询
   `GET /strategies/{sid}/backtests` 看到 `source=manual` 的 `running→completed`，`verification_status`
   与策略明细一致；`tasks[0].window` = 2 年区间。
2. **自定义区间**：再跑 `{start_date:'2025-01-01', end_date:'2026-08-31'}` → 新任务 `window` 为该区间、
   `lookback_years=null`。
3. **失败留痕**：对不存在/已删策略 `run` → SSE failed + 列表出现 `status=failed`、`failure_reason` 非空。
4. **影子历史**：不带/带 `strategy_id` 各调一次，确认列齐全、某日未参与的策略不出行。
5. **自动复测**：`AUTO_RETEST_ENABLED=true` 且把 `AUTO_RETEST_INTERVAL_DAYS` 调很小后等 job 触发，
   或直接在 `AUTO_RETEST_TIME` 后看 `strategy_backtests` 是否多出 `source=auto` 行。
6. **生成即首测**：从事件新建策略（`hypothesize` dry_run=false）后，回到策略详情「回测管理」——
   新候选应立刻出现 `source=auto` 的首测任务（2 年区间），完成即 `verification_status=passed/failed`；
   响应 `auto_first_backtest` = 入队条数。重复确认同批事件不会重复建任务。
